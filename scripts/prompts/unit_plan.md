# 単元の構成の仕様（資格対策）

資格対策の学びの**単元**（シラバスの中分類。`data/<対象>/syllabus.json` の `items[].middle_no`）ごとに、
学ぶ順を決める「単元の構成」を 1 つ書くための指示書。担当は **1 単元に 1 体**。

単元の構成は、次の 3 か所が読む。

- 画面: 単元のページを「全体像 → まとまりの見出し → 学ぶ順の論点」で示し、論点のページで「先に読むと良い論点」へ導く
- 書き直しの束を作る道具: まとまりを 1 つの束にし、受け持ちと前提を書き手に渡す（`scripts/prompts/rewrite_materials_by_group.md`）
- 教材の書き手: 受け持ちでない説明を繰り返さない。比較と、全体像・まとまりの説明に書いた注意は、学ぶ順で後の論点が受ける（`scripts/prompts/write_materials.md` の「他の論点との分担」）

---

## なぜ要るか

単元の中を出題の多い順に並べると、前提が後ろに来る（データベースでは土台の関係データベース・主キーより先に正規化が来る。セキュリティでは暗号化が 80 番目あたりにある）。
同じ説明を論点をまたいで何度も言う（関係演算の 3 つを 4 本、利益の 5 段階を 3 本、認証局を 5 本で説明している）。
学習者が読む前に欲しいのは、単元の地図・先に読むと良い論点・名前が似た語への注意だった。

**出題回数は学ぶ順に使わない。** 出題回数は画面の印と「次に学ぶ」の推薦が使う。この仕様書が決めるのは学ぶ順だけ。

---

## 入力

`data/<対象>/unit_inputs/<単元番号 2 桁>.json`（書き直しの束を作る道具が作る。担当は作り直さない。形の正本は UC-026 の契約の `writeUnitInput`）

```json
{
  "unit_no": 21,
  "unit": "データベース",
  "field": "テクノロジ系",
  "major": "技術要素",
  "topics": [
    {
      "topic_id": 214,
      "term": "関係データベース",
      "syllabus_item": 54,
      "syllabus_item_name": "データベース方式",
      "question_count": 3,
      "related_terms": ["…"],
      "explanation": "…（今の最も新しい世代の教材）",
      "detail": "…"
    }
  ]
}
```

- `topics` はその単元の全論点。並びは小項目の番号の順、同じ小項目の中は論点 ID の順（学ぶ順ではない）
- `explanation`・`detail` は、教材の世代を古い順に重ねて論点ごとに最も新しい物（配る本文と同じ選び方）
- 論点 ID は `data/<対象>/topic_ids.json` の値。並び順から採らない

## 出力

`data/<対象>/unit_plans/<単元番号>.json`（単元番号は 2 桁。例 `21.json`）。担当は自分の単元のファイルだけを書く。

```json
{
  "unit_no": 21,
  "unit": "データベース",
  "overview": "表の形でデータを持ち、キーで表どうしをつなぐ仕組みを学びます。設計（キーと正規化）、操作（関係演算と SQL）、障害に備える処理（トランザクションと回復）の順に進みます。正規化の「一貫性」と ACID 特性の「一貫性」は別の意味です。",
  "groups": [
    {
      "name": "表とキー",
      "description": "データを表で持ち、行をキーで見分けてつなぐ土台です。",
      "topics": [214, 220, 205, 203]
    },
    {
      "name": "表を操作する",
      "description": "表から行や列を取り出し、表どうしを組み合わせる操作です。",
      "topics": [201, 230, 231, 232, 222]
    }
  ],
  "owners": [
    {
      "subject": "関係演算の 3 つ（選択・射影・結合）",
      "owner": 201,
      "topics": [201, 230, 231, 232]
    }
  ],
  "prerequisites": {
    "205": [203],
    "201": [214]
  }
}
```

例の論点 ID は形を示すための仮の値（実在の ID は `unit_inputs` の `topic_id` から採る）。
形の正本は `docs/goals/GOAL-10-verify-content-before-delivery/UC-024-check-unit-plans-at-gate/contract.yaml` の `UnitPlan`、上限と下限の値の正本は同じ契約の `limits`（下の表の数はその写し）。

| キー | 中身 | 機械が見る決まり（門が止める） |
| --- | --- | --- |
| `unit_no` | 単元の番号（`syllabus.json` の `middle_no`） | ファイル名の番号と同じ。その対象のシラバスに実在する |
| `unit` | 単元の名前（`syllabus.json` の `middle`） | `unit_no` の名前と同じ |
| `overview` | **全体像**。この単元で何を学ぶかを 2〜3 文 | 空でない文字列 |
| `groups[]` | **まとまり**。並びが学ぶ順 | 1 つ以上 |
| `groups[].name` | まとまりの名前 | 空でない文字列。同じ単元の中で重ならない |
| `groups[].description` | まとまりの 1 行の説明 | 空でない文字列 |
| `groups[].topics` | 論点 ID の並び。並びがまとまりの中の学ぶ順 | 論点 ID は整数。8 個まで |
| `owners[]` | **受け持ち**。複数の論点が同じ説明を要る共通の前提の説明と、それを受け持つ論点 | 無ければ空の配列 |
| `owners[].subject` | またがる説明の名前（「利益の 5 段階」など） | 空でない文字列 |
| `owners[].owner` | 受け持つ論点の ID | `owners[].topics` の中で、学ぶ順で最初に出る論点 |
| `owners[].topics` | その説明に触れる論点の ID（受け持ちを含む）。2 つ以上 | この単元の論点だけ |
| `prerequisites` | **前提**。キーは論点 ID の文字列、値は先に読むと良い論点の ID の配列 | 下の「前提」 |

**門が止める、単元の全体の決まり**: その単元の論点は、すべて**ちょうど 1 つのまとまり**に入る（入っていない論点・2 つのまとまりに入る論点・この単元に無い論点 ID・実在しない論点 ID があれば止まる）。

---

## 決め方

### 1. 全体像（`overview`）

- この単元で何を学ぶかを 2〜3 文で言う。細部の要約ではなく、単元の中心の考えと、まとまりの流れ
- 敬体（です・ます）。記法（`**`・`[[ ]]`）は使わない
- 名前が似た語・対になる語への注意は任意。全体像に書くのは 1 つまでで、ほかの注意は、その語を習うまとまりの説明（`description`）に書く（例「正規化の一貫性と ACID 特性の一貫性は別の意味です」「バリューチェーンと VE は別物です」）
- 書いた注意は、教材のどこかが必ず受ける。受けるのは、比べる 2 つのうち学ぶ順で後の論点（教材の書き方は `scripts/prompts/write_materials.md` の「他の論点との分担」）。受ける論点が単元の中に無い注意は書かない

### 2. まとまり（`groups`）

- 1 まとまりは **3〜8 論点**。8 を超えると書き直しの束に入りきらない（門が止める）。3 を下回るのは、論点の少ない単元でほかに分けようが無いときだけ（門は知らせる）
- **束ね方**: 中身で関係する論点を束ねる。小項目の番号順で束ねるだけで前提の順になる単元（例: データベース）はそれでよい。小項目が粗すぎる単元（例: セキュリティの対策・実装技術に 45 論点）は、関連語の束（暗号と証明書・認証・無線・攻撃の手口・管理の仕組み など）を作る
- **名前**: 中身を言う短い名詞句（「暗号と証明書」「2 軸で分ける」「財務諸表を読む」）。「その他」「基本」のような中身の分からない名前にしない
- **説明**: 1 行。このまとまりで何ができるようになるか、何を扱うか

### 3. 学ぶ順（まとまりの順と、まとまりの中の順）

まとまりの順も、まとまりの中の順も、次の 3 つで決める。

- **前提 → 応用**（他の論点の説明に出てくる土台を先に。例: 暗号化 → 公開鍵暗号方式 → ハイブリッド暗号方式 → デジタル署名 → デジタル証明書 → 認証局）
- **全体 → 個別**（総称を先に、個別の手口や種類を後に。例: マルウェア → マクロウイルス）。総称が個別の語を使わずに説明できるときだけ使う
- **身近 → 抽象**（日常で見る物から、仕組みや制度へ）

3 つとも、**語の先出しが無い**ように使う（後で習う語が先の論点の説明に出ないようにする）。

- ある論点の説明に要る語を論点名に持つ論点は、その論点より前に置く
- 他の論点の語を束ねて説明する論点は、束ねられる論点の後に置く（例: DBMS はトランザクション・排他制御・回復の後、BSC は KGI・KPI の後、SWOT は 3C・PEST の後）。個別の語を使わないと説明できない総称も、この形で個別の後に置く

出題回数は順に使わない。上の 3 つで決まらないときだけ、出題の多い方を先にする。

例（IP の企業活動の会計・財務）: 損益計算書 → 粗利益 → 営業利益 → 利益・原価 → 損益分岐点 → 貸借対照表 → 自己資本比率 → ROE。

### 4. 受け持ち（`owners`）

- 複数の論点の今の教材が同じ説明をしているとき（`unit_inputs` の `explanation`・`detail` を読んで見つける）、または学ぶ順で並べたときに同じ説明が要る論点が続くとき、その説明を `owners` に 1 件書く
- **受け持ちに書くのは、複数の論点が同じ説明を要る共通の前提の説明だけ。** 比較・使い分け（2 つの論点の違いも、3 つ以上の論点にまたがる違いも）は書かない。比べる 2 つは学ぶ順で後の論点が、3 つ以上を並べる比較は並べる物のうち学ぶ順で最後の論点が持つ（`scripts/prompts/write_materials.md` の「他の論点との分担」）
- **受け持つのは、その説明に触れる論点のうち学ぶ順で最初に出る 1 本**。他の論点は、書き直しで受け持ちの論点を `[[用語]]` で指し、1 文以内で触れるだけになる
- 例: 「利益の 5 段階」は損益計算書が受け持ち、粗利益・営業利益は指すだけ。「認証局が公開鍵の持ち主を保証する」はデジタル証明書が受け持ち、認証局（CA）・PKI は指すだけ
- 単元をまたぐ重複・比較は受け持ちに書かない（`owners[].topics` はこの単元の論点だけ）。後の単元の論点が前の単元の論点を指して比較を持つ（`scripts/prompts/write_materials.md` の「他の論点との分担」）
- 受け持ちを変えたいなら、学ぶ順を先に変える（受け持ちは学ぶ順から決まる）

### 5. 前提（`prerequisites`）

- 論点ごとに「先に読むと良い論点」を **0〜2 本**。読まずに読むと説明の語が分からない論点だけを挙げる（関連するだけの論点は挙げない）
- 同じ対象の論点なら、他の単元の論点でもよい（例: セキュリティの論点が、ネットワークの単元の論点を前提にする）
- 前提が無い論点はキーを書かない
- **門が止める決まり**: 前提は実在する論点 ID で、自分自身でない。2 本まで。前提が同じ単元の論点なら、学ぶ順でその論点より前にある。前提をたどって元の論点に戻る（循環する）並びは書かない（単元をまたいでも同じ）

---

## やらないこと

- 論点の名前（`term`）・論点 ID・小項目の割り当てを変えない（論点の単元は分類の小項目から決まるので、単元の構成では変えない）。分類が合わないと思ったら報告に書く
- 教材を書かない・直さない。受け持ちの説明の中身も書かない（書くのは教材の書き直しの担当）
- 他の単元の `unit_plans/` のファイルを書かない
- 出題回数で並べない

## 回を追加して論点が増えたら

新しい論点は、その単元の構成のどれかのまとまりに入れ直す（入っていない論点があると門が止める）。まとまりが 8 を超えるなら分ける。

---

## 書き上げたら

```bash
python3 scripts/check_unit_plans.py --data data/<対象>
```

対象のすべての単元の構成を見る（自分の単元に関する指摘だけ直せばよい。他の単元は並行して書かれている）。
止める理由（論点の過不足・まとまりの大きさの上限・受け持ち・前提・欠けた欄）が 0 になるまで直す。
まとまりが 3 論点を下回るときは警告だけ出る（止まらない）。単元の構成が無い単元は、止めも警告もしない。

## 報告（親へ）

- まとまりの名前と論点の数、学ぶ順を決めた理由を 1 行ずつ
- 受け持ちに書いた説明と、見つけた根拠（どの論点の今の教材が同じ説明をしていたか）
- 分類が合わないと思った論点（直していない）
- 門の結果（自分の単元に関する止める理由と警告の数）
