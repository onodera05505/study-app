# 教材に添える図の仕様

図は**自分で SVG を書かない**。仕様 JSON を書くと `scripts/render_material_figures.py` が
決まった様式で描く。担当ごとに見た目がばらつかず、直すときは JSON を直して描き直せる。

---

## 置き場所と形

1論点1ファイル。`data/<試験>/material_figures/<topic_id>.json`（例 `data/ip/material_figures/1.json`）

```json
{
  "topic_id": 53,
  "term": "論理関数",
  "figures": [ { "id": 1, "type": "blocks", "caption": "…", "after": "explanation", "…": "…" } ]
}
```

| キー | 意味 |
| --- | --- |
| `topic_id` | 論点 ID（`data/<試験>/topic_ids.json` の値。並び順から採らない） |
| `term` | その論点の用語。教材の `term` と同じ文字列にする |
| `figures[].id` | 1 始まりの整数（1 以上 10000 以下。整数でない値と範囲外の値はエラー）。ファイル内での重複はエラー |
| `figures[].type` | `blocks` / `sequence` / `matrix` / `chart` / `steps` / `cycle` / `layers` / `parts` / `timeline` / `venn` の 10 だけ |
| `figures[].caption` | 図の説明文。画面が図の下に文字として出す。**敬体（です・ます）**で、図が何を表し、どこをどう読むかを書く。図の中身の読み上げ・本文の繰り返しは書かない。図の要点（論点の芯）は言ってよく、計算の答えの値と、問いへの答えの形の文は書かない（「過去問の答えを言わない・写さない」の caption の線）。角かっこ（`A[1]` など）を含んでよい（教材の代替文に入っても 1 つの図の行として読まれる）。**`](` の並び・`]]` の並び・改行は書かない**（教材の代替文に入ると図の行として読まれず文字のまま出るか、描画の検査に当たる。入れ子の添字 `A[B[1]]` は「添字 B[1] の A の要素」のように言い換える）（図の下で一目で読める 1〜2 文・60 字前後が目安。読み方に要る語を削る理由にしない）（`--check` が全文の文末と禁止語を見る）。必須で、空か無い図は `render_material_figures.py` が描かずに止め、その図を示す。教材の `![…]` の代替文に入り、画面がそこから図に結び付けた文字として、見た目でも読み上げでも 1 回だけ示す。SVG には持たせない（見える文字にも `<title>` にも入れない） |
| `figures[].after` | 差し込み位置。`"explanation"`＝短い説明の末尾、それ以外は `detail` に**実在する**見出しを `"### しくみ"` の形で書き、図はその見出しの節の末尾（次の見出しの行の直前。後に見出しが無ければ `detail` の末尾）に入る。同じ差し込み位置の図は、`figures` に並ぶ順に上から入る。必須。資格対策の教材では、`"explanation"` に置くのは要点そのものを表す 1 枚だけで、他はその図が支えるブロックの見出しに置く（`scripts/prompts/write_materials.md` の「図の置き場」。IT パスポートも同じ）。`attach_material_figures.py` がこの位置に図を入れるのは書き直した世代から選んだ論点で、前の世代から選んだ論点では本文の図の置き方を変えない。書き直した世代から選んだ論点で、見出しが教材に無い図が 1 つでもあると、`attach_material_figures.py` は教材のファイルを 1 つも書き換えず、その論点と図と理由を問題として示して失敗で終える。書く前に `render_material_figures.py --check` が実在を見る |

`figures[]` の `id`・`type`・`caption`・`after` は必須で、無いとエラー。各型の節が「必須」と書く欄も同じで、無いとエラー。
`nodes`・`edges`・`actors`・`steps`・`stages`・`layers`・`parts`・`events`・`sets`・`regions`・`series` は配列で書き、配列でない値はエラー。
欄の値の型（辞書・配列・文字列・数）が各型の節の書き方と違うときはエラーで、道具は例外で落ちずにその図と理由を示す。
この仕様書の「数」「整数」は有限の数で、無限大や NaN（JSON の `1e400` はこれに読まれる）と、浮動小数点で表せない大きさの整数（10 の 400 乗など）は型が違うエラー。
整数の欄（`figures[].id`、`blocks` の `nodes[]` の `row`／`col`、`layers` の `brackets[]` の `from`／`to`、`matrix` の `emphasis` の行・列）は
0 以上 10000 以下（`figures[].id` は 1 以上 10000 以下）で、範囲外はエラー。
ファイルが JSON として読めない・入れ子が深すぎるとき、ファイルの中身が辞書でない・`topic_id` が整数でない・`term` が文字列でない・`figures` が配列でないときもエラーで、道具はそのファイルと理由を示す。

出力は `public/figures/materials/<試験>/<topic_id>-<id>.svg`。

## 書くときの決まり

- **図は解説の代わりではなく、図があると理解しやすい要点だけに付ける**（構成・手順・
  2軸の分類・数値の動きなど。判断は次の節「図を付ける判断と、図だけで分かること」）。表や擬似言語は文章のままにする
- **ロードマップ型の学びで図を付けた単位は、図が示す構成・手順・対比を本文の文で繰り返さない。** 本文には、図を読む前の 1〜2 文の導入と、図に描けないこと（理由・例外・使いどころ）だけを残し、図に移った文は削る。削った後も本文だけで単位の要点が一言で言えること
- ラベルは短く。**自動で折り返さない**ので、長いときは `\n` を自分で入れる
- **caption にも図の中身にも、紐づく過去問の答え合わせの印・選択肢と問題文の言い回し・本文が説明していない誤答の否定・場面・値・図や表を書かない・写さない。** 論点の芯（定義・しくみ・境界・手順）が紐づく過去問の答えと重なるのはよい。線の引き方は次の節「過去問の答えを言わない・写さない」
- 記法: `^`・上付き数字（²）・IPA の句読点（，．）を書かない（「2 の n 乗」「、」「。」）。caption の 2 文目は「〜してください」で閉じない（敬体の門に当たる）
- **caption は SVG の中に持たせない**（見える文字にも `<title>` にも入れない。説明文は画面の文字として 1 回だけ出る）。caption を変えたら教材の代替文を合わせ直し、正本（この JSON）と教材の代替文の 2 者が一致していることを見る
- **caption は、学ぶ順（`scripts/prompts/unit_plan.md` の単元の構成）でまだ出ていない例・図を指さない**（×「同じ例で」「先の図の」が、後の論点の例や図を指す）
- 強調（`emphasis`）は**1図に1つか2つ**（目安。門は見ない）。全部強調すると強調にならない。強調してよい所は次の節の「強調」
- **caption が強調を指すなら、指す所と `emphasis` の位置を一致させる。** 「強調した X」と書いたら X の項目・セル・系列に `emphasis` があり、`emphasis` の無い図で「強調した」と書かない（×caption は「両方が新しいものが多角化です」、強調は市場浸透のセル）
- **図の中の語は、図を置く論点の学ぶ順の位置で読める語だけにする。** 学ぶ順で後の論点の語（論点名）を、比較の相手としても前の論点の図に入れない（比べる 2 つは学ぶ順で後の論点が持つ。`scripts/prompts/write_materials.md` の「他の論点との分担」）。`after` を変えて（`explanation` へ移すなどして）この決まりを避けない。後の語が要る図は、後の論点の図にする
- **同じ語は、どの図でも同じ意味で描く。** 意味は、その語を論点名に持つ論点の定義の文（教材の `explanation` の 1 文目）に合わせる。試験の範囲で 1 つの語が 2 つの意味を持つとき（監査役の業務監査と、内部監査の業務監査）は、図の中で書き分ける（「監査役の業務監査」）
- 図の中身を後から直す段（中身・caption の直し、論点の間の移し替え、外した図を戻す）は `scripts/prompts/rewrite_figures_review.md`。書き直しの段（`rewrite_materials_by_group.md`）と単元の突き合わせの段（`rewrite_unit_crosscheck.md`）は図の中身を変えない

## 過去問の答えを言わない・写さない

この節の線は 2 つの目的から引く。図は概念を表し、特定の過去問の答え合わせをしない（答え合わせは問題解説がする）ことと、過去問を引き写さないこと。論点は紐づく過去問が問う中身で括ってあるので、図が論点の芯（定義・しくみ・境界・手順）を表せば、紐づく過去問の答えと重なるのは教材の役目のとおり（`scripts/prompts/write_materials.md` の「満たすべき最低条件」）で、答え合わせではない。**紐づく過去問**（その論点に分類された過去問。書き直しの束の `questions` の問題文・選択肢・正解）に対して、caption と図の中身（ラベル・セル・注記 `note`・値・強調）は次を守る。
見出しは問わない（`### 計算の解き方` の図も、`explanation` の図も同じ）。判定は、紐づく過去問の現物（問題文・選択肢・正解）と並べて行う（「この種の問題はふつう…」の一般論で決めない）。

**判定の問いは 1 つ:「紐づく過去問の現物（その問題の言い回し・その問題が作った項目・値・選択肢の顔ぶれ）を見ていなければ、この書き方にならないか」。** 現物を見ていなくても論点の芯を教材の言葉で表せばこの書き方になるなら、概念の説明で、書いてよい。現物を見たからこの書き方になったのなら、答え合わせか写しで、書かない。下の線は、この問いを書き方の種類ごとに言った物で、迷ったらこの問いに戻る。

- **答え合わせの印を書かない。** 選択肢の記号や語の並び、回と問番号、正誤の印、問いへの答えの形で言う文を書かない
  （×「機能4だけ」「（正）（誤）」「シナリオ d の累積」「令和7年度秋期 問77」。○ 論点の定義の文「データディクショナリには、データの名前・意味・形式の定義が入ります」は、紐づく過去問がそれを問うていても書いてよい）
- **言い回しの線**: caption・ラベル・セル・注記に、選択肢の句・問題文の句をほぼそのままの言い回しで置かない。論点の定義・しくみ・境界を教材の言葉で言うのは、紐づく過去問がそれを問うていてもよい。規格・法令・シラバスが定める語は、選択肢と重なっても使ってよい
  （× 選択肢の句「利用者が操作した記録を一定期間保管する」を、句のまま対策のセルに置く。○ 境界を教材の言葉で「UX は人の感じ方、ユーザビリティは製品の能力」と置く）
- **誤答の否定の線**: その論点の今の本文が境界・対比として説明していない事柄を、選択肢を打ち消すために図へ足さない（選択肢の記述を打ち消す注記。「〜は防げない」「〜どまり」「〜は守られない」）。本文が説明している境界（近い概念との違い）を図が表すのはよい（下の「本文の決まりは図にも当たる」と同じ向き）
  （× 本文がシングルサインオンとの違いを説明していない論点の図に「シングルサインオンは試行を止めない」を足す。○ 本文が UX とユーザビリティの違いを説明している論点の図が、2 つを並べて違いを表す）
- **caption の線**: caption は図の読み方を言い、図の要点（論点の芯）を言ってよい。計算の答えの値と、問いへの答えの形の文（問題文の句をなぞって答えを言う文）は書かない
  （×「5 通りになります」「帯域幅などの通信品質を約束できるのは IP-VPN です」。○「横に並ぶ 2 列を比べると、UX は人の感じ方、ユーザビリティは製品の能力だと読めます」）
- **値の線**: 紐づく過去問が与える値と答えの値を、同じ役（同じ登場物の同じ量）で図に使わない。同じ役の一致が 2 つ以上あれば写し、答えの値は 1 つでも写し。同じ役の一致が 1 つだけで答えの値でない物、論点の定義で決まる値（2 の累乗・規格の値）、単位の換算、目盛、番号は写しに数えない
  （例: 過去問が固定費 300 万円・変動費率 0.4 を与えて損益分岐点の売上高を問うとき、○ 図が固定費 300 万円だけを同じ役で使い、変動費率を別の値にして答えも違えば写しでない。× 変動費率 0.4 も同じ役で使えば写し）
- **登場物と題材の線**: 問題文の場面（題材と登場する物の組。レストランの受付、水田の水位と水門）を図の例にしない。過去問の登場物に付けた名前・記号（作業 a〜c、製品 X、機械の名前、人・組織）と題材（業種・業務・品物）の組を、過去問と同じ組で使わない。計算の型そのものを言う一般の語（作業・機械・先行と後続・固定費 など）は登場物に数えない。選択肢の事例と語も図の例にせず、同じ種類の別の事例にする
  （× 過去問が「製品 X を作る工場」の場面のとき、図も製品 X と工場の組で描く。○ 一般の語「作業」「先行と後続」で、別の題材の例にする）
- **骨組みの線**: 過去問 1 件を解いてみせるのは本文の `### 計算の解き方`（`scripts/prompts/write_materials.md`）で、計算の手順の図は同じ手順を別の例でたどる。計算の手順の図は、過去問と同じ計算の型の骨組み（登場物の数・前後関係の形・表の行と列の数）で描いてよい。条件は、値の線と登場物と題材の線を守り、図の例の答えが紐づく過去問の答えと違うこと
  （○ 過去問と同じく作業 4 つ・合流 1 つの形で、別の所要日数と別の題材にし、最短の日数が過去問と違う。× 骨組みも値も変えたが、最短の日数が過去問の答えと同じになる）
  - 図の中の計算は、本文と紐づく過去問が置く前提（各作業者は 1 日 8 時間働く・各処理は開始時に 1 回だけ読み込む、など）と食い違わない
    （× 本文と過去問が「各処理は開始時に 1 回だけ読み込む」と置くのに、図が処理の途中の読み込みを数える。○ 図の計算も開始時の 1 回だけを数える）
- **図表の線**: 過去問の図・表（木・網・流れ図・利得表・領域図・比較表）を、同じ構成と値で描き直さない（引用にもなる）。図の中に問題文や選択肢を書き写さない
  （× 過去問の利得表を同じ行・列・値で描く。○ 同じ種類の表を、別の題材と値で描く）
- **振り分けの線**: 問題が選ばせる組合せ・振り分け・正誤（「a〜c に合う物の組」「〜だけを全て挙げよ」「〜に該当するものはどれか」）を、図のセルや項目が埋める形にしない。その過去問が作った項目・事例（問題の a〜d の記述、選択肢の事例）を、言い換えても、過去問が振り分けさせる先（段・区分）に置かない。論点の定義が並べる物（段階とその役割、区分とその定義）を教材の言葉で置くのと、定義の言い方・別の事例を置くのはよい
  （× 過去問が a〜c の記述を 3 つの段へ振り分けさせるとき、a〜c を言い換えて段に 1 つずつ置く。○ 3 つの段の名前と、段ごとの役割を定義の言い方で置く）
  - 論点と近い概念を観点で比べる表は、比べる物の顔ぶれが選択肢と重なってよい。ただしセルの言い回しを選択肢の句にしない
  - 例の欄・例の項目には、選択肢の事例を入れない（著作物の例・対策の例・記憶媒体の例・指標の例のように置き換えのきく例は、同じ種類の別の事例にする）
  - 置き換えのきかない物（分類の代表の名前そのもの。揮発性の DRAM・SRAM、記憶の階層）と、定義そのものが並べる物は描いてよい。それに問題に合わせた注記を足さない
- **強調の線**: `emphasis` は論点の芯（論点自身の行・列・項目か、図の要点の芯）に置いてよく、それが紐づく過去問の答えと重なってもよい。論点の芯でなく、過去問の問いの条件・答えに当たるだけのセル・項目は強調しない
  （× 論点の芯でない「コンバージョン率が低くリテンション率が高い」のセルだけを、問いの条件だから強調する。○ 論点自身の行を強調する）
- **本文の決まりは図にも当たる。** `write_materials.md` の「計算の解き方は過去問 1 件まで」「全選択肢の値を出さない」「誤答のケアは問題解説」（教材と問題解説の役割分担・書き方の約束）は、caption と図の中身にも当たる。本文からこの決まりで外した値・例題・誤答のケアを、図に移して残さない

## 図を付ける判断と、図だけで分かること（判断基準）

図を付けるかは「**図があると理解しやすいか**」で決める（図がまだ無いから付ける、ではない）。
付けた図は、caption も本文も読まずに図だけを見て分かる質にする。

### 図を付けるか — 中身の型と図の働き

単位の要点を 1 つずつ取り出し、要点ごとに**中身の型**を決め、型に合う**図の働き**を当て、働きに合う図の型を選ぶ
（Clark & Lyons の「中身の型 × 図の働き」の枠組み）。

| 中身の型 | 要点の例 | 図の働き | 合う図の型 |
| --- | --- | --- | --- |
| 事実（名前や値） | 部品の名前と場所、明細の項目 | 表現的（見た目や在りかを写す） | `parts`（部位を絵の上で指す）。名前や値が 1 つなら図にしない |
| 概念（分類や比べる） | 記憶装置 3 種の違い、権限の範囲 | 組織的（関係を並べて見せる） | `matrix`（観点で比べる）・`venn`（重なり・入れ子）・`layers`（積み上げ） |
| 手順（人がやる順） | 申請から承認まで、施術の順 | 変換的（段階を見せる） | `sequence`（相手とのやり取りがある）・`steps`（段が順に進む） |
| プロセス（仕組みの動き） | 通信の流れ、PDCA、開発工程 | 変換的（動きを見せる） | `blocks`（経路・状態遷移）・`sequence`・`cycle`（輪で回る）・`steps`・`timeline`（時間に沿う） |
| 原理（量の関係や因果） | 損益分岐、需要と価格、悪循環 | 関係的（量の関係）／解釈的（因果や理論） | `chart`（関係的）・`blocks`／`cycle`（解釈的。矢印のラベルで因果を運ぶ） |

- **飾りの図は付けない。** 要点を運ばない絵、雰囲気のための図、見出しを絵にしただけの図は描かない。
  手描きの挿絵も使わない（絵は「絵の語彙」の絵記号だけ）
- **本文だけで一言で言える要点は図にしない**（名前 1 つ・値 1 つ・2 者の 1 点だけの違い）
- **要点の数だけ図を付けてよい。** 1 単位の図の数に上限は無い。どの図も要点は 1 つ

### 図の作り — 言葉と絵を組ませる（Mayer の多媒体学習の原則）

- **区切り: 1 図に要点は 1 つ。** 要点が 2 つあるなら図を分ける
- **近接: 説明文は図のすぐそば。** caption は図の真下に出る。`after` は、その要点を述べている段落の位置にする（全部の図を `explanation` の末尾に積まない）
- **強調は 1〜2 か所**（`emphasis`。目安。門は見ない）。読み手の目を要点の芯へ向ける所だけに
- **余計な物を入れない。** 要点に関係の無い箱・項目・絵記号・装飾を足さない

### 閉じた図のテスト

- **閉じた図のテスト**: caption と本文を伏せ、図だけを見た読み手が、その単位の要点
  （ロードマップ型は `roadmap.json` の `summary`、資格型は教材の定義文の芯）を 1 文で言えること。
  言えない図は描き直す。確かめるのは図を書いた担当ではなく、図だけを渡された別の担当。
  渡すのは描いた画像（`--png-dir` の PNG。画面が出す図と同じ見え方）で、JSON の文字ではない（強調・向き・並びは画像でしか見えない）。
  1 単位に図が複数あるときは、図ごとに、その図が受け持つ要点を 1 文で言えること

### 同じ内容の図の判定

2 枚の図が同じ内容かは、**図が運ぶ要点**で決める。型・項目の顔ぶれ・見た目が似ているかでは決めない。
外す・寄せる段（`rewrite_materials_by_group.md` の同じ内容の図を外す直し、`rewrite_unit_crosscheck.md` の図の重複の報告、`rewrite_figures_review.md`）は、どれもこの判定を使う。

- **判定**: 残す側の図だけを見て（caption も本文も伏せ、描いた画像で）、外す側の図が受け持つ要点（閉じた図のテストの 1 文）を言えるなら、同じ内容。言えないなら同じ内容ではない
- 外す側の図にしか無い物が、その要点の 1 文に入るなら（段・領域・値・空欄の意味・系譜の 1 段）、同じ内容ではない（×「空欄＝動作が未定義」の図と「空欄＝変化なし」の図。×片方にしか無い段を要点に持つ系譜の図）
- 残す側が外す側より多くを運ぶのはよい。型が違っても要点が同じなら同じ内容で、型と顔ぶれが同じでも要点が違えば別の図
- 判定は単元の中の論点どうしに当てる。束の境目では切らない（同じ束の中の論点どうしも、束をまたぐ論点どうしも同じ判定）。どちらを残すかは `write_materials.md` の「図の置き場」（受け持ち・比較を持つ論点・学ぶ順で最初にその内容が要る論点）
- 同じ内容ではないと判定した 2 枚が要点の一部を重ねて持つときは、どちらも外さない。重なりを 1 か所にする直しは、図の中身を直せる段（`rewrite_figures_review.md`）で行う

### 型の選び方

- **型は、図に運ばせたいことで選ぶ**

  | 図に運ばせたいこと | 型 |
  | --- | --- |
  | 2 つ以上を同じ観点で比べる | `matrix` |
  | 手順・やり取り（順番に意味があり、相手との往き来がある） | `sequence` |
  | 量の変化・大小 | `chart` |
  | 構成・経路・状態遷移で、矢印が「何が・どう動くか」を運ぶ | `blocks` |
  | 段が一方向に進む（工程の流れ・成熟度の段） | `steps` |
  | 段が輪になって戻る（改善の輪・景気の輪・悪循環） | `cycle` |
  | 積み上がり、下が上を支える（通信の層・システムの層・ピラミッド） | `layers` |
  | 1 つの物がどの部位でできているか（機械の中身・明細の構成） | `parts` |
  | 時間に沿った出来事と期間（ライフサイクル・年表・契約の期間） | `timeline` |
  | 範囲の重なりや入れ子（権限の範囲・集合の演算） | `venn` |

  箱に名前だけを入れて線でつないだ形（樹形図・一覧・分類の階層）は図にしない。
  本文の箇条書きにするか、比べる観点が立つなら `matrix` にする
- **`matrix` を手本にする。** 観点×対象の格子なので、読み手が行と列をたどって自分で比べられ、
  違いが図の中で閉じる。手本は eng の論点 4（ストレージ）の図 1：メモリ・SSD・HDD を「速さ・電源を切ると・動く部分」の
  3 観点で並べ、「ストレージは遅い代わりに電源を切っても残る」が表だけで言える

### 箱と矢印・段の間が運ぶ中身

- **項目で組む型** ＝ `blocks`・`steps`・`cycle`・`layers`・`parts`・`timeline`・`venn` の 7 つ。項目（箱・段・層・部位・出来事・領域）を並べて組む型で、
  名前だけの項目の割合の決まりはこの 7 つすべてに、線の名前の決まりはそのうち線を持つ `blocks`（`edges`）・`steps` と `cycle`（`next_label`）に当たる。
  `sequence`・`matrix`・`chart` は項目で組む型でない
- **`blocks` の箱と矢印が運ぶ中身**
  - 箱の `label` は「名前＋一言（役割か、隣の箱との違い）」を `\n` で改行して 2 行以上にする。
    1 行だけ（名前だけ）の箱が全ノードの半分を超える図はエラー
  - 線には必ず `label`（何が流れるか／何が起きるか／どの条件で移るか）を付ける。
    `label` の無い線（空の文字列や空白だけの `label` も同じ）は、`arrow: "none"` の線と自己ループも含めてエラー
  - 構成だけを示す図（部品の並び）も `blocks` でよい。そのときも各箱の一言が他の箱との違いを運んでいること
  - ノードが 3 個以下で線が 2 本以下の `blocks` は警告（本文の 1 文で足りる疑い）。描くのは止めないが、
    閉じた図のテストに通るか、図にする理由があるかを見直す
- **`steps`・`cycle`・`layers`・`parts`・`timeline`・`venn` の項目も同じ**
  - 項目（段・層・部位・出来事・領域）の `label` は「名前＋一言」を `\n` で 2 行以上にする。
    1 行だけ（名前だけ）の項目が全項目の半分を超える図はエラー
  - 段の間の矢印（`steps` と `cycle` の `next_label`）は、何を渡すか／何が起きるかを書く。無い・空・空白だけはエラー
  - 項目の数は型ごとの下限と上限の内に収める（外れればエラー。各型の節に書く）

## 1. `blocks` — 箱と矢印

構成図・ブロック図・経路・状態遷移に使う（使いどころと中身の決まりは「図を付ける判断と、図だけで分かること」）。

```json
{
  "id": 1, "type": "blocks", "after": "explanation",
  "caption": "業務処理をアプリケーションサーバに集めるので、クライアントは画面だけを持てばよくなります。",
  "nodes": [
    {"id": "cl1", "label": "クライアント A\n画面の表示と入力", "row": 0, "col": 0},
    {"id": "cl2", "label": "クライアント B\n画面の表示と入力", "row": 1, "col": 0},
    {"id": "ap", "label": "アプリサーバ\n業務処理を一手に", "row": 0, "col": 1, "emphasis": true},
    {"id": "db", "label": "DB サーバ\nデータを一元管理", "row": 0, "col": 2, "shape": "cylinder"}
  ],
  "edges": [
    {"from": "cl1", "to": "ap", "label": "入力と処理結果", "arrow": "both"},
    {"from": "cl2", "to": "ap", "label": "入力と処理結果", "arrow": "both"},
    {"from": "ap", "to": "db", "label": "SQL と検索結果", "arrow": "both"}
  ]
}
```

- `nodes` は必須、`edges` は任意（無いのは線 0 本と同じ）
- `nodes[]` — `id`（図の中で一意。重複はエラー）、`label`、`row` / `col`（**0 始まりの格子位置**。0 以上の整数で、負の値はエラー。4 つとも必須。
  同じ `row` は横一列）。任意で `emphasis`（true で強調色）、
  `shape`（`box` 既定 / `round` / `cylinder`＝データストア / `cloud`＝ネットワーク。それ以外の語はエラー）、
  `icon`（「絵の語彙」の名前。箱の中、文字の左に出る）
- `edges[]` — `from` / `to`（`nodes` の `id`。どちらも必須。`nodes` に無い `id` を指すとエラー）と `label`（必須）。任意で
  `style`（`solid` 既定 / `dashed`）、`arrow`（`to` 既定 / `both` / `none`）。どちらもそれ以外の語はエラー
- `from` と `to` が同じなら自分への矢印（状態遷移の自己ループ）になる
- 格子は詰めて使う。列は 3〜4、行は 3 くらいまでが読みやすい（目安。門は見ない）

## 2. `sequence` — 手順・やり取り

プロトコルのハンドシェイク、処理の流れに使う。

```json
{
  "id": 1, "type": "sequence", "after": "### ハンドシェイクの流れ",
  "caption": "公開鍵暗号は共通鍵を渡すためだけに使い、本文の暗号化は共通鍵で行います。",
  "actors": [{"id": "c", "label": "クライアント"}, {"id": "s", "label": "サーバ"}],
  "steps": [
    {"from": "c", "to": "s", "label": "ClientHello（使える暗号方式を提示）"},
    {"from": "s", "to": "c", "label": "ServerHello ＋ サーバ証明書", "note": "証明書の正当性を認証局の公開鍵で確認する"},
    {"from": "c", "to": "s", "label": "共通鍵の素をサーバの公開鍵で暗号化して送付"},
    {"from": "s", "to": "c", "label": "Finished（以降は共通鍵で暗号化）"}
  ]
}
```

- `actors` と `steps` は必須
- `actors[]` — `id`（図の中で一意。重複はエラー）と `label`。どちらも必須。**左から書いた順**に並ぶ。2〜4 人で、外れるとエラー。任意で `icon`（「絵の語彙」の名前。登場人物の名前の上に出る）
- `steps[]` — `from` / `to` / `label`。3 つとも必須。`from` / `to` は `actors` の `id` で、`actors` に無い `id` を指すとエラー。上から書いた順に **1. 2. 3.** と番号が付く
- `from` と `to` が同じなら自分への処理（短い折り返し矢印）
- `note` は任意。矢印の下に小さく出る。**そこを外すとどうなるか**のような一言に使う
- 手順は 4〜6 個まで（目安。門は見ない）。それ以上は図で見る意味が薄れる（図に入らない手順も要るなら、図を分けるか本文に残す。図に合わせて手順を落とさない）

## 3. `matrix` — 2軸の分類・対比

```json
{
  "id": 1, "type": "matrix", "after": "### 4つの戦略の中身",
  "caption": "既存か新規かの2軸で成長戦略を4つに分けます。右下ほどリスクが大きくなります。",
  "x": {"label": "製品", "values": ["既存製品", "新製品"]},
  "y": {"label": "市場", "values": ["既存市場", "新市場"]},
  "cells": [
    ["市場浸透\n既存市場で\nシェアを上げる", "新製品開発\n既存の顧客に\n新製品を売る"],
    ["市場開拓\n既存製品を\n新しい市場へ", "多角化\n新製品を\n新市場へ"]
  ],
  "emphasis": [[1, 1]]
}
```

- 大きさは **行も列も 2〜3**（2×2・2×3・3×2・3×3）。行か列の数が 2〜3 の外ならエラー
- `x`・`y`（どちらも `label` と `values`）と `cells` は必須
- `cells` は **y の行ごと・x の列順**。`cells[r][c]` は `y.values[r]` × `x.values[c]`。
  `cells` の行数が `y.values` の個数と違う、またはどれかの行の列数が `x.values` の個数と違うとエラー
- 各セルは「名前 ＋ 一言」を `\n` で改行して書く。3 行まで（目安。門は見ない）
- `emphasis` は任意。`[[行, 列], …]`（0 始まり）。`cells` の外（行が `y.values` の個数以上、列が `x.values` の個数以上、負の数）を指すとエラー

## 4. `chart` — 数値のグラフ

```json
{
  "id": 1, "type": "chart", "after": "explanation",
  "caption": "売上高の線と総費用の線が交わる点が損益分岐点です。ここを超えた分だけ利益が出ます。",
  "kind": "line",
  "x": {"label": "売上高（万円）", "values": [0, 200, 400, 600, 800, 1000]},
  "y": {"label": "金額（万円）", "min": 0},
  "series": [
    {"label": "売上高", "values": [0, 200, 400, 600, 800, 1000]},
    {"label": "総費用（固定費 300 ＋ 変動費率 0.5）", "values": [300, 400, 500, 600, 700, 800]}
  ],
  "vlines": [{"x": 600, "label": "損益分岐点"}],
  "annotations": [{"x": 600, "y": 600, "text": "600 万円"}]
}
```

- `kind` — 必須。`line` / `bar` / `step`。それ以外の語と欄が無いのはエラー
- `x`（`label` と `values`）・`y`・`series` は必須
- `x.values` — 数値（等間隔でなくてよい）またはカテゴリ名の文字列。`bar` は普通カテゴリ。2 個以上で、2 個未満はエラー
- `series[]` — **1〜3 本**。0 本と 4 本以上はエラー。`label` と `values` は必須。`values` は `x.values` と同じ個数・すべて有限の数で、
  個数が違う・数値でない物があるのはエラー。
  任意で `emphasis`（true の系列だけ強調色になり、他は無彩色になる）
- `y` — `label` は必須で、無い・空・空白だけはエラー。`min` / `max` は任意（省略するとデータから決める）で、書くなら有限の数（そうでなければ型が違うエラー）
- `vlines[]`（縦の補助線。損益分岐点など）と `annotations[]`（点への短い注記）は任意。書くなら `vlines[]` は `x` が必須、`annotations[]` は `x`・`y`・`text` が必須で、`annotations[]` の `y` は有限の数（そうでなければ型が違うエラー）。
  `x` は、数値軸では `x.values` の最小〜最大の範囲内の数（範囲外はエラー）、カテゴリ軸では `x.values` のどれか（無い値はエラー）

## 5〜10 の型に共通の項目の決まり

`steps`・`cycle`・`layers`・`parts`・`timeline`・`venn` の項目（段・層・部位・出来事・領域）は、どれも次の鍵を持つ。

- `label` — 必須。「名前＋一言」を `\n` で改行して 2〜3 行。1 行だけ（名前だけ）の項目が全項目の半分を超えるとエラー、4 行以上もエラー
- `emphasis` — 任意。`true` の項目だけ強調色になる。1 図に 1〜2 項目（目安。門は見ない）
- `icon` — 任意。「絵の語彙」の名前。置けるのは `steps`・`cycle`・`layers`・`parts` の項目と `parts` の `whole` だけ
  （`timeline` の出来事と `venn` の領域・集合には置けない）
- 項目は書いた順に並ぶ（並び方は各型の節）。項目に `id` は持たせない（`venn` の集合だけ `id` を持つ）

## 5. `steps` — 段階図

段が一方向に進む流れ（ウォーターフォールの工程、成熟度の段）に使う。段は階段状に並び、段の間に矢印が入る。

```json
{
  "id": 1, "type": "steps", "after": "explanation",
  "caption": "工程は上から順に一方向へ進み、前の工程の成果物が次の工程の入力になります。後から前の工程へ戻りにくいのはこのためです。",
  "direction": "down",
  "stages": [
    {"label": "要件定義\n何を作るかを決める", "icon": "person", "next_label": "要件定義書"},
    {"label": "設計\n作り方を決める", "icon": "document", "next_label": "設計書"},
    {"label": "実装\nプログラムを書く", "icon": "device", "next_label": "プログラム"},
    {"label": "テスト\n要件どおりか確かめる", "icon": "check", "next_label": "確かめた製品", "emphasis": true},
    {"label": "運用\n使いながら直す", "icon": "gear"}
  ]
}
```

- `direction` — 必須。`down`＝左上から右下へ下る階段（工程が流れ落ちる）／`up`＝左下から右上へ上る階段（段が上がるほど進んだ状態）
- `stages[]` — 段。必須。**3〜6**。書いた順に、`down` は左上から、`up` は左下から並ぶ
- `stages[].next_label` — その段から次の段への矢印のラベル（何を渡すか／何ができると次へ進むか）。
  **最後の段以外は必須**。最後の段に中身のある `next_label` を書くとエラー（矢印の先が無い）。
  最後の段の空・空白だけ・null の `next_label` は、無いのと同じに扱って描く
- 段に戻りの矢印は描かない。戻りが要点なら `cycle` か `blocks` にする

## 6. `cycle` — 循環

段が輪になって戻る流れ（PDCA、景気の輪、悪循環）に使う。

```json
{
  "id": 1, "type": "cycle", "after": "explanation",
  "caption": "評価で見つけた差を改善に回し、次の計画へ戻します。輪を一周するたびに仕事の質が上がります。",
  "center": "継続的改善",
  "stages": [
    {"label": "Plan 計画\n目標と手順を決める", "icon": "document", "next_label": "計画書"},
    {"label": "Do 実行\n計画どおりにやる", "icon": "person", "next_label": "実績の記録"},
    {"label": "Check 評価\n計画と実績を比べる", "icon": "search", "next_label": "見つかった差", "emphasis": true},
    {"label": "Act 改善\n差の原因を直す", "icon": "gear", "next_label": "直した手順"}
  ]
}
```

- `stages[]` — 段。必須。**3〜6**。最初の段を輪の真上に置き、書いた順に時計回りに並ぶ
- `stages[].next_label` — その段から次の段への矢印のラベル。**全部の段に必須**（最後の段の矢印は最初の段へ戻る）
- `center` — 任意。輪の中央に出す短い語（輪が何を回しているか）。`\n` で 2 行まで（目安。門は見ない）

## 7. `layers` — 層

積み上がり、下の層が上の層を支える構成（OSI や TCP/IP の層、システムの層、ピラミッド）に使う。

```json
{
  "id": 1, "type": "layers", "after": "explanation",
  "caption": "下の層ほど信号の伝送に近く、各層は直下の層の働きを使って上の層へ機能を渡します。経路の途中の機器は下の 3 層だけを扱います。",
  "shape": "stack",
  "layers": [
    {"label": "アプリケーション層\n用途ごとの約束を決める", "note": "HTTP・SMTP"},
    {"label": "トランスポート層\n端から端まで確実に届ける", "note": "TCP・UDP"},
    {"label": "ネットワーク層\n宛先までの経路を選ぶ", "note": "IP", "emphasis": true},
    {"label": "データリンク層\n隣の機器まで届ける", "note": "イーサネット"},
    {"label": "物理層\n信号を線や電波に流す", "note": "ケーブル・電波"}
  ],
  "brackets": [
    {"from": 0, "to": 1, "label": "端末の中で\n処理する"},
    {"from": 2, "to": 4, "label": "経路の機器も\n処理する"}
  ]
}
```

- `layers[]` — 層。必須。**2〜7**。**上の層から書く**（`layers[0]` が一番上）
- `layers[].note` — 任意。層の右に出す注記（その層の具体例など）。1 行（目安。門は見ない）
- `shape` — 任意。`stack` 既定（同じ幅の層を積む）／`pyramid`（上ほど狭い台形に積む。上ほど数が少ない・上位であることを形で運ぶ）
- `brackets[]` — 任意。層の左に出す括弧の注記。`from` / `to`（どちらも必須）は `layers` の位置（0 始まり、`from` ≤ `to`）、`label` は必須（無い・空・空白だけはエラー）で `\n` で 2 行まで（行数は目安。門は見ない）。
  括弧どうしは重ねない（範囲が重なるとエラー）

## 8. `parts` — 分解図

1 つの物がどの部位でできているか（CPU の中身、給与明細の構成）に使う。中央に物を 1 つ置いて部位に分け、
引き出し線で各部位の名前＋一言を示す。

```json
{
  "id": 1, "type": "parts", "after": "explanation",
  "caption": "CPU の中は、指示する部位・計算する部位・値を持つ部位に分かれます。強調した制御装置が他の部位を動かします。",
  "whole": {"label": "CPU", "icon": "gear"},
  "parts": [
    {"label": "制御装置\n命令を読み解いて指示する", "emphasis": true},
    {"label": "演算装置\n四則演算と比較をする"},
    {"label": "レジスタ\n計算中の値を一時に持つ"},
    {"label": "キャッシュメモリ\nよく使うデータを手元に置く"}
  ]
}
```

- `whole` — 必須。分解する物。`label`（必須で、無い・空・空白だけはエラー。物の名前。1 行が目安で、行数は門は見ない）と `icon`（任意）。物は 1 つの大きな箱として描き、
  `label` を箱の上端に、`icon` があればその左に出す
- `parts[]` — 部位。必須。**3〜8**。物の箱の中を部位の数だけの区画に分け、書いた順に左から右・上から下へ区画を割り当てる。
  区画には `label` の 1 行目（名前）だけを出し、`label` の全文は箱の外の注記に出して区画と引き出し線で結ぶ。
  注記は書いた順に、前半（部位の数の半分を切り上げた数）を左側の上から、残りを右側の上から並べる
- 部位の大きさの比は持たない（量の比が要点なら `chart` の `bar` にする）

## 9. `timeline` — 時間軸

時間に沿った出来事と期間（ライフサイクル、年表、契約の期間）に使う。横の軸に、点（ある時の出来事）と期間（いつからいつまで）の両方を並べられる。

```json
{
  "id": 1, "type": "timeline", "after": "explanation",
  "caption": "帯は製品が売れる時期の移り変わりで、時期ごとに打つ手が変わります。強調した成長期に投資を集めます。",
  "axis": {"label": "発売からの時間（例）", "ticks": ["発売", "1 年", "2 年", "3 年", "4 年", "5 年"]},
  "events": [
    {"from": 0, "to": 1, "label": "導入期\n知られておらず売上は小さい"},
    {"from": 1, "to": 2.5, "label": "成長期\n売上が急に伸びる", "emphasis": true},
    {"from": 2.5, "to": 4, "label": "成熟期\n売上が頭打ちで価格を競う"},
    {"from": 4, "to": 5, "label": "衰退期\n売上が落ち撤退を考える"},
    {"at": 1.5, "label": "競合の参入\n差別化が要りだす"}
  ]
}
```

- `axis` — 必須。`label`（軸の名前。必須で、無い・空・空白だけはエラー）と `ticks`（必須。目盛りの文字列。**2〜12**。左から等間隔に並ぶ）
- `events[]` — 出来事と期間。必須。**3〜8**。`at` を持つ物が**点**、`from` と `to` を持つ物が**期間**。どちらか一方だけを持つ
  （両方・どちらも無いはエラー）
- `at` / `from` / `to` は `ticks` の位置（0 始まり）の有限の数。小数でよい（`1.5` は 2 つ目と 3 つ目の目盛りの中間）。
  0 以上 `ticks` の個数 −1 以下で、期間は `from` < `to`
- 期間は軸の上に帯で描き、重なる期間は段を分ける。点は軸の上の印と、軸の下の注記で描く

## 10. `venn` — 包含・重なり

2〜3 の範囲の重なりや入れ子（権限の範囲、集合の演算）に使う。

```json
{
  "id": 1, "type": "venn", "after": "explanation",
  "caption": "2 つの部署の権限は一部が重なります。重なりの操作はどちらの部署の人もできます。",
  "layout": "overlap",
  "universe": "社内システムの全権限",
  "sets": [{"id": "a", "label": "経理部の権限"}, {"id": "b", "label": "人事部の権限"}],
  "regions": [
    {"in": ["a"], "label": "経理部だけ\n伝票を承認する"},
    {"in": ["b"], "label": "人事部だけ\n給与を改定する"},
    {"in": ["a", "b"], "label": "両方\n社員名簿を見る", "emphasis": true},
    {"in": [], "label": "どちらでもない\nシステムの設定"}
  ]
}
```

- `layout` — 必須。`overlap`＝円が互いに重なる／`nested`＝入れ子（`sets[0]` が一番外、次が内側）
- `sets[]` — 範囲。必須。**2〜3**。`id`（図の中で一意。重複はエラー）と `label`（どちらも必須。範囲の名前。1 行でよい。半分の判定には数えない）
- `universe` — 任意。全体を囲む枠の名前。書くと全部を囲む長方形とその名前が出る
- `regions[]` — 領域。必須。`in`（必須）は、その領域が属する範囲の `id` の組（**それ以外の範囲には属さない**領域を指す）。
  `in` は集合として比べ、書く順は問わない（`["a","b"]` と `["b","a"]` は同じ領域）。1 つの `in` に同じ `id` を 2 回書くとエラー。
  `label` は共通の決まりどおり「名前＋一言」
  - `overlap` は、空でない組み合わせ全部を 1 つずつ書く（2 範囲は 3 領域、3 範囲は 7 領域）。欠け・重複はエラー
  - `nested` は、外から順に数えた先頭の組（`sets` が a・b・c なら `{a}`・`{a, b}`・`{a, b, c}`）を全部 1 つずつ書く。欠け・重複・それ以外の組はエラー
  - `in: []`（どの範囲にも属さない領域）は `universe` があるときだけ書ける。書くなら 1 つ

## `--check` が見ること（型の中身の門）

`render_material_figures.py --check` は、caption・`after`・禁止語の門に加えて、型の中身を次のとおり判定する。
エラーは描かずに止め、警告は出すだけ。判定の文言は下のとおり（`{where}` は論点 ID と図 ID で、`[<ファイル名>] 論点 <論点 ID> 図 <図 ID>` の形）。

| 型 | 判定 | 区分 | 文言 |
| --- | --- | --- | --- |
| すべて | `type` が 10 の型のどれでもない | エラー | `{where}: 未知の type '…'（blocks/sequence/matrix/chart/steps/cycle/layers/parts/timeline/venn のいずれか）` |
| `blocks` | 線に `label` が無い・空・空白だけ | エラー | `{where}: edges[i]（from→to）に label が無い（線には何が流れるか／何が起きるか／どの条件で移るかを書く）` |
| `blocks` | 1 行だけの箱が半分を超える | エラー | `{where}: 1 行だけ（名前だけ）の箱が n/m 個で半分を超える（箱は「名前＋一言」を \n で 2 行以上に）` |
| すべて | `after` が `"explanation"` でも、配る本文と同じ選び方で選んだ世代の教材の `detail` に実在する見出しでもない | エラー | `{where}: after '…' が教材に無い` |
| すべて | 同じファイルの `figures[].id` が重複する | エラー | `{where}: figures の id n が重複する（id はファイル内で一意）` |
| ファイル | JSON として読めない・入れ子が深すぎる | エラー | `<ファイル>: JSON が読めません（<理由>）` |
| ファイル | ファイルの中身が辞書でない・`topic_id` が整数でない・`term` が文字列でない・`figures` が配列でない | エラー | `<ファイル>: <欄> の型が違う（<期待する型>）` |
| すべて | `figures[].id` が整数でない（小数・文字列・無限大・NaN など） | エラー | `{where}: figures の id '…' は 1 始まりの整数` |
| すべて | 整数の欄（`figures[].id`・`nodes[]` の `row`／`col`・`brackets[]` の `from`／`to`・`matrix` の `emphasis` の行・列）の値が範囲の外（`figures[].id` は 1〜10000、他は 0〜10000） | エラー | `{where}: <欄> の値 '…' が範囲（0〜10000）の外`（`figures[].id` は「1〜10000」） |

| すべて | 項目の配列（`nodes`・`edges`・`actors`・`steps`・`stages`・`layers`・`parts`・`events`・`sets`・`regions`・`series`）が配列でない | エラー | `{where}: <配列名> は配列` |
| すべて | 欄の値の型が書き方と違う（`x` が文字列、`nodes` が数、要素が辞書でない、数の欄が無限大・NaN（`chart` の `values`・`y.min`／`y.max`・`annotations[]` の `y` を含む） など。項目の配列が配列でないときは上の行の文言） | エラー | `{where}: <欄> の型が違う（<期待する型>）` |
| `blocks` | `nodes[]` に同じ `id` が 2 つ以上ある | エラー | `{where}: nodes の id 'x' が重複する（箱の id は図の中で一意）` |

| `blocks` | 箱の `shape` が `box`／`round`／`cylinder`／`cloud` でない（省略は `box`） | エラー | `{where}: nodes[i] の未知の shape '…'（box/round/cylinder/cloud）` |

| `chart` | `kind` が `line`／`bar`／`step` でない（欄が無いも） | エラー | `{where}: 未知の kind '…'（line/bar/step）` |

| `chart` | `x.values` が 2 個未満 | エラー | `{where}: x.values は 2 個以上（今は n）` |
| `chart` | 系列が 0 本 | エラー | `{where}: chart の系列が無い（今は 0）` |
| `chart` | 系列が 4 本以上 | エラー | `{where}: chart の系列は 3 本まで（今は n）` |

| `steps` | `direction` が `up`／`down` でない | エラー | `{where}: 未知の direction '…'（up/down）` |
| `layers` | 層の数が 2〜7 の外 | エラー | `{where}: layers の層は 2〜7（今は n）` |
| `layers` | `shape` が `stack`／`pyramid` でない | エラー | `{where}: 未知の shape '…'（stack/pyramid）` |

| `timeline` | `ticks` が 2〜12 の外 | エラー | `{where}: axis.ticks は 2〜12（今は n）` |

| `venn` | `sets` に同じ `id` が 2 つ以上ある | エラー | `{where}: sets の id 'x' が重複する（範囲の id は図の中で一意）` |

| 5〜10 の型 | 1 行だけの項目が半分を超える | エラー | `{where}: 1 行だけ（名前だけ）の段が n/m 個で半分を超える（段は「名前＋一言」を \n で 2 行以上に）`（「段」は型ごとに `steps`・`cycle`＝段、`layers`＝層、`parts`＝部位、`timeline`＝出来事、`venn`＝領域） |
| 5〜10 の型 | 項目の `label` が 4 行以上 | エラー | `{where}: stages[i] の label が n 行（3 行まで）`（配列名は型ごとの項目の配列） |
| 5〜10 の型 | 項目に `label` が無い・空・空白だけ | エラー | `{where}: stages[i] に label が無い`（配列名は同上） |
| すべて | `--check` を通ったのに描く途中で例外が出た（道具の欠陥） | エラー | `{where}: 描けません（<理由>）` |
| `icon` を持つ所 | 語彙に無い名前 | エラー | `{where}: nodes[i] の未知の icon '…'（絵の語彙 person/people/…/hand のいずれか）`（場所は `actors[i]`・`stages[i]`・`layers[i]`・`whole`・`parts[i]` も同じ形） |
| `icon` を置けない所 | 「絵の語彙」が挙げる 7 か所以外のどこかに `icon` がある（`timeline` の `events[]`・`venn` の `sets[]`／`regions[]`・`blocks` の線・`sequence` の手順・`chart` の系列・`matrix` の軸・図の一番上の階層を含む） | エラー | `{where}: events[i] に icon は置けない（置けるのは blocks・sequence・steps・cycle・layers・parts）` |

`'…'` は Python の `repr` の形（既存の `未知の shape` と同じ）。

## 描く・検証する

```bash
# 検証だけ（描かない）。問題があれば論点IDと図IDを添えて出て、終了コード 1（警告は出すだけで終了コード 0）
python3 scripts/render_material_figures.py --data data/ap --check

# 描く（既定の出力先は public/figures/materials/<試験>）
python3 scripts/render_material_figures.py --data data/ap --only 53 174

# 目視確認（PNG も書く）
python3 scripts/render_material_figures.py --data data/ap --only 53 \
    --out /tmp/figcheck --png-dir /tmp/figcheck

# 手本（10 の型のサンプル。型ごとに 1 ファイル）
python3 scripts/render_material_figures.py --data data/ap --samples --check
```

`--only` を付けたときは、絞った論点の図だけを判定する（他の論点の図にエラーがあっても、絞った論点の図は描く）。
絞った論点の図にエラーがあれば、描かずに止めてその図を示す。
`--check` を通った図を描く途中で例外が出たときは（道具の欠陥）、1 枚も書き出さずに止めて、その図と理由を示す。`--check` を絞り無しで回すと全部の図を判定する。

手本は `data/ap/material_figures/_samples/` にある（`_` 始まりは本番の入力に入らない）。上の 10 の型の例は、型ごとの手本 `_samples/<topic_id>-<type>.json` の図 1 の写し（例を変えたら手本も同じに直し、`--samples --check` が通ることを見る）。
**書いたら必ず PNG を目で見ること。** 文字がはみ出していないか、矢印が箱に届いているか、
凡例が重なっていないかは、検証では分からない。

### PNG で「壊れて見える」もの（SVG は正しい。直さない）

PNG 化に使う PyMuPDF の SVG 描画には穴がある。ブラウザでは正しく出る。

- **長音符「ー」と中黒「・」が消える。**「サーバー」が「サ バ」に見える
- **破線が実線に見える**（ライフライン、`style: "dashed"`、`vlines`）
