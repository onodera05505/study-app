# 教材（解説・周辺知識）の執筆仕様

論点ごとの学習用テキストを書くための指示書。全論点で同じ方針を使うことが目的。

**この仕様は v2（2026-08-23 改訂）。** v1 は改行だけのプレーンテキストだったが、
1段落 300字前後の塊が3〜4個続いて読みにくかったため、決まった記法で構造を付ける形に変えた。

---

## このアプリが目指しているもの

**受験する試験に最短で合格すること。** ただし単なる過去問暗記にはしない。

この仕様書は**IT パスポートと応用情報技術者試験（午前）の両方**で使う。違うのは
読み手の前提知識の深さだけで、書き方の決まりは同じ。応用情報を書くときは、
「用語を知っているか」ではなく**「計算・判断ができるか」**を問われる前提で書くこと
（式・手順・判断基準を必ず本文に置く）。

論点の背後にある知識を添えて、「ちゃんと学んでいる」実感が持てる状態にする。

だから教材は、市販テキストのような網羅的な解説ではなく、
**「その論点が試験でどう問われるか」を軸に、理解に必要な周辺知識を添えたもの**にする。

## 満たすべき最低条件

**その論点に紐づいた過去問を、この教材と問題解説を合わせて読めば解けること。**

これが唯一の必須条件。逆に言えば、そこに要らない情報は書かなくてよい。
まともに考えれば分かることを事細かに説明する必要はない。

## 2026-09-01 の方針変更（v3）— 教材と問題解説の役割分担

**誤答選択肢のケアは、問題側の解説（`scripts/prompts/write_question_explanations.md`）に移した。**
教材の役割は「その用語が何か・何が出たらそれか・図・計算の手順」に絞る。
理由: 単語の説明に選択肢の話が書いてあるのは不自然で、説明が長いとやる気が削がれる。
12 回出た論点は 12 問ぶんの問題解説が付くので、網羅性は問題の数が担保する。

v3 の教材は `materials_v3/` に書く（v2 は残す。seed は v3 を優先して読む）。

### 共通の変更

- `explanation` の 1 文目（定義）の直後に **見分けワード**の行を置く:
  `- **見分けワード**: 独立採算・意思決定の迅速化・事業領域ごと`（3 語以内。問題文にこれが出たらこの用語、という語）
- `### 出題パターン` の見出しは廃止。「〜という形で問われました」の列挙は問題解説側の仕事
- `### 混同しやすい用語` は、**選択肢に並んだから**ではなく**概念として取り違えやすいから**必要なときだけ残す。
  残すのは 2 つまで。用語名は `[[用語]]` で囲む（色付きになり、押すとポップで 1 行説明が出る）
- 本文中で他の用語に触れるときも `[[用語]]` が使える。片っ端に付けない。読者が「これ何だっけ」と思う語だけ
- 図の行 `![…](/figures/materials/…)` は**残す**。消しても `attach_material_figures.py` が入れ直すが、位置がずれる

### IT パスポート — 簡易化する

読者は入門者。市販教材の「図解でわかりやすい」を模倣しつつ、試験に直結する部分だけ切り取る。

- **目安**: `explanation` 250 字・`detail` 400 字（図・表・計算手順は数えない）。
  **ただしこれは上限ではなく目安。** 字数に収めるために必要な判断材料を落としたり、わかりにくくなるなら超えてよい。
  優先順位は「わかりやすさ ＞ 必要最低限の情報が入っていること ＞ 字数」
- `detail` に残すのは `### しくみ`（なぜそうなるか。3〜5 文）、`### 計算の解き方`（計算があれば）、
  概念的に取り違えやすい `### 混同しやすい用語`（2 つまで）。それ以外は削る
- 硬い語は言い換える: 規格番号（JIS Q 38500 など）は書かない、英語併記は略語そのものが用語のときだけ、
  「組織能力」「統制」「整備」→「決める・やらせる・確かめる」のように動作で言う
- 1 文は 60 字以内を目安に切る

### 応用情報 — 情報量は削らない

読者は学ぶ意欲のある人。**v2 の本文にある判断材料は残す。**
やることは「別の用語の説明」を問題解説側へ移すことだけ:

- `### 出題パターン` の選択肢列挙を外す（判断基準の説明として書かれている部分は `### しくみ` などへ移す）
- `### 混同しやすい用語` のうち、選択肢に並んだだけの語を外し、概念的に取り違えやすいものを残す（2 つまで）
- 見分けワードの行を足す。`[[用語]]` を付ける。それ以外の文章は短くしない

## 2つのモード

### 新規執筆

回を追加して新しく現れた論点に、ゼロから教材を書く。

### 書き直し（v1 → v2）

既に書かれた教材を v2 の形に整え直す。**これは書き換えであって、書き下ろしではない。**

- **情報を落とさない。** v1 の本文にある判断材料は、原則すべて v2 に持っていく。
  短くまとめようとして「〜など」で丸めない
- 構造を変えるための言い換えはしてよい。文をリストの項目に割るときに
  主語を補う、順序を入れ替える、といったことは必要になる
- **v1 に無い内容を足すのは、過去問を解くのに足りていないときだけ。**
  紐づく過去問を読んで、v1 の記述では正解を選べないものがあれば補う。
  「あった方がいい豆知識」を思いつきで足さない
- v1 に事実の誤りを見つけたら直す。ただし**過去問の原本と照らして**確かめること。
  一般論を根拠に「IPA の問題は普通こうだ」と判断しない（過去に誤報が7件あった）

## 入力

`data/material_bundles/bundle_NN.json` に、担当する論点が入っている。各論点には:

- `term` — 論点名
- `field` / `syllabus_item_name` / `middle` — シラバス上の位置
- `question_count` — 過去問での出題回数（重要度）
- `related_terms` — 分類時に拾われた周辺の用語
- `questions` — **その論点が実際に出題された過去問**（問題文・選択肢・正解・図表）
- `current` — 現行の教材（書き直しモードのときだけ入っている）

`questions` が最重要の材料。**実際にどう問われたかを見てから書く**こと。

## 使ってよい記法

**次の5つだけ。** これ以外は使わない。表示側（`src/client/components/Markdown.tsx`）が
この5つしか解釈しないので、他を書くと記号がそのまま画面に出る。

| 記法 | 書き方 | 使いどころ |
| --- | --- | --- |
| 見出し | `### 見出し` | `detail` の区切り。`explanation` では使わない |
| 箇条書き | `- 項目` | 並列に並ぶもの。混同しやすい用語、判断の分かれ目 |
| 番号付き | `1. 項目` | 順序があるもの。計算手順、段階を追う説明 |
| 強調 | `**語**` | 正誤の分かれ目になる語。1項目に1〜2か所まで |
| 表 | `\| 用語 \| 観点 \|` | 3つ以上の用語を2〜4の観点で見比べるとき |

**使ってはいけないもの:** `#` / `##`（h1・h2 は画面の見出しと衝突する）、リンク、
画像、コードブロック、引用（`>`）、水平線。

**画像は書き手が入れるものではない。** 論点ごとの図はスクリプトが作って教材に
差し込むので、`![…](…)` を自分で書かないこと（書くと検証で弾かれる）。

### 表の書き方

`detail` の中だけで使う。**3つ以上の用語を、2〜4の観点で見比べさせたいとき**に限る。
2列で足りるなら箇条書き（`- **用語** — 違い`）のままでよい。表は縦に長くなるほど
読みにくくなるので、迷ったら箇条書きにする。

- **ヘッダ行と `| --- |` の区切り行が要る。** 区切り行が無いと表として描画されない
- 列は**最大4**、行は**ヘッダ込みで最大8**
- セルは短く**1〜2文節**。文を入れない（スマホでは横スクロールになる）
- 各行のセル数をヘッダと揃える。1つでもずれると画面にパイプがそのまま出る
- セルの中でも `**強調**` は使える。それ以外の記法は使わない

```
| 方式 | 鍵 | 主な用途 |
| --- | --- | --- |
| 共通鍵暗号 | 送受信で**同じ鍵** | 本文の暗号化 |
| 公開鍵暗号 | 公開鍵と秘密鍵の**対** | 鍵の受け渡し |
| ハイブリッド | 両方 | SSL/TLS |
```

書き方の細かい約束:

- **リストの項目は1行で書く。** 折り返して2行目をインデントしても、別の項目として扱われる
- 項目の中で用語と説明を分けるときは全角ダッシュを使う: `- **内部統制** — 業務が…`
- 箇条書きは**3〜5項目**を目安にする。2項目なら文章で書いた方が読みやすい。
  6項目を超えるなら、それは見出しで分けるべき2つの話が混ざっている
- リストばかりにしない。**理由や背景は文章で書く。** 箇条書きは、
  並列に並ぶものを見比べさせたいときの道具

## 書くもの

### `explanation`（短い説明）— 150〜300字程度

学習画面で最初に見せる本文。「詳しく解説」を開かなくても、その論点の要点が掴める状態にする。

構成は固定:

1. **1文目で言い切る。** その論点が何であるかを、**論点名（括弧の前まで）を `**論点名**` と太字にして** `〜とは、…です` の 1 文で。別の呼び名（「バリューチェーン」を「価値活動」で）や上位の語で始めない
2. **1行空けて、試験で問われる点を箇条書きで2〜3項目。** 何と区別させられるか、
   どこが引っかけか。定義の丸写しではなく、過去問で実際に何を判断させられたかを書く

見出し（`###`）は使わない。短いので構造は箇条書きだけで足りる。

**「計算で問われる」と書くなら、その計算の中心になる式を `explanation` にも置くこと。**
`detail` にしか式が無いと、「詳しく解説」を開くまで式に辿り着けない。
式の話をしているのに式が無い状態に見えてしまう。

```
- 用語の意味よりも計算で問われます。**損益分岐点売上高＝固定費÷限界利益率**
```

**選択肢の記号（ア・イ・ウ・エ）を書かない。** 「正解はエです」と書くと、
後で問題を差し替えたり選択肢の順序が変わったりしたときに誤りになる。
「**91日**が答えになります」のように内容で書く。

```
**IT ガバナンス**とは、経営陣が組織の IT 利用を統制し、事業目的の達成につなげる仕組みです。

- 評価・指示・モニタを担うのは**経営陣自身**。外部への丸投げや担当部門への責任転嫁は誤り
- 評価する対象は**現在と将来**の IT 利用。過去の実績ではない
```

### `detail`（詳しい解説・周辺知識）— 600〜1200字程度

「詳しく解説」で展開される部分。**`###` の見出しで区切る。** 使う見出しは次から選ぶ。

| 見出し | 内容 | 必須か |
| --- | --- | --- |
| `### しくみ` ほか内容に合わせた名前 | なぜそうなるのか。丸暗記にしないための理由づけ | ほぼ必須 |
| `### 混同しやすい用語` | 試験で最も差がつくところ | 該当すれば必須 |
| `### 出題パターン` | （v3 で廃止。v2 の教材にだけ残る）問われ方の列挙は問題解説側の仕事 | v3 では書かない |
| `### 計算の解き方` | 手順を1つずつ。過去問の数値で実際に解いてみせる | 計算問題があれば必須 |

- 見出しは**3〜4個**に収める。5個を超えると、開いた瞬間に見出しの一覧に見えて読む気が失せる
- 1つ目の見出しは内容に合わせて具体的に付けてよい（`### 3つの役割（JIS Q 38500）` など）。
  中身が分かる名前の方が拾い読みしやすい
- `### 混同しやすい用語` は箇条書きが合う。`- **[[用語]]** — 違い` の形で並べる（用語集にある語は `[[ ]]` を付ける。太字だけだとポップが出ない）。見出し名は変えない。**2 つまでの上限は見出し名ではなく項目数で数える**（別名の見出しで 3 つ目以降を足さない）
- `### 出題パターン` は v3 では書かない。「判断軸」「見分け方」「対応づけ」のような別名の見出しで選択肢の振り分けを書くのも同じこと（2026-09-25 の読み直しで 12 論点に戻っていた）
- `### 計算の解き方` は番号付きリストで手順を割る。式は文中に普通に書いてよい

## 書き方の約束

- **常体（だ・である）ではなく敬体（です・ます）**で書く。気軽に学べるアプリなので。**箇条書きの項目・番号付きの手順・表の説明文も敬体**（担当ごとに割れる所。体言止めも避ける）
- **読点は「、」句点は「。」**（通常の日本語表記）。過去問データ側は IPA 原文に合わせて
  「，」を使っているが、こちらは自分たちの文章なので通常表記でよい
- **過去問の問題文をそのまま引用しない。** 出典表示の義務が生じる。
  「〜を選ばせる問題が出ています」のように要約して触れる
- 不確かなことは書かない。過去問から読み取れないことを推測で補わない
- 太字を使いすぎない。1つの段落・項目に1〜2か所まで。全部太字は太字が無いのと同じ
- **教材に選択肢の消し方を書かない**（2026-09-25 の読み直しで最多の型）。「〜ではありません」「〜という限定もありません」「〜では絞れません」「〜を落とせます」「〜で見分けられます」「〜で仕分けてください」「引っかけは〜」は誤答のケアで、問題解説（note）の持ち場。教材は問題の外でも読まれる。同じ論点の解説 note とほぼ同文の行は教材から消す（`check_materials.py` が一致を警告する）
- **同じ語・同じ数値を 1 つの教材の中で 2 つの意味に使わない**（「同じ側」「上下」のような位置の語、計算の合計に出る数値）。式を置くなら記号の意味（M・N・［ ］）も同じ場所に書く
- **「計算の解き方」は過去問 1 件を解いてみせるまで**。全選択肢の値を出したり、正解の組をそのまま表にしない（解説側と二重になる）
- 見分けワードは「問題文にこの語が出たらこの論点」と決まる語だけ。論点名そのもの・対の用語・一般語（要点）・本文が例外だと書く性質は置かない
- 制度・基準は策定した主体と公表した所を分けて書く（「金融庁が定めた」→ 策定は企業会計審議会）。法令は改正で名前が変わるので、過去問の時点の名前で書くときはそう断る
- 略号（GPL・SLM・BGP）は初出で 1 行の言い換えか `[[ ]]`。用語集にある語で一度 `[[ ]]` にしたら以後も `[[ ]]`（同じ教材の中で素の太字と混ぜない）

## 出力形式

```json
{
  "bundle": 1,
  "materials": [
    {
      "topic_id": 1,
      "term": "サービスデスク",
      "explanation": "…",
      "detail": "…"
    }
  ]
}
```

- 出力先は**担当への指示で指定されたパス**（IT パスポートなら `data/ip/materials_v2/`、
  応用情報なら `data/ap/materials_v2/`）。v1（`materials/`）は書き換えない
- 改行は JSON の `\n`。見出しの前は空行を入れなくてよい（表示側で間を取る）
- 担当バンドルの全論点を含めること。抜けるとその論点だけ v1 のまま残る

## 出力量について

1バンドルは8論点。1論点あたり `explanation` 150〜300字 + `detail` 600〜1200字なので、
JSON 全体で 12,000 字程度になる。**一度の Write で書き切れる量なので、分割せず1回で書く。**

（当初は1バッチ30論点で走らせたが、出力が大きすぎて全エージェントが応答の途中で
落ちた。8論点に細分化したのはそのため。これ以上増やさないこと。）

## 書き上げたら

```bash
python3 scripts/check_materials.py --dir data/materials_v2
```

記法・字数・見出し構成・過去問の引用を機械的に見る。指摘が出たら直す。
