# 作業ログ 2026-08-24 — 教材を v2 に書き直した

過去問の取り込み（残り18回）を中断して、**既に書いてある532論点の教材を作り直した**。
未取込の回を増やすより、手元の内容を学習コンテンツとして仕上げるほうが効果が高いと判断したため。

結果は本番反映済み（https://itpass-study-c91.pages.dev）。

## 何が問題だったか

v1 の教材は、過去問を読みながら随時書き足していったもので、**読み物としての体裁が無かった**。

- `detail` は中央値 714字が3〜4段落の塊。403論点がちょうど3段落
- 見出しゼロ、箇条書きは144論点のみ（しかも文中の「・」が大半）
- 表示側も `<p style={{whiteSpace:'pre-wrap'}}>` でべた書き

一方で、段落の書き出しを数えると「出題…」433件、「混同…」182件。
**構造は文章の中に既に潜んでいて、引き上げれば済む状態**だった。

## 立てた仮説と、その答え合わせ

> 情報量は今のままで、体裁を整えるだけで十分では

**体裁については当たり、情報量については外れだった。**

全532論点で「紐づく過去問を1問ずつ突き合わせ、この教材だけで正解を選べるか」を
確認させたところ、**加筆なしで済んだのは3割弱**。残りは現行教材では解けない過去問を抱えていた。

- **WBS** — 4問中3問が解けない（分解の向き、粒度の決まり、WBS 辞書の役割が未記載）
- **損益分岐点** — 7問中6問に計算例なし
- **ディレクトリ構造** — 相対パスの組み立て手順そのものが未記載
- **OSS** — 「Firefox＝ブラウザ／MySQL＝DBMS」の対応がなく、名前から選ぶ問題が解けない

原因は書き手の手抜きではない。**v1 は「その論点の代表的な1〜2問」を見て書かれていた。**
論点に紐づく過去問が増えても、教材は最初に書いたままだった。

総文字数は 464,684字 → 550,726字（+18%）。増えたぶんはこの穴埋めである。

## やったこと

### 1. 表示を Markdown 化した

`src/client/components/Markdown.tsx`。依存追加なしの自前レンダラで、**解釈するのは4つだけ**。

| 記法 | 用途 |
| --- | --- |
| `### 見出し` | detail の区切り |
| `- 項目` | 並列に並ぶもの |
| `1. 項目` | 順序があるもの（計算手順） |
| `**語**` | 正誤の分かれ目 |

表・リンク・画像・コードブロックは意図的に外した。書き手が複数いるので、
記法を絞らないと担当ごとに見た目がばらつく。

**v1 のプレーンテキストもそのまま描ける**（1行＝1段落）ようにしてあるので、
書き直し前後が混在したまま本番に出せた。これが「頻度順に進めて途中で止めても損しない」を成立させた。

### 2. 執筆仕様を v2 に改訂した

`scripts/prompts/write_materials.md`。v1 は「Markdown を使わない」と書いてあったので全面改訂。
使ってよい記法、`detail` の見出し構成（しくみ／混同しやすい用語／出題パターン／計算の解き方）、
字数レンジ、そして**書き直しモード**（情報を落とさない・過去問を解けないときだけ加筆）を固定した。

### 3. 検証を3本立てにした

| スクリプト | 見るもの |
| --- | --- |
| `check_materials.py` | 記法・見出し構成・字数・過去問の引用・**担当バンドルと出力の論点の一致** |
| `check_material_coverage.py`（新規） | v1 にあって v2 に無い固有語、`detail` が v1 比8割未満に縮んだ論点 |
| 画面確認 | 実際の描画 |

`check_materials.py` の Markdown 判定は「混入エラー」から「規定の記法か」に**反転**させた。
v1 と v2 が混在しても両方を検査できる（`detail` に `###` があれば v2 と判定）。

### 4. 67バンドル × 8論点で分担させた

`scripts/build_material_bundles.py` で出題頻度の降順にバンドルを生成。
各論点に現行教材と**紐づく過去問（正解つき）**を同梱した。
過去問を渡さないと、担当は整形だけして情報の欠落に気づけない。

## 詰まった点

### API の過負荷でまとめて落ちる

2回あった。1回目は6体が「読み込み開始直後」で停止（環境側の一時不調）。
2回目は 529 Overloaded で6体。並行数を 8 → 4 → 3 と落として対応した。

**落ちても書き出し済みのファイルは残る**設計なので、被害は時間だけで済んだ。
実際、2回目に落ちた6体のうち4体は書き出し後に落ちていた。
やり直しはバンドル単位で完結する。

### 担当の自己申告が当てにならなかった

**同じ担当が、担当していない論点番号を並べた report を返してきた例が複数あった。**
ファイルの中身は正しかったので、報告文だけの問題だった。

ただしこれは「担当が別の論点を書いてしまい、担当分が誰にも書かれないまま残る」
という事故と見分けがつかない。そこで `check_materials.py` に
**入力バンドルと出力の論点を突き合わせる検査**を追加した。最終的に不一致はゼロ。

**教訓: 報告文ではなく成果物を機械で検証する。**

### 過去問の原文引用

1件だけ検出された（インバウンドマーケティングの出題パターンが問題文と30字以上一致）。
要約表現に置き換えて解消。担当プロンプトに引用禁止を明記してからは発生しなかった。
