# 学びの対象（資格以外のロードマップ型）を足して本番に出す手順（線）

「この学びをしたい」から入る。**人が触る場所は 3 つだけ**: 対象の登録（1 コマンド）、質疑応答の答え（`data/<対象>/kickoff.json` と登録簿 `roadmapSpec`）、本番の対話操作（`bootstrap_personal.sh`）。残りはスクリプト。
入口は Skill `/learn-target`。最初の実例は itc（`docs/作業ログ_2026-09-15_ロードマップ試作.md`）。

## 0. 対象を登録し、質疑応答を完結させる（生成に入る前）
```bash
python3 scripts/new_target.py <key> --name "<画面の名前>" --target-name "<対象の一言>" --fields "分野1,分野2,分野3,分野4" [--per-day 3] [--days 14]
```
登録簿 `src/shared/targets.json`（UI・出典名・回の問題数・模試設定・仕様書の値）、`scripts/pages_projects.json`（Pages 名・DB 名）、`.env.<key>`、`wrangler.jsonc` の env、`data/<key>/{kickoff.json, roadmap_config.json, explain_terms.json}` ができる。
- `kickoff.json` は `data/_defaults/kickoff_defaults.json` の既定で埋まっている。**空の項目（目標・期限・一次資料・横展開・知識の種類・読者像・対象の ID 等）を本人と答える**
- 答えのうち仕様書に効く値（読者像・利用場面の見出し・問 2 の趣旨・禁止語・学習者役の一人称）は `targets.json` の `<key>.roadmapSpec` に写す
- 門: `python3 ~/.claude/brain/check_target_kickoff.py --file data/<key>/kickoff.json` が未回答 0、`python3 scripts/new_target.py --check` が問題 0
- 仕様書を描出: `python3 scripts/render_prompts.py --data data/<key>` → `data/<key>/prompts/{roadmap_materials,roadmap_questions,roadmap_learner}.md`。**担当にはこれを読ませる**（`scripts/prompts/roadmap_*.md` はテンプレート）

## 1. 生成（担当は Opus。値は kickoff / roadmap_config）
1. 一次資料の収集（担当 3: 公的・標準／実務や採用の公開資料／利用場面で問われる頻度）→ `data/<key>/sources/*.json`（転記なし・`fetched` を正直に）
2. 名寄せと重み付け（担当 1）→ `topics_candidates.json`（交差数・頻度・前提・到達基準）。前提（`prereq`）は単位の名前ではなく論点の ID の整数で書く。単位に副題を添えるときは、候補の単位に名前（`term`）とは別の欄 `subtitle` で書く
3. `python3 scripts/build_roadmap.py --data data/<key>`（`roadmap_config.json`: must_include / exclude / min_per_goal / prereq_add / prereq_replace / cluster / summary_override / group_by）→ `roadmap.json`・`material_bundles/`。回の束ね方は下の「1.5」。`roadmap_config.json` で単位を指す所はすべて論点の ID で、`summary_override`・`prereq_add`・`prereq_replace` の鍵は ID の数字の文字列、その値の前提と `must_include`・`exclude`・`cluster` の一覧は整数で書く。どの候補にも当たらない ID があると組み立てが止まり、その ID が出る（REQ-430・434）。候補の `subtitle` は名前と分けたまま `roadmap.json` の単位の `subtitle` へ移る（REQ-429）。組み立て直さずに要約だけを直すときは `python3 scripts/apply_summary_override.py --data data/<key> --id <論点の ID> --summary <要約>` が設定と `roadmap.json` の両方を書き換える（当たらない ID ならどちらも書かずに止まる。REQ-435・436）
4. 教材（担当: 8 論点 / 体。`data/<key>/prompts/roadmap_materials.md` を最初に読ませ、`check_roadmap_bundle.py` を回させる）→ `materials/`
5. 確認問題（担当: 1 バンドル / 体。誤答解説 `choice_notes` つき）→ `roadmap_questions/`。独立解答 2 体が教材だけで解いて不一致率 20% 以下
6. 図（kickoff の figures が「付ける」）: `plan_roadmap_figures.py --ids …` → 担当が `material_figures/<id>.json` → `render_material_figures.py`
7. 門: `python3 scripts/check_roadmap.py --data data/<key>`

## 1.5 回の束ね方（日か章か）
回は「日」か「章」で束ねる。決めるのは `roadmap_config.json` の `group_by`（無ければ日）。
- **日で束ねる**（既定。itc など）: 学ぶ順を `per_day` ずつ割って日にする。回の ID は `<key>-dNN`、見出しは登録簿 `roadmapSpec.roundLabel`（例「{day} 日目」）。1 回の問題数は登録簿 `questionsPerRound`（＝ `roadmapSpec.perDay` × 2）
- **章で束ねる**（eng）: `group_by: "chapter"`、`max` は候補数（全候補を載せる。`per_day` は使わない）。名寄せで各候補に `chapter`（章の名前）と `tier`（印の段。登録簿 `roadmapSpec.tiers` の level）を付けておく。欠けた候補があると `build_roadmap.py` が止まる
  - 章の順は登録簿 `fields` の分野の順 → 候補ファイルでの章の初出の順。章の中は候補ファイルの順を骨格に前提を前に出し、★（印 1）の単位を章の末尾に置く（同じ章の上位の単位の前提になっている ★ は前に出て、注が出る）。章の大きさは中身のまま。`cluster` は使わない
  - `roadmap.json` は `group_by: "chapter"`・`rounds`（章の数）を持ち、各単位は `round`（章の番号）・`chapter`（章の名前）・`tier` を持つ（`day` は持たない）
  - 回の ID は `<key>-cNN`。確認問題の回の見出しは `roadmapSpec.roundLabel` を `{day}`（章の番号）と `{label}`（章の名前）で埋めた語（`{label}` が無ければ末尾に空白と章の名前を足す。例「第 1 章 コンピュータを形づくる部品」）。1 回の問題数はその章の単位数 × 2
- どちらでも、投入データの各論点は `round`（回の ID。補足の論点は `roadmapSpec.extraRoundId`）・`round_label`（日では見出しと同じ語、章では章の名前、補足では `extraRoundLabel`）・`tier`（登録簿に `tiers` がある学びだけ値。補足の論点も候補の印を持つ。無い学びは null）を持つ
- 単位に副題を添えるときは、候補（`topics_candidates.json`）の単位に名前（`term`）とは別の欄 `subtitle` で書く。`build_roadmap.py` が `roadmap.json` の単位の `subtitle` へ移し（REQ-429）、`build_target_dataset.py` がそのまま投入データ `topics.json` の `subtitle` へ、`build_seed.py` が `subtitle` 列へ移し、名前から副題を切り出さない（REQ-414）。副題を持たない単位は欄を書かない。空の文字列や文字列でない値を書くと組み立てが止まる（REQ-422）。欄の形の正本はこの 2 本のスクリプト
- 登録簿 `roadmapSpec` には、回の見出しの語 `roundHeading`（`{day}` を含み、章で束ねる学びは章の名前 `{label}` も）・回の数の語 `roundCount`（`{n}`）・回ごとの確認の語 `roundCheck`・確認問題の回の見出しの型 `roundLabel`（`{day}`）が要り、補足の分野・回の ID・回の見出し `extraField`・`extraRoundId`・`extraRoundLabel`（回の ID は `exemptRounds` にも、分野は `fields` にも置く）が要る。日で束ねる学びは `perDay`・`questionsPerRound`（＝`perDay` × 2）と 1 回の論点数の語 `perRoundCount`（`{perDay}`）も要り、章で束ねる学びはこの 3 つを持たない。印を持つ学びは `tiers` の各段に `label` が要る。投入データは、学ぶ順が 1 から欠番なく続き、確認問題の回が紐づく単位の回と一致する（補足の回を除く）。欠けていれば配備（`deploy-pages.sh` が呼ぶ `check_roadmap_registry.py`）も投入（`check_seed.py`）も止まる（BR-037・不変条件 D14）

## 2. 学習者役で検証（2〜3 周）
`build_learner_pack.py --data data/<key> --cycle <周の番号> --out <data/ の外の、無いか空の場所>`（その周のパックの写しを `data/<key>/eval/pack_cycle_<周の番号>.json` に残す。同じ周の写しか結果があれば作らない）→ 初心者ロールの新しい担当（`prompts/roadmap_learner.md` の一人称。自己申告の `topic_id` には `roadmap.md` の括弧の単位 ID を必ず書く）→ 閉じた本の説明テスト（`explain_terms.json` の 12 語）を別担当が採点 → `grade_learner.py --data data/<key> --cycle <同じ周の番号> --answers <答えのファイル> --explain <採点のファイル>`（その周の写しで採点し、同じ周の結果があれば断る）。直して新しい周の番号でもう 1 周。決まりの正本は UC-019（`docs/goals/GOAL-12-measure-with-learner-role/UC-019-measure-with-learner-pack/`）。

## 4. 本番（個人アカウント）
```bash
npx wrangler login                              # 個人アカウント（登録簿の account_id）。同じ Mac で別アカウントに差し替わっていることがある
bash scripts/bootstrap_personal.sh <key>        # 人: D1 は先に `npx wrangler d1 create study-app-<key>-db` して ID を wrangler.jsonc に。Pages・migrations・secret
bash scripts/finish_remote.sh <key>             # migrations を当てる → 投入 → 突き合わせ → デプロイ → 模試設定
```

**既に出ている対象（itc・mkt・msg・ecl・eca・cnv など）を出し直すときも、先に migrations を当てる。** 新しい列（`topics.round` など）を読む画面を列の無い D1 に出すと 500、列の無い D1 に seed を流すと INSERT が落ちる。`finish_remote.sh <key>` は「`d1_migrations.sh <key> apply`（本番は当てる前にバックアップ）→ `seed_remote.sh` → `deploy-pages.sh`」の順に回す。`deploy-pages.sh` と `seed_remote.sh` を単独で回すときは、先頭の `d1_migrations.sh <key> check` が未適用を見つけて止まる。**apply だけ当てて `deploy-pages.sh` を回さない**: 新しい列を持つ seed を入れるまで論点の回は空で、`deploy-pages.sh` の `check_d1_rounds.sh <key>` が止める。ローカルで確かめるときは `bash scripts/d1_migrations.sh <key> apply --local && bash scripts/seed_remote.sh <key> --local && bash scripts/check_d1_rounds.sh <key> --local`（不変条件 D26）

## 4.3 まなびばに載せる（SSO。要件 §15）

新しい学びは、まなびばの一覧と権限に載せないと誰も入れない（学び側はまなびばからのログインだけ受ける）。
1. 学び側の Pages に共有秘密: `bash scripts/set_sso_secret.sh`（4 つ全部に同じ値を置き直す。`.sso_secret.local` が要る）
2. `wrangler.jsonc` の env に `SSO_PORTAL_URL` があることを確認（`new_target.py` が書く。2026-09-17 に書くよう直した）
2.5 デプロイ後に `bash scripts/check_sso_prod.sh`（O13。sso:true・secretSet:true・パスワードログイン 404）
3. `bash scripts/deploy_portal.sh`（登録簿から学びの一覧を作り直して出す）。**`finish_remote.sh` の後**に回す（登録簿に url が入ってから。入る前は一覧に出ない）
4. まなびばの管理画面で、開ける人に新しい学びの権限を付ける

## 決めてあること（2026-09-15 本人）
- 自作の確認問題は出典を画面に出さない（`roadmap: true` で非表示。データには持つ）
- 外した単位は消さず「補足（ロードマップ外）」の分野に `sort_order` の末尾で置く。回は `<key>-ex`（問題数は固定でない。登録簿 `exemptRounds`）
- 確認問題は誤答ごとの 1 行解説を持つ。学習者役は Opus（小さいモデルにしない）
- 図は付ける。優先は学ぶ順・到達基準・手順／対比／計算の単位

## 落とし穴
- **OAuth トークンは失効し、別プロジェクトのログインで別アカウントに差し替わる**（中央 `reports/125`）。本番操作の前に `whoami` と account_id の照合（スクリプトが止める）
- `wrangler d1 migrations apply` は確認プロンプトで止まる。非対話は `CI=1`（ただし CI=1 は OAuth を拒むので本番は人が対話端末で）
- `data/<key>/questions/` は投入経路が `*.json` を全部「回」として読む。生成前の問題は `roadmap_questions/` に置く
- 資格版の D1 に `sort_order` 列は無くてよい（資格版の SQL と seed は列を参照しない）。次に ip / ap を触るときに `migrations apply` で揃える
- `app_settings` の列の既定値（100 問）は seed が新しい DB でだけ対象の値で作る。既存 DB は `align_app_settings.sh`
