# 検査観点カタログ — ユーザー視点でアプリを検査する層の一覧

**書いた日: 2026-09-02。** きっかけは用語ポップの全滅（データ側の検査は全部通っていたのに、
画面では 9 割が文字のまま出ていた）。個別の検査を場当たりで足すのをやめ、
**「どの層で・何を・どうやって見るか」を先に固定して、抜けている層を機械的に見つける**ための文書。

このアプリ専用ではない。**次のアプリを作るときは、この文書を最初に持ち込んで
各層の検査を作りながら実装する**（あとから足すと今回のように事故で気づくことになる）。

## 原則（層より先にこれ）

1. **層ごとに門を置く。** 検査は「やる」ではなく「やらないと先へ進めない」形にする
   （例: `check_seed.py` が通らないと投入しない、`check_render.sh` が通らないとデプロイしない）
2. **実データ全件。** 代表例の抜き取りは、書き手（担当エージェント）ごとの流儀のずれを拾えない
3. **状態の行列で見る。** 画面 × { 未取得 / 空 / データあり / エラー } × { 画面幅 } を列挙してから見る。
   「動くか」だけ見に行くと、読み込み中・空・失敗の状態を見ずに帰ってくる
4. **確認した「つもり」を疑う。** 「API に入っている」「コードが bundle にある」は「画面に出ている」ではない。
   どの層まで確認したかを言葉にする
5. **検査自体を検査する（変異テスト）。** 門を作ったら、わざと壊して落ちることを確認するまでが実装
6. **報告は数値。** 担当の「問題ありませんでした」は信じない。件数・exit code・スクリーンショットで受け取る
7. **誤報を前提に裏取り。** 「壊れている」という報告は原本と照合してから直す（8 回中 7 回誤報の実績）

## 層の一覧

| # | 層 | 何が壊れるか | このアプリでの門 | 状態 |
| --- | --- | --- | --- | --- |
| L1 | 元データ（JSON） | 書き手ごとの流儀ずれ、正解の食い違い、範囲外の記法 | `check_materials.py` / `check_explanations.py` | あり |
| L2 | seed → DB | 出典の取り違え、UPSERT の列漏れ、件数の欠け | `check_seed.py` ＋ 投入後 SELECT | あり |
| L3 | API | 形の変化、認証、失敗時のステータス | `check_api.sh`（ローカルに立てて全経路に当てる） | あり |
| L4 | 描画（コンポーネント × 実データ） | 記法の素通し、図の欠落、ボタンにならない用語 | `check_render.sh`（デプロイ前に自動） | あり |
| L5 | 画面（本物のブラウザ × 状態 × 幅） | レイアウト崩れ、はみ出し、読み込み中の誤表示、コンソールエラー | `audit_screens.sh`（Chromium で全画面×全状態を採取） | あり（`audit_screens.sh`） |
| L6 | 使いやすさ（ヒューリスティック） | 迷う導線、押せそうで押せない、文言の不統一、フィードバック不足 | 観点表 × L5 のショットのレビュー（実施記録: `改善候補_2026-09-02.md`） | あり（手順） |
| L7 | 運用 | 本番だけ壊れる（PBKDF2 上限等）、secret 未反映、バインディング欠け | deploy-pages.sh・手順書・`docs/落とし穴.md` | あり（文書） |

## L3: API の検査 — 使い方

- `bash scripts/check_api.sh ip`（`ap` も同様）。ローカルに `wrangler dev`（ポート 8788）を
  自前で立てて検査し、終わったら落とす。**本番には当てない**
- 見るもの: 認証の境界（保護 16 経路 × 未認証3通り）／失敗時のステータスと `{error: 日本語}`／
  各 GET の形（`src/server/routes/*.ts` から書き起こした期待形と全要素を突き合わせ）／
  API と ローカル D1 の件数の一致／セッションの一連の流れ／空の一覧が `[]` か
- 期待形のキーには「クライアントが参照しているか」の印が付いていて、**参照キーの欠けは
  エラー・それ以外は警告**。画面を足してキーを増やしたら、`scripts/check_api.py` の
  期待形にも足す（足し忘れは警告として出る）

## L5: 画面の検査 — 状態の行列

採取するもの: スクリーンショット（PNG）＋ DOM ＋ コンソールエラー ＋ 失敗したリクエスト。

- **画面**: 全ルート（このアプリなら 9 ＋ ログイン）
- **アカウント状態**: 新規（進捗ゼロ）／学習途中／受験の中断あり／履歴が多い。**状態はアカウントで作る**
  （画面をモックしない。モックは「その状態が本当に作れるか」を検査しない）
- **データ状態**: 各画面の { 読み込み中 / 空 / 通常 / 大量・極端に長い } 。読み込み中はネットワークを
  遅延させて撮る
- **エラー状態**: API を落として（500 / ネットワーク断）各画面がどうなるか。白画面・無限スピナー・
  古いデータの残留は全部不合格
- **画面幅**: 375px（スマホ）/ 640 前後（このアプリの breakpoint）/ 1280px。**横スクロールが
  ページ全体に出たら不合格**（表・図は自分の枠内でスクロールする）
- **配色**: ライト／ダーク（`prefers-color-scheme` 両方で撮る）
- **操作**: 押せるもの全部を実際に押す。ポップ・メニューは開いた状態も撮る。Esc・外側クリックで閉じるか
- **アクセシビリティの最低線**: 押せるものが `button`/`a` か、画像に alt、フォームに label、
  フォーカスが見えるか（axe 等の機械検査を1回通す）

### 使い方

```bash
bash scripts/audit_screens.sh ip           # ビルド → wrangler dev(8787) → 採取。ap も同じ
```
`$SCRATCH/audit/<試験>/` に PNG と `manifest.json`（撮った組合せ・hscroll・コンソールエラー・
axe violation）が出る。**まず `manifest.json` の summary を読み、`hscroll` と `spinnerOnError` と
`consoleErrors` が 0 でない行の PNG だけを開く**（全部見るには多すぎる）。
状態の違うアカウントは `scripts/audit_fixtures.mjs` が API 経由で作る（SQL は叩かない）。入り方は `check_api.py` と同じで、
手元の SSO の偽物が発行した使い捨てコードを学び側の signInWithCode で換える（学び側のパスワードの経路は無い）。

## L6: 使いやすさの観点表（スクリーンショットを見ながら）

1. **今どこで何が起きているか分かるか** — 読み込み中の表示、保存されたことの通知、正誤の即時フィードバック
2. **次に何をすればよいか分かるか** — 空状態が次の行動を案内するか（「まだ〜がありません」で終わらない）
3. **戻れるか・取り消せるか** — 誤操作の戻り道。破壊的操作（中断・ログアウト）に確認があるか
4. **迷わないか** — 同じものは同じ名前か（文言の不統一）。ナビの現在地が分かるか
5. **読む負荷** — 1画面の情報量。折りたたみの初期状態は適切か。長文が壁になっていないか
6. **触れるか** — タップ領域の大きさ、押せるものが押せそうに見えるか、ホバー依存の情報が無いか
7. **待たせないか** — 体感の遅さ。連打への耐性（二重送信）
8. **間違いに強いか** — 入力の検証と、失敗したときの文言（原因と対処が書いてあるか）

レビューのやり方: 1画面ずつ、観点表の番号で指摘を出す。**指摘には必ずスクリーンショットの
ファイル名と根拠の コード:行 を付ける**（付けられない指摘は捨てる）。

## 新しいアプリを作るときの持ち込み手順

1. この文書をコピーし、L1〜L7 の「このアプリでの門」列を埋める（最初は全部「穴」でよい）
2. 画面を1つ作るたびに、状態の行列（L5）へ行を足す
3. データの検査（L1/L2）と描画の検査（L4）は**データが 10 件のうちに**作る。全件検査は最初なら一瞬で書ける
4. デプロイスクリプトを作った日に、門をその中に入れる
5. リリース前に L5/L6 を1周。以後は画面を足したときだけ差分で回す

## 画面を人や担当が見るときの束（2026-09-16 追記）

`npm run build` は既定（ip）の束を作る。ロードマップ型（itc / mkt）の画面を `wrangler dev --env <key>` で見るときは `npx vite build --mode <key>` で束を作り直す（`scripts/deploy-pages.sh` はこれを使う）。受入担当が ip の束で mkt を見て空振りした。

`wrangler dev` で画面やログインを見るには `JWT_SECRET` が要る。`.dev.vars` に書く（雛形は `.dev.vars.example`）。`--env <key>` を付けるときは `.dev.vars.<key>` だけが読まれるので、そちらにも書く。無いとログインも認証を要する経路も 503 で断られる。
