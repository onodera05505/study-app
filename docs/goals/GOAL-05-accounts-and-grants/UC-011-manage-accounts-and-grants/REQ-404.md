# REQ-404

> 管理者の役割を外す更新か管理者のアカウントの削除を受け付けるとまなびばの管理者が 0 人になる場合（2 人の管理者の求めが重なった場合を含む）、システムは、その求めについて役割もアカウントも権限も変えず、最後の管理者は外せないことを示す。

## 検証方針

- **分割クラス**:
  - `#race-mutual-demotion` — 管理者が 2 人だけの状態で、2 人が互いの役割を外す求め（名前と権限も添える）を重ねた入力（片方だけが通り、断られた求めは 409 の理由つきで、役割も名前も権限も変えない。契約の例 `lastAdminDemotion`）
  - `#race-mutual-delete` — 同じ状態で、2 人が互いのアカウントの削除を重ねた入力（片方だけが通り、断られた求めはアカウントも権限も消さない。契約の例 `lastAdminDelete`）
  - `#race-demotion-and-delete` — 同じ状態で、一方が相手の役割を外し、相手が一方を削除する求めを重ねた入力（片方だけが通り、管理者が 1 人残る）
  - `#not-last-admin-passes` — 管理者が 3 人の状態で、2 人が互いの役割を外す求めを重ねた入力（0 人にならないので両方とも通る。条件の外側の境界）
  - `#self-demotion-before-conflict` — 管理者が 2 人だけの状態で、同じ管理者が相手の降格と自分自身の降格を重ねた入力（自分自身の降格は 409 より先に 400 で断られる。契約の updateAccount の errors の隣り合う 2 件）
- **尽きている根拠**: 管理者を減らす操作は契約の `updateAccount`（役割を利用者にする）と `deleteAccount` の 2 つで、求め 1 件ずつでは呼び出した管理者が残る（REQ-167・REQ-172）ので、0 人になりうるのは 2 つの求めが重なり、どちらも書き込みの前の検査を通った場合だけ（UC.md の並行性の行）。重なる 2 つの組は（降格・降格）（削除・削除）（降格・削除）の 3 通りで尽き、条件の外側は管理者が残る人数の 1 つ（3 人）で取る。errors の並びの隣り合う組は、updateAccount の自分自身の INVALID_INPUT と CONFLICT を 1 クラスで取る。
- **境界の扱い**: 「重なり」は、片方の求めが最初の書き込みに達したところで、もう一方も書き込みに達するまで待たせて作る（D1 の口でだけ差し込み、まなびばのコードには触れない）。どちらの求めが先に書き込むかは文が決めないので、通った側と断られた側は応答から分けて見る。deleteAccount の NOT_FOUND と CONFLICT は、無い相手の削除で管理者は減らないので両方の条件を満たす入力が作れず、先後のクラスは置けない。
- **検証しない**: 断りの文面（R-102）。実際の配備の D1 での同時実行の並び（単体の偽の D1 は 1 本の SQLite で、本番の並び方は観測できない。書き込みの時点で断る検査の有無はこの偽の D1 で決まる）。
