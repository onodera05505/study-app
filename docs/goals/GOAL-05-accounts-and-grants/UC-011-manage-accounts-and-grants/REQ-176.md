# REQ-176

> 役割が利用者のアカウントから、アカウントの一覧・作成・更新・パスワードの再設定・削除のいずれかを求められた場合、システムは、求められた内容を返さず、いかなる変更も行わず、管理者だけが使えることを示す。

## 検証方針

- **分割クラス**:
  - `#list-as-member` — 役割が利用者のセッションで一覧を求める入力（一覧が返らず、管理者だけが使えることが示される）
  - `#create-as-member` — 役割が利用者のセッションで作成を求める入力（アカウントも権限もできない）
  - `#update-as-member` — 役割が利用者のセッションで更新を求める入力（相手の項目も権限も変わらない）
  - `#reset-as-member` — 役割が利用者のセッションでパスワードの再設定を求める入力（パスワードも相手のセッションも変わらない）
  - `#delete-as-member` — 役割が利用者のセッションで削除を求める入力（アカウントも権限も消えない）
  - `#forbidden-before-invalid` — 役割が利用者のセッションで、送った本文も形を満たさない求め（先に管理者だけが使えることが示される。契約の例 `forbiddenBeforeInvalid`）
- **尽きている根拠**: 契約の管理の operation は 5 つで、そのすべてが FORBIDDEN の errors を持つので operation ごとに 1 クラス（要件の文が挙げる 5 つと 1 対 1）。役割は enum の 2 値なので「管理者でない」は利用者の 1 通りで尽きる。先後は、FORBIDDEN より後に置かれた INVALID_INPUT と同時に成り立つ入力 1 つで確かめる。
- **検証しない**: セッションが無い呼び出し（契約の各 operation の UNAUTHENTICATED。BR-001 が持ち、UC.md の事前条件の外。この UC には UNAUTHENTICATED を持つ要件が無く、要件の欠けとして報告）。断りの文が内部の事情を映さないこと（BR-002 は利用者向けの経路に限る＝OQ-88 で、管理の経路はその外）。
- **参照先**: `tests/portal/repay_UC-011_manage_accounts.test.ts` の describe「REQ-176 利用者からの管理の操作」（全クラス）。本番相当の経路は system suite の `scripts/check_portal_api.py::check_admin_accounts`（まなびばに実際に HTTP で当てる検査。一般の利用者が 5 つの経路すべてで断られることを見ている。`@covers` の対象外）
