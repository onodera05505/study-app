# REQ-178

> 更新の求めに、受け付けられない名前・役割のいずれか、または学びの登録簿に無い学びが含まれていた場合、システムは、そのアカウントの項目も権限も変えず、受け付けられなかった項目を示す。

## 検証方針

- **分割クラス**:
  - `#bad-name` — 名前が空、または 50 文字を超える入力（契約の例 `emptyName`）
  - `#bad-role` — 役割が契約の enum の外の値である入力
  - `#unknown-learning` — 開ける学びに、学びの登録簿に無い key が含まれる入力（BR-004）
  - `#malformed-body` — 本文が JSON でない入力
  - `#partially-valid-request` — 形を満たす項目と満たさない項目が混ざる入力（満たす項目も反映されない＝部分適用なし）
  - `#invalid-before-not-found` — 存在しない id と、形を満たさない名前を同時に含む入力（先に受け付けられなかった項目が示される。契約の例 `invalidBeforeNotFound`）
- **尽きている根拠**: 契約の `updateAccount` の 1 件目の INVALID_INPUT の `when` が挙げる領域は、本文が JSON でない／名前の形／役割の形／`grants` の学びが登録簿に無い、の 4 つで 1 クラスずつ。「そのアカウントの項目も権限も変えず」は、妥当な項目が混ざる求めで初めて観測できるので 1 クラスを足す。先後は、後ろに置かれた NOT_FOUND と同時に成り立つ入力 1 つで確かめる。
- **境界の扱い**: 名前は 0 文字と 51 文字が外側の境界（通る側は REQ-165）。役割は enum の外の値 1 つで尽きる（中は REQ-166）。
- **検証しない**: 呼び出した本人の降格（契約では同じ INVALID_INPUT だが NOT_FOUND より後の 2 件目の entry で、REQ-167 が持つ。OQ-121）。断りの文面（R-102）。
- **参照先**: `tests/portal/repay_UC-011_manage_accounts.test.ts` の describe「REQ-178 更新の入力検証」（全クラス）。本番相当の経路は system suite の `scripts/check_portal_api.py::check_admin_validation`（まなびばに実際に HTTP で当てる検査。`@covers` の対象外）。
