# UC-011 アカウントを作り、学びの権限とパスワードを付け替え、削除する

## 概要

管理者が、アカウントと権限の正本であるまなびばで、アカウントの一覧を見ながら、アカウントを作り、
名前・役割・学びの権限を付け替え、パスワードを再設定し、要らなくなったアカウントを削除するまでを
1 回で終える。以下の「システム」はまなびば（ACT-04）を指す。

## 事前条件

- 管理者がまなびばにログインしている（役割が管理者）
- 権限に使える学びが、学びの登録簿に載っている
- 更新・パスワードの再設定・削除の相手のアカウントは既にあり、その相手が別の端末でログイン中のこともある
- 適用される業務規則: BR-001, BR-002, BR-004, BR-005, BR-006, BR-007, BR-008, BR-039

## 主シナリオ

1. 管理者が管理の画面を開く
2. システムが全アカウントの名前・メール・役割・作成時刻と、それぞれに付いている学びの権限を、作成順に出す
3. 管理者がメール・名前・初期パスワード・開ける学びを入れてアカウントを作る
4. システムがアカウントと権限を作り、役割を利用者にして、一覧に加える
5. 管理者が相手の名前・役割・開ける学びを送って更新する
6. システムが送られた値を反映し、権限を送られた一覧に置き換える
7. 管理者が相手のパスワードを再設定する
8. システムがパスワードを入れ替え、その相手が開いているログインをすべて切る
9. 管理者がアカウントを削除する
10. システムがアカウントとその権限を消し、一覧から外す

### REQ-162

- pattern: Event-driven
- status: active

> 管理者が管理の画面を開いたとき、システムは、すべてのアカウントの名前・メールアドレス・役割・作成時刻と、それぞれに付いている学びの権限を、作成順に示す。

#### 検証方針

- **分割クラス**:
  - `#all-accounts-in-creation-order` — 役割の違うアカウントが複数ある状態で一覧を求める入力（全件の名前・メールアドレス・役割・作成時刻が作成時刻の昇順で出る）
  - `#grants-per-account` — 権限の付いている行と付いていない行が混ざる状態の入力（行ごとに権限のある学びが学びの key の昇順で出て、権限の無い行は空）
  - `#only-self` — 呼び出した管理者自身だけがある状態の入力（自分の行が 1 件だけ出る。表の「呼び出した管理者自身」の行）
  - `#screen-shows-all-columns` — 管理の画面の表が、行ごとに名前・メールアドレス・役割・作成時刻・権限を出している状態（一覧の応答だけでなく画面で観測する）
- **尽きている根拠**: `listAccounts` は request を持たないので、入力空間はまなびばのアカウントの状態だけ。表の「ある」3 行は行の役割と呼び出した本人かどうかだけが違い、一覧はどの行も同じに返すので役割の混ざった代表の入力 1 つで尽きる。残る自由度は行ごとの権限の有無と、自分 1 件だけという最小の状態。文の「示す」は一覧の応答（契約の `listAccounts`）と管理の画面の 2 か所で観測が分かれるので、画面の側を 1 クラス足す。表の「存在しない」の行は `不可`。
- **境界の扱い**: アカウントが 0 件の状態は起こらない（事前条件で管理者がログインしているので自分の行が必ずある）ため、`#only-self` が最小の境界。
- **検証しない**: セッションが無い呼び出し（BR-001。UC.md の事前条件の外）。役割が利用者の呼び出し（REQ-176）。作成時刻と id の値そのもの（まなびばの DB が決める。R-102）。画面での作成時刻の書式（見た目）。

### REQ-163

- pattern: Event-driven
- br: BR-039
- status: active

> 管理者が、まだアカウントの無いメールアドレスと、名前・初期パスワード・開ける学びを入れてアカウントの作成を求めたとき、システムは、役割を利用者としたアカウントと指定された学びの権限を作り、一覧に加える。

#### 検証方針

- **分割クラス**:
  - `#create-with-grants` — まだアカウントの無いメールアドレスと名前・初期パスワード・開ける学びを入れた入力（役割が利用者のアカウントと指定の学びの権限ができ、一覧に加わる）
  - `#create-without-grants` — 開ける学びを省いた入力（権限の無いアカウントができ、一覧の権限は空）
  - `#create-normalized-email` — メールアドレスの前後に空白があり大文字を含む入力（畳んだ値で保存され、一覧にもその値で出る）
  - `#role-not-taken-from-request` — 作成の求めに管理者の役割を添えた入力（契約の `createAccount` の request に役割は無く、できるアカウントの役割は利用者）
- **尽きている根拠**: 契約の `createAccount` の request で成功の入力が変えられるのは、必須の 3 項目に `grants` を送るか省くかの 2 通りだけ。request に無い役割を添えても役割が利用者のままであることを、役割を添えた入力 1 つで見る。メールアドレスは畳んでから保存すると契約が決めているので、畳む前と後で値が違う入力が 1 クラス。「一覧に加える」は作成の直後に `listAccounts` で読める形で各クラスが観測する。
- **境界の扱い**: 名前 1〜50 文字・初期パスワード 8〜200 文字の内側は代表値 1 つ（外側は REQ-177）。`grants` を 1 件送る場合と複数送る場合は同じクラスの代表値。
- **検証しない**: パスワードの記録の形（BR-039。クラスは REQ-290 が持つ）。同じメールアドレスで同時に作ったときにどちらが通るか（UC.md の並行性の行が `?`。一意性は BR-008 がまなびばの DB の一意制約で持つ）。

### REQ-164

- pattern: Unwanted behaviour
- br: BR-008
- status: active

> 既にアカウントがあるメールアドレスで作成を求められた場合、システムは、アカウントも権限も作らず、そのメールアドレスが登録済みであることを示す。

#### 検証方針

- **分割クラス**:
  - `#duplicate-email` — 既にアカウントがあるメールアドレスと同じ値で作成を求める入力（アカウントが増えず、登録済みであることが示される）
  - `#duplicate-email-after-folding` — 既存のメールアドレスと、契約の畳み（前後の空白・大文字小文字）を経て一致する値での入力（同じく作られない）
  - `#no-grants-on-conflict` — 既にあるメールアドレスに開ける学びを添えた入力（権限も作られず、既存のアカウントの権限も変わらない）
- **尽きている根拠**: 「既にアカウントがあるメールアドレス」は、送られた値がそのまま既存と一致する場合と、畳んでから一致する場合で尽きる。「アカウントも権限も作らず」の観測は、アカウントが増えないことと権限が作られないことの 2 面で、後者は `grants` を添えた入力でしか観測できないので別クラス。
- **検証しない**: 同時に作ったときにどちらが通るか（UC.md の並行性の行が `?`。BR-008 は DB の一意制約として C13 が見る）。形も満たさないうえに重複している入力（契約の errors の順で先に出るのは INVALID_INPUT。REQ-177 の `#invalid-before-conflict` が持つ）。断りの文面（R-102。契約が決めるのは CONFLICT のコードだけ）。

### REQ-165

- pattern: Event-driven
- status: active

> 管理者が、あるアカウントについて名前・役割・開ける学びのうち一部だけを送って更新を求めたとき、システムは、送られた項目だけを反映し（権限は送られた学びの一覧に置き換える）、送られなかった項目は変えない。

#### 検証方針

- **分割クラス**:
  - `#name-only` — 名前だけを送る入力（役割と権限は変わらない）
  - `#role-only` — 役割だけを送る入力（名前と権限は変わらない）
  - `#grants-replaced` — 開ける学びの一覧だけを送る入力（権限がその一覧に置き換わる＝足す側と外す側が同時に起こる）
  - `#grants-emptied` — 空の学びの一覧を送る入力（権限が全て外れ、名前と役割は変わらない）
  - `#all-fields` — 名前・役割・開ける学びをまとめて送る入力（3 つが同時に反映される。契約の例 `ok`）
  - `#no-field` — どの項目も送らない入力（何も変わらずに受け付けられる。OQ-115）
  - `#self-without-role` — 呼び出した管理者自身に、役割を含めず名前と開ける学びを送る入力（表の「呼び出した管理者自身」の行。断られずに反映される）
- **尽きている根拠**: 契約の `updateAccount` の request で送れる任意の項目は名前・役割・`grants` の 3 つなので、送る項目の部分集合は 8 通り。「送られた項目だけを反映し、送られなかった項目は変えない」は、単独で送る 3 通り・全部送る 1 通り・何も送らない 1 通りで尽き、2 項目の組は単独の重ね合わせと同値。`grants` は置き換えなので足す／外すは同じクラスの代表値で、全部外す空の一覧だけが別の境界。相手が自分自身かどうかは表の行を分けるので、役割を含めない自分自身への更新を 1 クラス（役割を含む場合は REQ-167）。
- **境界の扱い**: 名前は 1 文字と 50 文字、`grants` は 0 件と複数件が内側の境界（外側は REQ-178）。
- **検証しない**: 同じ学びが 2 回以上含まれる一覧（REQ-169）。存在しない相手（REQ-173）。同じ相手を同時に更新したときの勝ち負け（UC.md の並行性の行が `?`）。

### REQ-166

- pattern: Event-driven
- status: active

> 管理者が他人のアカウントの役割を送って更新を求めたとき、システムは、利用者から管理者への向きと管理者から利用者への向きのどちらでも、その役割を送られたとおりに変える。

#### 検証方針

- **分割クラス**:
  - `#promote-to-admin` — 他人の利用者に管理者の役割を送る入力（その相手が管理者になる）
  - `#demote-other-admin` — 他人の管理者に利用者の役割を送る入力（その相手が利用者になる）
  - `#same-role-unchanged` — 他人に今と同じ役割を送る入力（断られず、役割はその値のまま）
- **尽きている根拠**: 役割は契約の enum の 2 値なので、他人への更新で起こりうる遷移は 2 つの向きと同値の 3 通りで尽きる（同値は 2 通りあるが観測は同じで、同じクラスの代表値）。
- **検証しない**: 自分自身の降格（REQ-167）。降格の結果まなびばの管理者が 0 人になる場合（REQ-404）。enum の外の役割（REQ-178）。

### REQ-167

- pattern: Unwanted behaviour
- br: BR-006
- status: active

> 管理者が自分自身の役割を利用者に変えるよう求めた場合、システムは、役割も同じ求めに含まれる他の項目も変えず、自分の管理者の役割は外せないことを示す。

#### 検証方針

- **分割クラス**:
  - `#self-demotion-rejected` — 呼び出した本人の id に利用者の役割を送る入力（役割は管理者のまま残り、外せないことが示される）
  - `#self-demotion-keeps-other-fields` — 同じ求めに名前や開ける学びも含めた入力（名前も権限も変わらない。契約の例 `selfDemotion`）
  - `#self-role-admin-passes` — 呼び出した本人の id に管理者の役割を送る入力（断られない）
- **尽きている根拠**: 自分自身への更新で役割が問われるのは、送る役割が enum の 2 値のどちらかだけ。利用者は断られ、同じ求めに乗った他の項目も変わらず、管理者は断られない、の 3 つで尽きる。
- **境界の扱い**: `#self-role-admin-passes` が断る領域の境界（自分自身への更新そのものは禁じられておらず、通る側は REQ-165 の `#self-without-role`）。契約の errors では自分自身の降格は NOT_FOUND より後の 2 件目の INVALID_INPUT（OQ-121）だが、自分自身の id は必ず在るので両方の条件を満たす入力は作れず、先後を確かめるクラスは置けない。
- **検証しない**: 他人の降格（REQ-166）。管理者どうしが互いを降格する場合（REQ-404）。

### REQ-168

- pattern: Event-driven
- br: BR-007, BR-039
- status: active

> 管理者が他人のパスワードの再設定を求めたとき、システムは、そのアカウントのパスワードを送られた値に入れ替え、そのアカウントで開いているすべてのセッションを終わらせる。

#### 検証方針

- **分割クラス**:
  - `#password-replaced` — 他人のパスワードを送られた値に入れ替える入力（その相手は新しいパスワードで入れ、古いパスワードでは入れない）
  - `#sessions-terminated` — 相手が複数の端末でセッションを開いている状態での入力（そのアカウントのセッションが残らない。BR-007）
  - `#other-accounts-sessions-kept` — 他のアカウント（呼び出した管理者自身を含む）がセッションを開いている状態での入力（そのセッションは残る。BR-007 の射程の境界）
- **尽きている根拠**: 契約の `resetAccountPassword` の request は相手の id と新しいパスワードだけで、成功の入力の自由度はパスワードの値（内側は代表値 1 つ）だけ。観測は、入れ替わったことと、BR-007 が決めるセッションの扱い（相手のセッションが終わること・射程の外のセッションが残ること）の 3 つで尽きる。
- **境界の扱い**: パスワードは 8 文字と 200 文字が内側の境界（外側は REQ-179）。相手のセッションは複数件が「すべて終わらせる」を見る代表値で、0 件は `#password-replaced` の代表値。
- **検証しない**: 呼び出した管理者自身へのパスワードの再設定（REQ-403）。パスワードの記録の形（BR-039。クラスは REQ-290 が持つ）。

### REQ-169

- pattern: Event-driven
- status: active

> 権限として同じ学びが 2 回以上含まれる学びの一覧を受け取ったとき、システムは、その学びの権限を 1 つだけ付ける。

#### 検証方針

- **分割クラス**:
  - `#duplicate-on-create` — 同じ学びが 2 回以上含まれる一覧で作成を求める入力（その学びの権限が 1 つだけ付く）
  - `#duplicate-on-update` — 同じ学びが 2 回以上含まれる一覧で更新を求める入力（その学びの権限が 1 つだけ残る）
  - `#same-key-only` — 同じ学びだけが並ぶ一覧の入力（権限が 1 件に畳まれる）
- **尽きている根拠**: 学びの一覧を受け取る経路は契約の `createAccount` と `updateAccount` の 2 つで、どちらも「重複した key は 1 つに畳む」と書かれているので経路ごとに 1 クラス。1 つの一覧の形は「重複と他の学びが混ざる」「同じ学びだけが並ぶ」の 2 つで尽き、後者が畳んだ結果が 1 件になる境界。
- **境界の扱い**: 同じ学びが 3 回以上並ぶ場合は `#same-key-only` の代表値（2 回と 3 回以上で観測は変わらない）。
- **検証しない**: 重複と登録簿に無い学びが同時に含まれる入力（契約の errors の順で先に出るのは INVALID_INPUT。REQ-177・REQ-178 が持つ）。畳んだあとの並び（契約が学びの key の昇順と決める。R-102）。

### REQ-170

- pattern: Event-driven
- status: active

> 管理者が自分以外のアカウントの削除を求めたとき、システムは、そのアカウントとそのアカウントの学びの権限を消し、そのアカウントで開いているセッションも残さず、一覧から外す。

#### 検証方針

- **分割クラス**:
  - `#delete-other-member` — 自分以外の利用者のアカウントの削除の入力（アカウントが消え、一覧から外れる。表の「ある（他人・利用者）」の行）
  - `#delete-other-admin` — 自分以外の管理者のアカウントの削除の入力（利用者と同じに消える。表の「ある（他人・管理者）」の行）

- pattern: Unwanted behaviour
- status: active

> アカウントの作成・更新・パスワードの再設定・削除の書き込みの途中でまなびばのデータの保存に失敗した場合、システムは、その求めの書き込みを 1 つも残さない。

#### 検証方針

- **分割クラス**:
  - `#create-failure-leaves-nothing` — 権限つきのアカウントの作成の途中で、どれか 1 つの書き込みが保存に失敗する入力（アカウントも権限も残らない）
  - `#update-failure-leaves-nothing` — 名前・役割・権限をまとめて送る更新の途中で、どれか 1 つの書き込みが失敗する入力（どの項目も権限も変わらない）
  - `#reset-failure-leaves-nothing` — ログイン中の相手のパスワードの再設定の途中で、どれか 1 つの書き込みが失敗する入力（パスワードは入れ替わらず、相手のセッションも残る）
  - `#delete-failure-leaves-nothing` — 権限があり、ログイン中の相手の削除の途中で、どれか 1 つの書き込みが失敗する入力（アカウントも権限もセッションも残る）
- **尽きている根拠**: 文が挙げる書き込みの操作は作成・更新・再設定・削除の 4 つで、操作ごとに書き込む表の組が違う（アカウントと権限／アカウントと権限／アカウントとセッション／アカウントと権限とセッション）ので 4 クラス。各操作は、書き込む表が最も多い入力（権限・セッションのある相手、全項目の更新）を代表に取る。「途中」は、その求めが出す書き込みの文の何番目で失敗するかを 1 番目から書き込みが尽きるまで全部動かして尽くす（値の変種なのでクラスを割らない）。
- **境界の扱い**: 失敗は D1 の口で書き込みの文（INSERT・UPDATE・DELETE・REPLACE）を投げさせて作る。batch は 1 つの単位として扱い、その中の書き込みのどれかで失敗させるとその batch 全体が失敗する。読みの失敗は書き込みを残しようがないので入力に取らない。
- **検証しない**: 失敗の応答の形（BR-002。全経路の最終段は UC-017 の REQ-258）。成功を返さないことだけを見る。

### REQ-661

- pattern: Event-driven
- status: active

> 管理者が管理の画面から学びの権限の保存・他人のパスワードの再設定・他人のアカウントの削除を行い、その操作（削除では、続く一覧の読み直しまで）が済んだとき、システムは、管理の画面に、その操作が済んだことを示す。

#### 検証方針

- **分割クラス**:
  - `#grants-saved-shown` — 管理の画面で行の学びの印を付け替えて保存が済むと、画面に済んだことが出る（同じ操作が断られたときに出る文とは違う文）
  - `#password-reset-shown` — 管理の画面で他人のパスワードの再設定が済むと、画面に済んだことが出る（同じ操作が断られたときに出る文とは違う文）
  - `#deleted-shown` — 管理の画面で他人の削除を確かめて済み、一覧の読み直しも済むと、画面に済んだことが出る
  - `#delete-reload-failed` — 削除は済んだが続く一覧の読み直しに失敗すると、済んだことは出ず、読み直しの失敗の理由が出る
- **尽きている根拠**: 文が挙げる画面の操作は 3 つで、操作ごとに 1 クラス。削除は続く読み直しの成否で 2 つに分けた
- **検証しない**: 出る文の言い回し（何を伝えるかまでを決める）。アカウントの作成（済んだことは作成の欄の近くに出る。REQ-163 の画面の側）。再設定のパスワードの入力や削除の確かめを取り消したとき（画面は何も求めない）

### REQ-662

- pattern: Unwanted behaviour
- status: active

> 管理の画面からの学びの権限の保存が断られるか届かなかった場合、システムは、管理の画面に断りの理由を示し、その学びの印を操作の前の状態に戻す。

#### 検証方針

- **分割クラス**:
  - `#grant-check-refused` — 印を付けた保存が断られると、画面に断りの理由が出て、その印が外れた状態に戻る
  - `#grant-check-unreachable` — 印を付けた保存が届かないと、画面に届かなかったことが出て、その印が外れた状態に戻る
  - `#grant-uncheck-refused` — 印を外した保存が断られると、画面に断りの理由が出て、その印が付いた状態に戻る
  - `#grant-uncheck-unreachable` — 印を外した保存が届かないと、画面に届かなかったことが出て、その印が付いた状態に戻る
- **尽きている根拠**: 印の向き（付ける・外す）の 2 つと、保存の結果（断られる・届かない）の 2 つの組で尽きる。断りの種類ごとの理由の文は API の側（REQ-176・REQ-178 など）が決める
- **検証しない**: 理由の文の言い回し。パスワードの再設定と削除が断られたときの画面（理由を示すことは各要件の「示す」が決め、画面の側のクラスは各要件に足す）
