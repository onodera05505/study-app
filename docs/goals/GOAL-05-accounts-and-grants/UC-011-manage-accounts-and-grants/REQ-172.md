# REQ-172

> 管理者が自分自身のアカウントの削除を求めた場合、システムは、そのアカウントも権限も消さず、自分は削除できないことを示す。

## 検証方針

- **分割クラス**:
  - `#self-delete-rejected` — 呼び出した本人の id を指す削除の入力（アカウントも権限も残り、自分は削除できないことが示される。契約の例 `selfDelete`）
- **尽きている根拠**: 契約の `deleteAccount` の request は id だけで、「自分自身」は呼び出した本人の id と一致するか否かの 2 値。一致しない側は REQ-170 が持つので、この要件の入力空間は 1 クラス。アカウントが残ることと権限が残ることは同じ入力の観測なので分けない（R-1105）。
- **境界の扱い**: 一致しない id が通ることが断る領域の境界（REQ-170 の `#delete-other-member`）。契約の errors では INVALID_INPUT が NOT_FOUND より先だが、自分自身の id は必ず在るので両方の条件を満たす入力は作れず、先後を確かめるクラスは置けない。
- **検証しない**: 管理者が 1 人のときと複数のときの違い（どちらでも断られ、0 人になる場合を分けて決めた文は上流に無い。BR-006）。
- **参照先**: 単体テストは無い（`tests/portal/` にこの UC のテストが無く、宣言した全クラスが未検証）。本番相当の経路は system suite の `scripts/check_portal_api.py::check_admin_self_guard`（まなびばに実際に HTTP で当てる検査。`@covers` の対象外）。
