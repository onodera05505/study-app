# REQ-179

> パスワードの再設定の求めに、受け付けられないパスワードが含まれていた場合、システムは、パスワードを入れ替えず、どのセッションも終わらせず、受け付けられなかった項目を示す。

## 検証方針

- **分割クラス**:
  - `#short-password` — パスワードが 8 文字未満の入力（契約の例 `shortPassword`）
  - `#long-password` — パスワードが 200 文字を超える入力
  - `#missing-password` — パスワードが欠けている入力
  - `#malformed-body` — 本文が JSON でない入力
  - `#sessions-kept-on-invalid` — 相手がセッションを開いている状態で、受け付けられないパスワードを送る入力（パスワードも相手のセッションも変わらない）
  - `#invalid-before-not-found` — 存在しない id と、形を満たさないパスワードを同時に含む入力（先に受け付けられなかった項目が示される。契約の例 `invalidBeforeNotFound`）
- **尽きている根拠**: 契約の `resetAccountPassword` の INVALID_INPUT の `when` が挙げる領域は、本文が JSON でない／パスワードが短い／長い（必須の欠落を含む）で、長さの外側は上下 2 クラス、欠落を 1 クラス。「どのセッションも終わらせず」は相手がセッションを開いている状態でだけ観測できるので 1 クラスを足す。先後は、後ろに置かれた NOT_FOUND と同時に成り立つ入力 1 つで確かめる。
- **境界の扱い**: 7 文字と 201 文字が外側の境界で、8 文字と 200 文字は通る側（REQ-168）。
- **検証しない**: パスワードの文字種と強さ（契約が決めるのは長さだけ。R-102）。
- **参照先**: 単体テストは無い（`tests/portal/` にこの UC のテストが無く、宣言した全クラスが未検証）。本番相当の経路は system suite の `scripts/check_portal_api.py::check_admin_validation`（まなびばに実際に HTTP で当てる検査。`@covers` の対象外）。
