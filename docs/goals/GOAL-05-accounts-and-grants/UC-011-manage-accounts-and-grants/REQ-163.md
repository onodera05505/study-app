# REQ-163

> 管理者が、まだアカウントの無いメールアドレスと、名前・初期パスワード・開ける学びを入れてアカウントの作成を求めたとき、システムは、役割を利用者としたアカウントと指定された学びの権限を作り、一覧に加える。

## 検証方針

- **分割クラス**:
  - `#create-with-grants` — まだアカウントの無いメールアドレスと名前・初期パスワード・開ける学びを入れた入力（役割が利用者のアカウントと指定の学びの権限ができ、一覧に加わる）
  - `#create-without-grants` — 開ける学びを省いた入力（権限の無いアカウントができ、一覧の権限は空）
  - `#create-normalized-email` — メールアドレスの前後に空白があり大文字を含む入力（畳んだ値で保存され、一覧にもその値で出る）
- **尽きている根拠**: 契約の `createAccount` の request で成功の入力が変えられるのは、必須の 3 項目に `grants` を送るか省くかの 2 通りだけ（`role` はこの要件の外。下記）。メールアドレスは畳んでから保存すると契約が決めているので、畳む前と後で値が違う入力が 1 クラス。「一覧に加える」は作成の直後に `listAccounts` で読める形で各クラスが観測する。
- **境界の扱い**: 名前 1〜50 文字・初期パスワード 8〜200 文字の内側は代表値 1 つ（外側は REQ-177）。`grants` を 1 件送る場合と複数送る場合は同じクラスの代表値。
- **検証しない**: 作成の求めに `role` を送った場合（契約の `createAccount` は `role` を受けるが、この要件は役割を利用者と決めており、送られた役割の扱いを決めた文が上流に無い。要件の欠けとして報告）。同じメールアドレスで同時に作ったときにどちらが通るか（UC.md の並行性の行が `?`。一意性は BR-008 がまなびばの DB の一意制約で持つ）。
- **参照先**: 単体テストは無い（`tests/portal/` にこの UC のテストが無く、宣言した全クラスが未検証）。本番相当の経路は system suite の `scripts/check_portal_api.py::check_admin_accounts`（まなびばに実際に HTTP で当てる検査。`@covers` の対象外）。
