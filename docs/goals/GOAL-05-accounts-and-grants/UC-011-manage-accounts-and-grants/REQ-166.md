# REQ-166

> 管理者が他人のアカウントの役割を送って更新を求めたとき、システムは、利用者から管理者への向きと管理者から利用者への向きのどちらでも、その役割を送られたとおりに変える。

## 検証方針

- **分割クラス**:
  - `#promote-to-admin` — 他人の利用者に管理者の役割を送る入力（その相手が管理者になる）
  - `#demote-other-admin` — 他人の管理者に利用者の役割を送る入力（その相手が利用者になる）
  - `#same-role-unchanged` — 他人に今と同じ役割を送る入力（断られず、役割はその値のまま）
- **尽きている根拠**: 役割は契約の enum の 2 値なので、他人への更新で起こりうる遷移は 2 つの向きと同値の 3 通りで尽きる（同値は 2 通りあるが観測は同じで、同じクラスの代表値）。
- **検証しない**: 自分自身の降格（REQ-167）。降格の結果まなびばの管理者が 0 人になる場合（BR-006。`enforced_at` が未決で、止めるか通すかを決めた文が上流に無い。UC.md の並行性の行も `?`）。enum の外の役割（REQ-178）。
- **参照先**: `tests/portal/repay_UC-011_manage_accounts.test.ts` の describe「REQ-166 他人の役割」（全クラス）。本番相当の経路は system suite の `scripts/check_portal_api.py::check_admin_accounts`（まなびばに実際に HTTP で当てる検査。`@covers` の対象外）。
