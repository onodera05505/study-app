# REQ-170

> 管理者が自分以外のアカウントの削除を求めたとき、システムは、そのアカウントとそのアカウントの学びの権限を消し、そのアカウントで開いているセッションも残さず、一覧から外す。

## 検証方針

- **分割クラス**:
  - `#delete-other-member` — 自分以外の利用者のアカウントの削除の入力（アカウントが消え、一覧から外れる。表の「ある（他人・利用者）」の行）
  - `#delete-other-admin` — 自分以外の管理者のアカウントの削除の入力（利用者と同じに消える。表の「ある（他人・管理者）」の行）
  - `#grants-removed` — 権限の付いた相手の削除の入力（そのアカウントの学びの権限も残らない）
  - `#sessions-removed` — 相手が別の端末でセッションを開いている状態での削除の入力（そのセッションも残らない）
- **尽きている根拠**: 契約の `deleteAccount` の request は相手の id だけなので、入力の自由度は相手の状態＝役割（表の 2 行）・権限が付いているか・セッションを開いているかの 3 軸。役割が 2 クラス、消える物の 2 軸が 1 クラスずつで尽きる。
- **境界の扱い**: 権限 0 件・セッション 0 件の相手は `#delete-other-member` の代表値（消す物が無くても断られない）。
- **検証しない**: 自分自身の削除（REQ-172）。存在しない相手（REQ-175）。学び側の配備に残る記録（REQ-171）。削除で管理者が 0 人になる場合（2 人の管理者の求めが重なったときだけ起こりうる。REQ-404）。
- **参照先**: `tests/portal/repay_UC-011_manage_accounts.test.ts` の describe「REQ-170 他人の削除」（全クラス）。本番相当の経路は system suite の `scripts/check_portal_api.py::check_admin_accounts`（まなびばに実際に HTTP で当てる検査。`@covers` の対象外）。
