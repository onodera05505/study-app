# REQ-177

> 作成の求めに、受け付けられないメールアドレス・名前・初期パスワードのいずれか、または学びの登録簿に無い学びが含まれていた場合、システムは、アカウントも権限も作らず、受け付けられなかった項目を示す。

## 検証方針

- **分割クラス**:
  - `#bad-email` — メールアドレスが契約の形を満たさない入力（契約の例 `badEmail`）
  - `#missing-required` — メールアドレス・名前・初期パスワードのいずれかが欠けている入力
  - `#bad-name` — 名前が空、または 50 文字を超える入力
  - `#bad-password` — 初期パスワードが 8 文字未満、または 200 文字を超える入力
  - `#unknown-learning` — 開ける学びに、学びの登録簿に無い key が含まれる入力（BR-004。契約の例 `unknownLearning`）
  - `#malformed-body` — 本文が JSON でない入力
  - `#invalid-before-conflict` — 既にあるメールアドレスと、形を満たさない初期パスワードを同時に含む入力（先に受け付けられなかった項目が示される。契約の例 `invalidBeforeConflict`）
- **尽きている根拠**: 契約の `createAccount` の INVALID_INPUT の `when` が挙げる領域は、本文が JSON でない／必須の欠落／メールアドレス・名前・初期パスワードの形／`grants` の学びが登録簿に無い、の 4 つで、形は項目ごとに 1 クラス。先後は、後ろに置かれた CONFLICT と同時に成り立つ入力 1 つで確かめる。「アカウントも権限も作らず」は各クラスで一覧が増えないことを見る（UC.md の失敗時の事後条件）。
- **境界の扱い**: 名前は 0 文字と 51 文字（前後の空白を落としてから数えるので、空白だけの名前は 0 文字の側）、初期パスワードは 7 文字と 201 文字が外側の境界。通る側（1・50・8・200）は REQ-163 が持つ。長さと形の値の正本は契約とまなびばの検証スキーマ（R-102）。
- **検証しない**: 作成の求めに添えられた役割（契約の `createAccount` の request に役割は無く、添えても断らずに利用者で作る。REQ-163 の `#role-not-taken-from-request`）。断りの文がどの項目を指すかの文面（R-102）。
- **参照先**: `tests/portal/repay_UC-011_manage_accounts.test.ts` の describe「REQ-177 作成の入力検証」（全クラス）。本番相当の経路は system suite の `scripts/check_portal_api.py::check_admin_validation`（まなびばに実際に HTTP で当てる検査。`@covers` の対象外）。
