# UC-034 学び側とまなびばの経路と作り手と運用の道具を入口の一覧に出し、契約と突き合わせられるようにする

## 概要

運用者が入口の一覧を出し、システムが学び側とまなびばの app に登録された経路と、道具の置き場の道具を 1 行に 1 件ずつ並べることで、契約に無い入口と入口の無い契約の操作を機械で見つけられるようにする（ADR-0014）。

## 事前条件

- 手元の作業環境に、配信しようとする版のソースと、道具の置き場がそろっている（名前の表 `scripts/entry_names.json` は、ファイル名と違う名前の道具があるときに置く）

## 主シナリオ

1. 運用者が、入口の一覧を出す
2. システムが、学び側とまなびばの app を読み込み、登録された経路を、どの method にも立つ中継ぎの登録を除いて経路の入口として並べる
3. システムが、道具の置き場の直下のソースのファイルと名前の表から、道具の入口を並べる
4. システムが、同じ入口を 1 つにまとめ、1 行に 1 件ずつ出す
5. 運用者が、出た一覧を契約との突き合わせに渡す

## 事後条件

- 成功時: 運用者が、学び側とまなびばの経路と道具の置き場の道具が 1 行に 1 件ずつ、重なりなく並んだ一覧を見ており、契約との突き合わせに渡せる
- 失敗時: 入口は 1 件も出ておらず、断った理由が示されている

## 要件

### REQ-585

- pattern: Event-driven
- status: active

> 運用者が入口の一覧を出すとき、システムは学び側とまなびばの app に登録された経路を、どの method にも立つ中継ぎの登録を除いて、method と、パラメーターを `{名前}` と書いた path で、1 行に 1 件ずつ経路の入口として出す。

#### 検証方針

- **分割クラス**:
  - `#contract-routes-listed` — 今のリポジトリで、確定した契約の受ける側の http の操作の method と path が、どれも経路の入口の行として出る
  - `#both-apps-routes` — 学び側とまなびばの両方の app の登録が、それぞれ経路の入口として出る
  - `#method-per-registration` — 同じ path に method の違う登録があれば、method ごとに 1 行ずつ出る
  - `#params-in-braces` — パラメーターを持つ path は、パラメーターを `{名前}` と書いて出る（パラメーターが 1 つ・2 つ）
  - `#param-pattern-dropped` — 正規表現つきのパラメーター（正規表現の中に `{` `}` を含む物を含む）は、正規表現を除いて `{名前}` と書いて出る
  - `#middleware-excluded` — どの method にも立つ中継ぎの登録（全部の path・一部の path に掛ける物）は、行として出ない
  - `#load-output-not-in-list` — app の読み込みの途中で標準出力に何か書かれても、一覧の行に混ざらない（一覧は 1 行に 1 件の入口だけ）
- **尽きている根拠**: 文の振る舞いは、どの app の登録か（学び側・まなびば）、登録ごとの行の数（method の違い）、path の書き方（パラメーターの有無）、出さない登録（中継ぎ）の 4 つの軸に尽き、軸ごとに 1 つ置く。今のリポジトリの全経路は、契約の wire を正本に 1 つで見る
- **境界の扱い**: 行は `kind`・`method`・`path` だけを持つ（一覧の形）。中継ぎかどうかは、どの method にも立つ登録かで分ける（ADR-0014）
- **検証しない**: どの method にも立つ、中継ぎでない処理の登録（ADR-0014 は出さないとし、一覧の形の README は method ごとに出すとしていて、決まっていない）。契約に無い app の経路が出ること（契約に無い入口の検出は `harness lint entries` の役目）

### REQ-586

- pattern: Event-driven
- status: active

> 運用者が入口の一覧を出すとき、システムは道具の置き場の直下のソースのファイル（設定がソースとする拡張子のファイル）を、名前の表に挙げていなければファイル名から拡張子を除いて camelCase にした名前で、名前の表に挙げたファイル（直下でないファイルを含む）は表が挙げた名前だけで、1 行に 1 件ずつ道具の入口として出す。

#### 検証方針

- **分割クラス**:
  - `#tools-listed` — 今のリポジトリで、道具の置き場の直下のソースのファイルは、名前の表に挙げていなければファイル名から導いた名前で、表に挙げたファイルは表の名前で、どれも道具の入口として出る
  - `#file-name-camel-case` — 直下のソースのファイルは、拡張子を除き `_` と `-` の区切りを camelCase にした名前で出る（拡張子の違うソースのファイルを含む）
  - `#non-source-files-not-listed` — 直下のソースでないファイル（データ・名前の表自身）と、表に挙げていない直下でないファイルは出ない
  - `#table-names-only` — 表に挙げた直下のファイルは、表の名前だけ（複数なら全部）で出て、ファイル名から導いた名前では出ない
  - `#table-nested-file` — 表に挙げた直下でないファイルは、表の名前で出る
  - `#table-key-other-spelling` — 表の鍵が同じファイルを別の書き方の相対パス（`./` で始まる・`..` を含む）で指しても、そのファイルは表の名前だけで出る
  - `#no-table-file-names` — 名前の表が無いときは、直下のソースのファイルが全部ファイル名から導いた名前で出る
- **尽きている根拠**: 文の振る舞いは、ファイルが入口になるか（直下のソースか・表に挙げたか）と、名前の出どころ（ファイル名・表）の組に尽きる。入口になるファイルは、表に無い直下・表にある直下・表にある直下でないの 3 つ、ならないファイルはソースでない直下と表に無い直下でないの 2 つ。表が無いときは UC の表の行が導いた場合として 1 つ置く。今のリポジトリの全道具は 1 つで見る
- **境界の扱い**: 名前の表の鍵は、道具の置き場（`scripts/`）からの相対パス（ADR-0014）。書き方が違っても同じファイルを指す鍵は、そのファイルを挙げたと読む
- **検証しない**: 表に挙げた名前の並びが空の場合（表の形に入るかを文が決めていない）。名前が数字で始まるファイル（camelCase の作り方を文が決めていない）

### REQ-587

- pattern: Ubiquitous
- status: active

> システムは、入口の一覧に同じ入口（経路は method と path の組、道具は名前）を 2 回以上出さない。

#### 検証方針

- **分割クラス**:
  - `#real-no-duplicates` — 今のリポジトリの一覧に、同じ経路（method と path）も同じ道具の名前も 2 回出ない
  - `#same-route-registered-twice` — 1 つの app に同じ method と path の登録が 2 つあっても、1 行だけ出る
  - `#same-route-in-both-apps` — 学び側とまなびばの app に同じ method と path の登録があっても、1 行だけ出る
  - `#files-same-name` — 拡張子だけが違う 2 つのファイル、区切りの書き方だけが違う 2 つのファイルが同じ名前になっても、1 行だけ出る
  - `#table-name-equals-file-name` — 表の名前が、表に無いほかのファイルから導いた名前と同じでも、1 行だけ出る
- **尽きている根拠**: 同じ入口は、経路では登録の重なり（1 つの app の中・2 つの app の間）、道具では名前の重なり（ファイル名どうし・表とファイル名）からだけ生じる。今のリポジトリの一覧全体を 1 つで見る
- **検証しない**: 経路の入口と道具の入口の間の重なり（kind が違うので同じ入口でない）

### REQ-588

- pattern: Unwanted behaviour
- status: active

> 運用者が入口の一覧を出すときに、名前の表が JSON として読めないか表の形でないとき、または表に挙げたファイルが無いとき、システムは入口を 1 件も出さずに断る。

#### 検証方針

- **分割クラス**:
  - `#table-not-json` — 名前の表が JSON として読めないと、INVALID_INPUT で断り、入口を 1 件も出さない
  - `#table-not-shape` — 名前の表が JSON として読めても表の形でない（最上位が配列・名前の並びが配列でない・名前が文字列でない）と、INVALID_INPUT で断り、入口を 1 件も出さない
  - `#listed-file-missing` — 名前の表に挙げたファイルが無い（直下・直下でない）と、NOT_FOUND で断り、入口を 1 件も出さない
  - `#shape-before-missing-file` — 表の形でなく、無いファイルも挙げていると、INVALID_INPUT で断る（契約の errors の順）
- **尽きている根拠**: 文の条件は、表が読めない（JSON でない・形でない）と、挙げたファイルが無いの 3 つに尽き、1 つずつ置く。契約の errors の隣の項目とは、両方が成り立つ入力で先の項目が勝つことを 1 つで見る
- **境界の扱い**: 表の形は、ファイル（道具の置き場からの相対パス）から名前の並び（文字列の配列）への対応（ADR-0014）
- **検証しない**: 名前の並びが空の配列・名前が空の文字列（表の形に入るかを文が決めていない）

### REQ-589

- pattern: Unwanted behaviour
- status: active

> 運用者が入口の一覧を出すときに、学び側かまなびばの app を読み込めないとき、システムは入口を 1 件も出さずに断る。

#### 検証方針

- **分割クラス**:
  - `#learning-app-unloadable` — 学び側の app を読み込めないと、INTERNAL で断り、入口を 1 件も出さない
  - `#portal-app-unloadable` — まなびばの app を読み込めないと、INTERNAL で断り、入口を 1 件も出さない
  - `#missing-file-before-app-unloadable` — 名前の表に挙げたファイルが無く、app も読み込めないと、NOT_FOUND で断る（契約の errors の順）
- **尽きている根拠**: 文の条件は 2 つの app のどちらかを読み込めないことに尽き、app ごとに 1 つ置く。契約の errors の隣の項目（表に挙げたファイルが無い）とは、両方が成り立つ入力で先の項目が勝つことを 1 つで見る
- **境界の扱い**: 読み込めないは、読み込むと例外を投げる app で作る
- **検証しない**: 読み込めても既定の書き出しが app でない場合（文の「読み込めない」に入るかを決めていない）
