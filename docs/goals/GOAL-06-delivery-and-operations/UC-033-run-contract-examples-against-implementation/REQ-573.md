# REQ-573

> 学び側とまなびばは、要求を断るどの応答にも、利用者に示す理由の文とは別に、その断りの種類の名前を 1 つ持たせる。

## 検証方針

- **分割クラス**:
  - `#operation-refusal` — 各経路の契約の errors に当たる断り（JSON の本文で断る物）で、応答が持つ名前がその条件の名前
  - `#same-status-different-name` — 状態の番号が同じで種類が違う断り（見つからない断りと、まなびばの場所が無い配備の設定が無い断り）で、応答が持つ名前が違う
  - `#common-refusal` — どの経路にも同じ形で立つ断り（ADR-0011。本人と分からない・受け持たない経路・決められた形を満たさない本文・想定していない失敗・設定が無い）で、応答が持つ名前が受け口の要件の当てた名前
  - `#non-json-refusal` — JSON の本文を持たない断り（まなびばの入口の平文の断りと、ログイン画面や一覧へ戻す断り）で、応答から名前が読める
  - `#portal` — まなびばの断りで、応答が持つ名前がその条件の名前
  - `#unchanged-screen` — 名前を持たせても、画面が利用者に示す理由の文が変わらない
- **尽きている根拠**: 断りは、経路ごとの断りとどの経路にも立つ断りの 2 つ、本文が JSON か否かの 2 つ、配備が学び側かまなびばかの 2 つで分かれ、状態の番号だけでは見分けられない所をクラス 2 が押さえる。
  入力は、http の契約が使う名前を学び側（UNAUTHENTICATED・INVALID_INPUT・NOT_FOUND・CONFLICT・RATE_LIMITED・NOT_CONFIGURED・UPSTREAM_UNAVAILABLE・FORBIDDEN・INTERNAL）とまなびば（INVALID_INPUT・UNAUTHENTICATED・FORBIDDEN・NOT_FOUND・CONFLICT）のそれぞれで 1 つ以上の契約の失敗例が尽くすように選ぶ（全部の失敗例を名前で照らすのは契約の実例の確かめの役目）。
- **検証しない**: 理由の文言（実装が正本）。名前の一覧そのもの（`docs/_shared/components.yaml` の `errorCodes` が正本）。
