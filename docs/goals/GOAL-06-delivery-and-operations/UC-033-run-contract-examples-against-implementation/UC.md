# UC-033 確定した契約の実例を実装に当て、契約どおりに応えない版を見つける

## 概要

運用者が契約の実例の確かめを回し、システムが確定した契約の実例をすべて手元で実装に渡して、成功例は応答の形を、失敗例は実装が出した断りの種類の名前を例と照らすことで、配信する版が契約どおりに応え契約どおりに断ることを機械で確かめる。

## 事前条件

- 手元の作業環境に、配信しようとする版のソースと確定した契約がそろっている
- 適用される業務規則: BR-064

## 主シナリオ

1. 運用者が、契約の実例の確かめを回す
2. システムが、確定した契約の、自分の持ち物の操作の実例を 1 件ずつ、その実例が前提とする状態を手元に用意してから実装に渡す
3. 実装が、成功例には応答を返し、失敗例には断りの種類の名前を出して断る → BR-064
4. システムが、成功例では実装の応答が例の応答を含むことを、失敗例では実装が出した名前が例の名前と同じことを確かめる
5. 運用者が、すべての実例が合ったことを見る

## 事後条件

- 成功時: 運用者が、確定した契約の自分の持ち物の操作の実例がすべて合ったことを見ており、配信する版の実装が契約どおりの形で応え、契約どおりの名前で断ることが確かめられている。本番の保存先・配備先・外の相手には何も送られていない
- 失敗時: 合わなかった実例と渡せなかった実例が挙げられて失敗で終わっており、本番の保存先・配備先・外の相手には何も送られていない

## 要件

### REQ-567

- pattern: Event-driven
- br: BR-064
- status: active

> 運用者が契約の実例の確かめを回すとき、システムは確定した契約の自分の持ち物の操作の実例をすべて実装に渡し、成功例では実装の応答が例の応答を含み、失敗例では実装が例と同じ断りの種類の名前で断ったときだけ、通ったことを示して終える。

#### 検証方針

- **分割クラス**:
  - `#success-shape` — 成功例を渡し、実装の応答が例の応答を含む（応答の余分な欄は含むことを妨げない）
  - `#failure-name` — 失敗例を渡し、実装が例と同じ名前で断る
  - `#all-examples` — 確定した契約の自分の持ち物の操作の実例の全件が渡され、全件が合ったときだけ通ったことを示す（下書きの契約と、他者の形を写した操作の実例は渡さない）
- **尽きている根拠**: 実例は成功例と失敗例の 2 つに尽き、通る条件はそれぞれの照らし方（含む・同じ名前）だけ。合わない側は REQ-568 が持つ。
- **検証しない**: 応答の中身の意味（各操作の要件のテストが持つ）。どの経路にも同じ形で立つ断り（ADR-0011。契約の実例に無いので、受け口の要件のテストが持つ）。

### REQ-568

- pattern: Unwanted behaviour
- br: BR-064
- status: active

> 契約の実例の確かめで、実装の応えが例と合わない実例、応答も断りの名前も持たない実例、または実装に渡せない実例が 1 件でもあれば、システムはその実例を挙げて失敗で終える。

#### 検証方針

- **分割クラス**:
  - `#success-mismatch` — 成功例に、実装が例の応答を含まない応答を返すか、断る（名前を出さずに止まる・断るのも断り。例の応答が終了の状態や状態の番号だけでも合わない）
  - `#failure-mismatch` — 失敗例に、実装が応答を返すか、例と違う名前で断る
  - `#failure-unnamed` — 失敗例に、実装が名前を出さずに断る（道具が終了の状態だけで止まる・HTTP の状態の番号だけで断る）
  - `#malformed-example` — 応答も断りの名前も持たない実例がある
  - `#unreachable` — 当たる入口が無い実例か、実装が応えない実例がある（回さずに通す実例は無い）
- **尽きている根拠**: 合わない形は、成功例の取り違え・失敗例の取り違え・名前の欠け・例そのものの不備・渡せないの 5 つに尽きる。1 件でもあれば失敗で終えることは、各クラスで合う実例と混ぜて見る。
- **検証しない**: 失敗を示す文の文言。

### REQ-569

- pattern: Unwanted behaviour
- status: active

> 契約の実例が本番の保存先・配備先・外の相手に触れる操作の物であっても、システムは契約の実例の確かめの中でそれらに何も送らない。

#### 検証方針

- **分割クラス**:
  - `#production-store` — 本番の保存先を読み書きする操作の実例（投入を流す手続きの seedRemote、投入後の突き合わせの verifySeedRemote）を回しても、本番の保存先に要求も書き込みも届かない
  - `#deploy-target` — 配備先に触れる操作の実例（配備先から秘密の名前の一覧を取る listDeploymentSecretNames。他者の形を写した操作なので、写しの操作も回すと指定したときだけ回る）を回しても、配備先に何も届かない
  - `#external-party` — 外の相手を呼ぶ操作の実例（本番の検査が配備を外から叩く checkDeploymentHealth・readDeploymentHealthHeaders・openDeploymentEntry・probeRetiredPasswordRoute、学び側からまなびばへ交換を求める signInWithCode、版の印を取りに行く fetchVersionStamp）を回しても、外の相手に何も届かない
- **尽きている根拠**: 手元の外にあるものは、本番の保存先・配備先・外の相手の 3 つに尽きる。
- **検証しない**: 手元に用意した代わりの相手の作り（実装の手段）。

### REQ-570

- pattern: Ubiquitous
- status: active

> システムは、契約の実例の確かめで、各実例をその実例が前提とする状態を用意してから回し、ほかの実例を回したかどうかと回した順によって、その実例の結果を変えない。

#### 検証方針

- **分割クラス**:
  - `#same-request-different-premise` — 同じ入力で成功例と失敗例が並ぶ操作（前提の状態だけが違う。例の名前と契約の `when` で見分ける）で、どちらも例どおりに応える
  - `#order-independent` — 実例を 1 件だけ回したときと、ほかの実例のあとに回したとき、順を入れ替えたときで結果が同じ
  - `#premise-identity` — 本人や権限を前提とする実例で、その実例が前提とする本人と権限が用意されている
- **尽きている根拠**: 実例の結果を変えうるのは、その実例が前提とする状態と、ほかの実例が残した状態の 2 つ。前者は前提の用意（クラス 1・3）、後者は回し方の違い（クラス 2）で尽きる。
- **検証しない**: 前提の状態の用意の作り（実装の手段）。

### REQ-571

- pattern: Unwanted behaviour
- br: BR-064
- status: active

> 作り手と運用者が手元で回す道具が、入口の引数か読み書きするファイルについて、道具を回す自分の持ち物の操作の契約の errors に当たって止まるとき、道具は標準出力に断りの種類の名前と理由を 1 つずつ持つ形を出し、0 でない終了の状態で終える。

#### 検証方針

- **分割クラス**:
  - `#entry-refusal` — 道具の入口の引数で断る入力（契約の `direction: inbound` の操作の errors）で、標準出力の名前がその条件の名前
  - `#file-refusal` — 道具が読むファイルについて道具を回す操作の errors に当たる入力（読むファイルが無い・読めない・形が合わない。読み書きの操作 1 つの失敗の名前は REQ-579）で、標準出力の名前がその条件の名前
  - `#same-exit-different-name` — 終了の状態が同じで種類が 2 つ以上ある操作で、種類ごとに違う名前が出る
- **尽きている根拠**: 道具の断りは、入口の引数に当たる物と、読み書きするファイルに当たる物の 2 つに尽きる。終了の状態だけでは見分けられない操作を 3 つ目のクラスで押さえる。
- **検証しない**: 理由の文言（実装が正本）。門が止める理由を挙げて止まるとき（契約の errors に当たる断りではなく、門の結果の応答）。

### REQ-572

- pattern: Unwanted behaviour
- br: BR-064
- status: active

> 画面の端末の記憶の操作のうち、契約が端末の記憶に書けない・読めないことを断りに挙げる操作は、端末の記憶に書けないか読めないとき、その操作を呼んだ側に断りの種類の名前を持つ失敗を渡す。

#### 検証方針

- **分割クラス**:
  - `#write-blocked` — 端末の記憶に書けない入力で、書く操作（消すことを含む）が呼んだ側に名前を持つ失敗を渡す
  - `#read-blocked` — 端末の記憶が読めない入力で、読む操作が呼んだ側に名前を持つ失敗を渡す
  - `#broken-value-not-refusal` — 端末の記憶は読めるが覚えた値が契約の形に合わない入力で、読む操作は失敗を渡さず、覚えていないときと同じ応答を返す
- **尽きている根拠**: 端末の記憶の失敗は、書けない・読めないの 2 つに尽きる（消すことは書くことに含め、読んでから書く操作は先に当たった側）。読めた値が形に合わないことは記憶の失敗ではなく、覚えていない側に畳むので、名前を渡さないことをクラス 3 で押さえる。
- **検証しない**: 名前を受けた画面の見た目と動き（各 UC の要件のまま変えない。REQ-078・REQ-242・REQ-153 などのテストが持ち、トークンを保存できないときの画面は REQ-574 が持つ）。契約の `errors` が空の端末の記憶の操作（読めない・書けないときも契約の応答の形で返し、失敗を渡さない。この文の射程の外）。

### REQ-573

- pattern: Ubiquitous
- br: BR-064
- status: active

> 学び側とまなびばは、要求を断るどの応答にも、利用者に示す理由の文とは別に、その断りの種類の名前を 1 つ持たせる。

#### 検証方針

- **分割クラス**:
  - `#operation-refusal` — 各経路の契約の errors に当たる断り（JSON の本文で断る物）で、応答が持つ名前がその条件の名前
  - `#same-status-different-name` — 状態の番号が同じで種類が違う断り（見つからない断りと、まなびばの場所が無い配備の設定が無い断り）で、応答が持つ名前が違う
  - `#common-refusal` — どの経路にも同じ形で立つ断り（ADR-0011。本人と分からない・受け持たない経路・決められた形を満たさない本文・想定していない失敗・設定が無い）で、応答が持つ名前が受け口の要件の当てた名前
  - `#non-json-refusal` — JSON の本文を持たない断り（まなびばの入口の平文の断りと、ログイン画面や一覧へ戻す断り）で、応答から名前が読める
  - `#portal` — まなびばの断りで、応答が持つ名前がその条件の名前
  - `#unchanged-screen` — 名前を持たせても、画面が利用者に示す理由の文が変わらない
- **尽きている根拠**: 断りは、経路ごとの断りとどの経路にも立つ断りの 2 つ、本文が JSON か否かの 2 つ、配備が学び側かまなびばかの 2 つで分かれ、状態の番号だけでは見分けられない所をクラス 2 が押さえる。
  入力は、http の契約が使う名前を学び側（UNAUTHENTICATED・INVALID_INPUT・NOT_FOUND・CONFLICT・RATE_LIMITED・NOT_CONFIGURED・UPSTREAM_UNAVAILABLE・FORBIDDEN・INTERNAL）とまなびば（INVALID_INPUT・UNAUTHENTICATED・FORBIDDEN・NOT_FOUND・CONFLICT）のそれぞれで 1 つ以上の契約の失敗例が尽くすように選ぶ（全部の失敗例を名前で照らすのは契約の実例の確かめの役目）。
- **検証しない**: 理由の文言（実装が正本）。名前の一覧そのもの（`docs/_shared/components.yaml` の `errorCodes` が正本）。

### REQ-579

- pattern: Unwanted behaviour
- br: BR-064
- status: active

> 作り手と運用者の道具が置き場のファイルを読み書きする操作は、呼ばれて契約の errors に当たるとき、その操作を呼んだ側に断りの種類の名前を持つ失敗を渡す。

#### 検証方針

- **分割クラス**:
  - `#read-missing` — 読む操作に、読むファイルが無い入力で、名前がその条件の名前（NOT_FOUND）の失敗を渡す
  - `#read-unreadable` — 読む操作に、ファイルが形として読めない入力で、名前がその条件の名前（INVALID_INPUT）の失敗を渡す
  - `#write-refused` — 書く操作に、書き出せない・既にある・描けない入力で、名前がその条件の名前（STORAGE_UNAVAILABLE・CONFLICT・INTERNAL）の失敗を渡す
  - `#success-no-failure` — 契約の errors に当たらない入力では、失敗を渡さず契約の response の形の値を返す
- **尽きている根拠**: 読み書きの操作の失敗は、読む側の「無い」「読めない」と、書く側の「書けない・既にある・描けない」に尽きる。errors に当たらない側を 4 つ目のクラスで押さえる（名前を持つ失敗を何にでも渡す実装と見分ける）。
- **検証しない**: 名前を受けた道具の扱い（道具を回したときの動きと人が見る出力は各 UC の要件のまま。道具を回す操作の断りは REQ-571）。契約の `errors` が空の読み書きの操作（失敗を渡さない。この文の射程の外）。理由の文言（実装が正本）。
