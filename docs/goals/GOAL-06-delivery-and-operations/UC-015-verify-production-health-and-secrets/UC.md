# UC-015 配信した本番が生きていることと秘密がそろっていることを機械で確かめる

## 概要

運用者が、配信のあとに本番の検査を 1 回回して、まなびばと各学びが外から生きていること・入口の画面が開けること・
配備ごとの秘密の名前がそろっていることを、値を読まずに確かめ、足りない配備と項目の名前を受け取る。

## 事前条件

- まなびばと各学びが本番に配備され、それぞれ配備ごとのデータの保存先に結びついている
- 運用者が、配備の権限を持つアカウントで配備先にログインしている
- 学びの一覧（名前・種類・値）が登録簿にある
- 適用される業務規則: BR-001, BR-005, BR-009, BR-033, BR-064

## 主シナリオ

1. 運用者が本番の検査を回す
2. 本番の検査が、まなびばと各学びの死活確認を認証なしで叩き、生きている応答を受け取り、その応答に定められたセキュリティヘッダが載っていることを確かめる
3. 本番の検査が、まなびばと各学びの入口の画面を外から開き、開けることを確かめ、各学びの学び側のパスワードでのログインと登録の経路が閉じていることを状態を変えずに確かめる
4. 本番の検査が、配備ごとの秘密の名前の一覧を取り、必要な名前がそろっていることを確かめる（値は読まない・出さない）
5. 本番の検査が、見た配備と項目、および足りなかった配備と項目を運用者に返す
6. 運用者が、足りないものが無いことを見て配信を終える

## 要件

### REQ-213

- pattern: Event-driven
- status: active

> 本番の検査が、まなびばと各学びの死活確認を認証なしで叩いたとき、まなびばと、与えられた学びの key が登録簿にある学び側の配備は、生きていることを示す応答を返す。

#### 検証方針

- **分割クラス**:
  - `#portal-alive` — まなびばの配備の死活確認を認証を添えずに叩いたとき、生きている印の応答が返る
  - `#learning-alive` — 学びの配備の死活確認を同じく認証なしで叩いたとき、生きている印の応答が返る
  - `#every-deployment-visited` — 叩く配備の集合が登録簿の配備と一致し、1 つも抜けない（BR-005。配備を足して叩き先を足し忘れると落ちる）
- **尽きている根拠**: `checkDeploymentHealth` の入力は配備の key だけで、key はまなびばの配備か学びの配備のどちらかに尽きる。認証を添えないことは全クラスに共通の前提。叩く先が 1 つ抜ける失敗は key ごとのクラスには映らないので、集合の一致を別のクラスに立てる。
- **境界の扱い**: 生きている判定の根拠は応答の本文（契約の `Ok`）に取り、状態コードだけで生きているとはしない。本文が印でない側は REQ-217 の `#body-not-alive-mark`。学びの key が与えられていない・登録簿に無い学び側の配備の死活確認は UC-017 の REQ-354 が持ち（生きていることを示さずに断る）、この文の入力に取らない。本番の検査ではその配備は REQ-217 で挙げられる側に落ちる。
- **検証しない**: 認証を添えて叩いたとき（この要件の射程外。認証の要る応答の側は REQ-223）。配信が進行中にどちらの版が応えたか（UC の表で `?`。コードに分岐が無い）。

### REQ-214

- pattern: Event-driven
- status: active

> 本番の検査が、まなびばと各学びの入口の画面を認証なしで外から開いたとき、それぞれの配備は画面を表示できる応答を返す。

#### 検証方針

- **分割クラス**:
  - `#portal-entry-opens` — まなびばの入口の画面を成す公開の経路を認証なしで外から開いたとき、表示できる応答が返る
  - `#learning-entry-opens` — 学びの入口の画面を成す公開の経路を同じく開いたとき、表示できる応答が返る
  - `#every-entry-path-visited` — 配備ごとに開く経路の集合が、`openDeploymentEntry` の成功の例が配備ごとに挙げる経路の集合と等しい（抜けも余りも無い）
- **尽きている根拠**: `openDeploymentEntry` の入力は配備の key と `/` で始まる経路の 2 つ。key はまなびばか学びに尽き、経路は「入口の画面を成す公開の経路」の有限の一覧に尽きる（一覧の外の経路は開ける対象でない）。開く先が抜ける失敗は key ごとのクラスに映らないので、集合の一致を別に立てる。
- **境界の扱い**: 入口の画面を成す経路の一覧の正本は `openDeploymentEntry` の `path` の enum と成功の例（まなびばは enum の全部、学びは `/`）で、`/style.css` はまなびばの入口に数える。観測するのは状態コードだけ（入口は静的ファイルで本文に形が無い）。表示できる応答とそれ以外の隣接は REQ-218 側で取る。
- **検証しない**: 画面の中身（文言・DOM）。この要件は「開けること」だけを決め、画面として読めるかは各画面の要件が受け持つ。認証の要る経路（REQ-223）。

### REQ-215

- pattern: Event-driven
- br: BR-009
- status: active

> 本番の検査が配備ごとの秘密の名前の一覧を確かめるとき、必要な名前がそろっているかだけを判定し、秘密の値は読まず結果にも出さない。

#### 検証方針

- **分割クラス**:
  - `#names-complete` — 必要な名前がすべて一覧にある配備を「そろっている」と判定する
  - `#names-only` — 判定の入力が名前の集合だけで、秘密の値を取る呼び出しをしない（契約の応答に値が無い）
  - `#value-absent-from-result` — 検査の結果のどこにも秘密の値が現れない
  - `#empty-list` — 一覧が空の配備でも、値を読まずに名前の判定だけで足りない側に落ちる
  - `#required-names-from-one-place` — 配備ごとに必要な名前の集合が 1 か所から来る（配備を足して名前の定義を足し忘れると落ちる）
  - `#version-independent` — 配信が進行中で新旧どちらの版が応えているか定まらないときも判定が変わらない（名前は配備に付き、配信物に付かない）
- **尽きている根拠**: 入力は配備の key と、その配備から返る名前の集合の 2 つ。名前の集合は必要な名前に対して（すべてある）（一部無い）（空）に尽き、ここは（すべてある）と（空）を受け持ち、一部無い側は REQ-221。値を読まないことは呼び出しの側（`#names-only`）と出力の側（`#value-absent-from-result`）の 2 面があり、片方だけでは漏れが残る。
- **境界の扱い**: 必要な名前の数 n に対し、欠け 0 件（`#names-complete`）と n 件（`#empty-list`）を両端に取る。欠け 1 件は REQ-221 の `#one-name-missing`。
- **検証しない**: 秘密の値そのものの正しさ（値の正本は配信先の secret で、名前の一覧からは観測できない。BR-009）。一覧が取れないとき（REQ-222）。

### REQ-216

- pattern: Event-driven
- status: active

> 本番の検査が結果を返すとき、見たすべての配備と項目に足りない物が無ければ、全体が通ったことを、見た配備ごとの項目の名前とともに運用者に返す。

#### 検証方針

- **分割クラス**:
  - `#all-pass-overall-pass` — 見たすべての配備と項目に足りない物が無いとき、全体が通ったことを運用者への出力と終了状態で返す
  - `#seen-items-listed` — 結果に、見た配備ごとに見た項目が契約の operation の名前で現れ、その集合が検査の叩いた operation の集合と等しい（学び側の死活確認と入口の経路を含む）
- **尽きている根拠**: 結果を返す入口の入力は「見た配備と項目」と「足りなかった物」の 2 つで、足りなかった物が 0 件のときだけがこの要件（1 件以上は REQ-220）。0 件のときに観測できるのは（全体が通ったこと）と（何を見たか）の 2 つに尽きる。
- **境界の扱い**: 足りない物 0 件（この要件）と 1 件（REQ-220 の `#one-problem-overall-fail`）が隣接の境界で、対で取る。
- **境界の扱い**: 項目の名前は、この UC の operation（`checkDeploymentHealth`・`openDeploymentEntry`・`probeRetiredPasswordRoute`・`listDeploymentSecretNames`）と、借りる UC-013 の `getAuthConfig` の名前（どれも契約の語彙）。学び側のパスワードでのログインと登録の確かめは、どちらも `probeRetiredPasswordRoute` の名前で現れる。
- **検証しない**: 項目の名前以外の出力の文言と並び（運用者が読む形で、契約の語彙に無い。OQ-119）。

### REQ-217

- pattern: Unwanted behaviour
- status: active

> 配備の死活確認が返らないか期待と違う応答であるとき、本番の検査はどの配備の死活確認が通らなかったかを問題として挙げる。

#### 検証方針

- **分割クラス**:
  - `#no-answer` — 配備に届かず死活確認が返らないとき、その配備を問題として挙げる
  - `#body-not-alive-mark` — 応答は届くが本文が生きている印でないとき、同じく問題として挙げる
  - `#only-failing-deployment-named` — 複数の配備のうち一部だけが通らないとき、問題に挙がるのはその配備の key だけで、通った配備は挙がらない
- **尽きている根拠**: 死活確認が通らない入力は（応答が得られない）（応答は得られるが本文が印でない）の 2 つに尽き、契約はこの 2 つを 1 つの `UPSTREAM_UNAVAILABLE` にまとめる。残るのは「どの配備か」が結果に正しく付くかで、通った配備と通らない配備が混じる入力で取る。
- **境界の扱い**: 本文が印でない側は、状態コードが成功で本文だけが違う入力を取る（状態コードだけを見る検査では通ってしまう点。OQ-64 がその欠陥を記録している）。
- **検証しない**: 届かない理由の区別（契約が両者を区別しないと決めている）。配信が進行中に新旧どちらの版が応えたか（UC の表で `?`。コードに分岐が無い）。

### REQ-218

- pattern: Unwanted behaviour
- status: active

> 配備の入口の画面が外から開けないとき、本番の検査はどの配備のどの経路が開けなかったかを問題として挙げる。

#### 検証方針

- **分割クラス**:
  - `#path-not-openable` — 入口の画面を成す経路が表示できる応答を返さないとき、問題として挙げる
  - `#deployment-unreachable` — 配備に届かず状態コードが得られないときも、同じく問題として挙げる
  - `#deployment-and-path-named` — 問題に、配備の key とその経路の両方が入る（どちらが欠けても運用者が直す先を決められない）
- **尽きている根拠**: 開けない入力は（状態コードが得られるが表示できる応答でない）（状態コードが得られない）の 2 つに尽きる。残るのは問題の指し先で、1 つの配備の複数の経路のうち一部だけが開けない入力で取る。
- **境界の扱い**: 表示できる応答とそれ以外の隣接を取り、開ける側は REQ-214 の `#portal-entry-opens`・`#learning-entry-opens`。
- **検証しない**: 開けなかった理由の分類（契約は 1 つの `UPSTREAM_UNAVAILABLE` にまとめる）。

### REQ-219

- pattern: Ubiquitous
- status: active

> 本番の検査は、ある配備や項目で問題を見つけても打ち切らず、残りの配備と項目をすべて見てから結果を返す。

#### 検証方針

- **分割クラス**:
  - `#continue-after-dead-deployment` — 先に見た配備の死活確認が通らなくても、後続の配備を見る
  - `#continue-across-items` — 1 つの配備で死活確認が通らなくても、その配備の入口の画面と秘密の名前の項目を続けて見る
  - `#all-problems-reported` — 問題が 2 つ以上あるとき、結果にそのすべてが挙がる（最初の 1 つで止まらない）
- **尽きている根拠**: 打ち切りが起こりうる継ぎ目は（配備と配備のあいだ）（1 つの配備の項目と項目のあいだ）の 2 つに尽き、どちらも見た数で観測できる。見た数が足りていても結果に出ない漏れが別にありうるので、挙がった問題の数を 3 つ目のクラスに立てる。
- **境界の扱い**: 問題の出る配備を一覧の先頭と末尾の両方に置いた入力を取る（先頭でだけ打ち切る実装は末尾の入力では気づけない）。
- **検証しない**: 見る順序そのもの（どの順でも結果が同じことを見るので、順序は要件でない）。問題の文の中身（REQ-217・REQ-218・REQ-221・REQ-222 が受け持つ）。

### REQ-220

- pattern: Event-driven
- status: active

> 本番の検査が結果を返すとき、見た配備と項目に問題が 1 つ以上あれば、全体を失敗として返す。

#### 検証方針

- **分割クラス**:
  - `#one-problem-overall-fail` — 問題が 1 つだけでも全体を失敗として返す
  - `#problems-listed` — 失敗の結果に、足りなかった配備と項目の名前がすべて挙がる
  - `#fail-from-any-item-kind` — 死活確認・入口の画面・秘密の名前のどの項目の問題でも、等しく全体が失敗になる
  - `#no-state-change` — 失敗を返しても本番の状態が何も変わっていない（検査は読むだけ）
- **尽きている根拠**: 入力は「問題の件数」と「問題の種類」の 2 軸。件数は 0 件（REQ-216）と 1 件以上に尽き、1 件以上の側をこの要件が受け持つ。種類は UC の表の 3 つの項目に尽き、どれでも結果が同じなのでまとめて 1 クラス。失敗時の事後条件（部分適用なし）は件数と独立なので別に立てる。
- **境界の扱い**: 0 件と 1 件の隣接。0 件の側は REQ-216 の `#all-pass-overall-pass`。
- **検証しない**: 出力の文言と並び（OQ-119）。問題の挙げ方の中身（REQ-217・REQ-218・REQ-221・REQ-222）。

### REQ-221

- pattern: Unwanted behaviour
- br: BR-009
- status: active

> 配備に必要な秘密の名前が一覧に無いとき、本番の検査はどの配備のどの秘密の名前が無いかを、秘密の値を出さずに問題として挙げる。

#### 検証方針

- **分割クラス**:
  - `#one-name-missing` — 必要な名前のうち 1 つだけが一覧に無い配備を、その名前を挙げて問題にする
  - `#all-names-missing` — その配備の必要な名前が一覧に 1 つも無いとき、必要な名前のすべてが挙がる
  - `#deployment-and-name-named` — 問題に、配備の key と欠けている秘密の名前の両方が入る
  - `#no-value-in-problem` — 欠けている名前を挙げるとき、その配備にある他の秘密の値を出さない
  - `#extra-names-ignored` — 必要な名前に無い名前が一覧に余分にあっても問題にしない（判定は必要な名前がそろっているかだけ）
- **尽きている根拠**: 入力は「必要な名前の集合」と「配備から返った名前の集合」の差で、差は（欠け 1 件）（欠けが全件）（余分がある）の 3 つに尽きる（欠け 0 件は REQ-215 の `#names-complete`）。残る 2 つは問題の形で、指し先（配備と名前）と値を出さないことを別に取る。
- **境界の扱い**: 必要な名前の数 n に対し、欠け 1 件と n 件を両端に取る。
- **検証しない**: 名前が一覧にあることとその値が正しいこと（値は読まないと決まっている。BR-009）。一覧そのものが取れないとき（REQ-222）。

### REQ-222

- pattern: Unwanted behaviour
- status: active

> 配備の秘密の名前の一覧を取れないとき、本番の検査はどの配備で取れなかったかを、ログイン中のアカウントのどれもその配備を持たないのか、一覧の取得そのものが失敗したのかを区別して問題として挙げ、その配備の秘密の名前がそろっているとは判定しない。

#### 検証方針

- **分割クラス**:
  - `#forbidden-wrong-account` — ログイン中の配備先のアカウントがその配備を持つアカウントと違うとき、その配備と理由を問題として挙げる
  - `#list-unavailable` — 一覧の取得そのものが失敗するとき（配備先に届かない・プロジェクトが見つからない）、その配備と理由を問題として挙げる
  - `#account-unknown-not-forbidden` — ログインしていない、またはログイン中のアカウントが分からないとき、アカウント違い（`FORBIDDEN`）に挙げず、取得の失敗（`UPSTREAM_UNAVAILABLE`）の側に挙げる
  - `#any-logged-in-account-owns` — 複数のアカウントにログインしていて、そのうち 1 つがその配備を持つとき、アカウント違いに挙げず一覧を取りに行く
  - `#forbidden-precedes-unavailable` — 別のアカウントでログインしていて取得も失敗しうる入力で、挙がる理由は `FORBIDDEN` の側（契約の `errors` の並びが評価の順。R-1207）
  - `#not-judged-complete` — 一覧が取れなかった配備を「必要な名前がそろっている」とは判定しない（通った扱いに倒さない）
- **尽きている根拠**: 契約の `listDeploymentSecretNames` の失敗は `FORBIDDEN` と `UPSTREAM_UNAVAILABLE` の 2 件で、各 1 クラスと隣接する 2 件の先後に 1 クラスを取り、`FORBIDDEN` の境目（ログイン中のアカウントが 0 個・分からない／複数で 1 つが持ち主）に 2 クラスを取ると失敗の入力空間が尽きる（名前が返る側は REQ-215・REQ-221）。残る 1 つは、取れなかったことが判定に跳ね返る側。
- **境界の扱い**: 2 つの理由の区別は、一覧の取得を試みたか（アカウント違いでは試みない）として出力と偽の wrangler の呼び出しの記録で観測する。
- **検証しない**: 取れなかった理由の文言（運用者が読む形で、契約の語彙に無い。OQ-119）。

### REQ-223

- pattern: Unwanted behaviour
- br: BR-001
- status: active

> 本番の検査が、認証を要する応答を認証なしで叩いたとき、まなびばと各学びはその応答を返さず断る。

#### 検証方針

- **分割クラス**:
  - `#learning-protected-refused` — 学び側の認証を要する応答を認証なしで叩くと、応答を返さず断られる
  - `#portal-protected-refused` — まなびばの認証を要する応答を認証なしで叩くと、同じく断られる
  - `#refusal-shape-same` — 断りの形がまなびばと学び側で同じ（BR-001）
  - `#public-set-is-closed` — 認証なしで通るのは死活確認と学びの一覧だけで、それ以外の経路は 1 つも通らない（通る経路の集合が 1 か所から来て、片側に足し忘れると落ちる）
  - `#no-change-on-refusal` — 断られた要求の変更がどこにも残らない
- **尽きている根拠**: 入力は「叩く先の配備」×「その応答が認証を要するか」の 2 軸。配備はまなびばと学びに尽き、認証を要するかは 2 値で、要さない側の集合が閉じていることを `#public-set-is-closed` で押さえると残りはすべて要する側になる。断りには（応答を返さない）（形が同じ）（変更が残らない）の 3 面があり、別々に観測する。
- **境界の扱い**: 認証を要する／要さないの隣接は、公開の経路の集合そのもので取る。認証の情報の形（無い・壊れている・別の秘密・期限切れ）の区別は各 UC の operation の `UNAUTHENTICATED` が持ち、ここでは「添えない」だけを取る。
- **検証しない**: 断りの本文が内部の状態を明かさないこと（BR-002 の射程）。認証の形の応答（UC-013 の `getAuthConfig`）。学び側のパスワードでのログインと登録の経路が閉じていること（REQ-350。叩く形はこの UC の `probeRetiredPasswordRoute`）。

### REQ-350

- pattern: Unwanted behaviour
- status: active

> 本番の検査が各学びの学び側のパスワードでのログインと登録の経路を状態を変えない要求で叩き、その配備が経路を受け持たないことに当たる断りを返さなかったとき、本番の検査はどの配備のどの経路が開いているかを問題として挙げる。

#### 検証方針

- **分割クラス**:
  - `#retired-routes-closed-pass` — 学び側のパスワードでのログインと登録の経路のどちらも受け持たない経路として断られる入力（問題として挙げない）
  - `#retired-route-open-raised` — どちらかの経路が受け持たない経路の断り以外を返す入力（届かないときを含む。その配備とその経路を問題として挙げる）
  - `#no-state-changing-probe` — 確かめに使う要求が、本番の状態を変えうる要求（決められた形を満たす本文を送る要求）でない
- **尽きている根拠**: 叩く経路はログインと登録の 2 つで、叩いた結果は「受け持たない経路の断りが返る」か「それ以外」の 2 つに尽き、確かめの要求そのものが状態を変えないことが REQ-220#no-state-change と同じ側の 1 面として加わる。叩く形の正本はこの UC の契約の `probeRetiredPasswordRoute`（受け持たない経路の断りそのものは UC-017 の REQ-256 が持ち、学び側がこの 2 つの経路を受け持たないことは UC-013 の REQ-204 が持つ）。
- **検証しない**: まなびばのログインと登録（まなびばの登録は UC-011 の管理者の操作で、この検査の対象外）。断りの本文の文言（OQ-119）。

### REQ-523

- pattern: Event-driven
- status: active

> 本番の検査がまなびばと各学びの死活確認の応答を確かめるとき、定められたセキュリティヘッダのうち載っていないものがあれば、その配備とヘッダの名前を問題として挙げる。

#### 検証方針

- **分割クラス**:
  - `#all-present` — まなびばと全ての学びの死活確認の応答に定められた 5 つのヘッダがそろう入力（どの配備もヘッダの問題に挙がらない。契約 `readDeploymentHealthHeaders` の `ok`）
  - `#learning-header-missing` — 学びの 1 つの死活確認の応答から一部のヘッダが欠ける入力（その学びと、欠けたヘッダの名前が全部挙がり、載っているヘッダの名前は挙がらない。契約の `headerMissing`）
  - `#portal-header-missing` — まなびばの死活確認の応答からヘッダが 1 つだけ欠ける入力（まなびばとそのヘッダの名前が挙がる）
  - `#no-answer` — 学びの 1 つの死活確認が返らずヘッダが得られない入力（その学びと、定められたヘッダの名前が全部挙がる。契約の `noAnswer`）
  - `#header-name-case-insensitive` — 5 つのヘッダはそろっているが名前の大文字・小文字が応答ごとに違う入力（載っている側として扱い、問題に挙がらない。契約はヘッダの名前を小文字にそろえて受け取る）
- **尽きている根拠**: 1 つの配備の死活確認の応答について、入力は（届いて全部そろう）（届いて一部が欠ける）（届かない）の 3 つに尽き、届いた側の名前の照合は大文字・小文字を区別しない 1 クラスを足して閉じる。配備の種類はまなびばと学びの 2 つで、欠ける側を両方で取る。定められたヘッダの名前は NFR-001 の 5 つ。
- **検証しない**: ヘッダの値の中身（要件は載っているかだけを見る。値の正しさは要件に無い）。死活確認以外の応答（静的ファイル）のヘッダ（要件は死活確認の応答だけを見る）。問題の文言と並び（運用者が読む形で契約の語彙に無い）。検査全体の終了の状態（REQ-220）と、先に問題が出ても残りを見ること（REQ-219）。

### REQ-578

- pattern: State-driven
- br: BR-064
- status: active

> 本番の検査は、挙げた問題に契約の errors に当たる物があるときだけ、人が読む問題の一覧を変えずに、標準出力の最後の行に、挙げた問題ごとの配備と項目を並べ、契約の errors に当たる問題にはその断りの種類の名前を添えた機械向けの 1 行を出す。

#### 検証方針

- **分割クラス**:
  - `#health-unreachable-named` — 死活確認が返らない配備が 1 つある入力で、最後の行にその配備の死活確認の項目が UPSTREAM_UNAVAILABLE を添えて並ぶ
  - `#each-http-item-named` — 死活確認のヘッダ・入口の画面の経路・学び側のパスワードでの経路のそれぞれが届かない入力で、その配備と項目（経路の違いを含む）に UPSTREAM_UNAVAILABLE が添う
  - `#secret-list-named` — 秘密の名前の一覧を、ログイン中のアカウントのどれもその配備を持たないため見られない入力と、一覧の取得が失敗する入力で、その配備の項目に FORBIDDEN と UPSTREAM_UNAVAILABLE がそれぞれ添う
  - `#unnamed-alongside` — 名前を持つ問題と、名前を持たない問題（足りない秘密の名前・欠けたヘッダ・閉じていない経路）が並ぶ入力で、どちらの問題も並び、名前は前者にだけ添う
  - `#human-list-unchanged` — 機械向けの行の前の出力が、同じ入力で行を足す前の出力と同じ
  - `#no-line-without-named` — 問題が無い入力と、名前を持たない問題だけの入力で、機械向けの行を出さない
- **尽きている根拠**: 問題は、名前を持つ物（契約の errors に当たる。外から叩く 4 項目の届かない・秘密の名前の一覧の 2 つの断り）と名前を持たない物（応答の値で見つけた問題）に分かれる。行を出すのは前者が 1 つ以上のときで、前者の項目ごと（クラス 1〜3）、混ざるとき（クラス 4）、出さないとき（クラス 6）で尽きる。人が読む一覧を変えないことをクラス 5 で押さえる。
- **境界の扱い**: 最後の行は、標準出力の最後の空でない行を JSON として読む。行の形と、各操作の失敗例の名前を項目から読む読み方は契約が持つ。
- **検証しない**: 理由の文言と人が読む一覧の文言（REQ-220）。全体の終了の状態（REQ-220）。
