# REQ-354

> 配備に学びの key が与えられていないか、与えられた key が登録簿に無いとき、学び側は既定の学びに倒さず、死活確認を含む受け持つ /api の経路へのどの要求にも、配備に設定が無いことに当たる形で断る。

## 検証方針

- **分割クラス**:
  - `#unknown-key-refused` — 登録簿に無い key を与えた配備の、受け持つ /api の経路への要求（どの学びとしても応えず、設定が無いことに当たる形で断る）
  - `#missing-key-refused` — key を与えていない配備の、受け持つ /api の経路への要求（同上）
  - `#health-also-refused` — そうした配備の死活確認（データの保存先が応答するかを問わず、生きていることを示す応答を返さない。本番の検査が REQ-217 で挙げられる側に落ちる）
  - `#auth-config-also-refused` — そうした配備への認証の形の問い合わせ（答える対象の学びが定まらないので、認証の形を答えずに断る）
  - `#precedes-other-refusals` — そうした配備で、認証を要する経路にトークンを添えず、本文も決められた形を満たさず、トークンの署名の秘密も無い要求（認証の断り・本文の断り・署名の秘密の不足の断りのどれでもなく、この断りが立つ）
- **尽きている根拠**: 解決できない key は「無い」と「登録簿に無い」の 2 つに尽き、断る対象が認証を要さない経路まで及ぶことを、データの保存先を引かない死活確認と、配備の設定を答える認証の形の問い合わせの 2 クラスで押さえる（認証を要する経路と要さない経路の差は、断りが key の解決より後ろに無いことでどれも同じ観測に落ちる）。同じ入力に他の断りが重なりうる軸は、UC の表 1 の添えられたもの・本文の形・署名の秘密の 3 つで、3 つが全部重なる入力を 1 クラスが取る（REQ-255・REQ-257・REQ-275・REQ-274・REQ-205・UC-015 の REQ-213 は、どれも学びの key が登録簿にある配備に射程を切っている）。受け持たない /api の経路はこの文の射程に入らない（REQ-256 が先で、key の状態を問わず見つからないことで断る）。死活確認はデータの保存先の状態を問わずこの文が先で、REQ-260 は key が登録簿にある配備だけを述べる。
- **検証しない**: 断りの本文の文言（BR-002 の射程）。key の値を配備に与える手順（配備の手続き `scripts/deploy-pages.sh` が登録簿から組む）。
- **参照先**: `tests/server/exam.test.ts::REQ-354 学びの key を解決できない配備はどの要求も断る`（断りの形は errorCodes の NOT_CONFIGURED を、REQ-275 と同じ 503 と、本文の `error` の日本語の 1 文で見る。本文の `code` の名前は REQ-573 の側）
