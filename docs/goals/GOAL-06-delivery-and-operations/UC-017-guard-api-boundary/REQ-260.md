# REQ-260

> 配備のデータの保存先が応答しない間も、まなびばと、与えられた学びの key が登録簿にある学び側の配備の死活確認は、生きていることを示す応答を返す。

## 検証方針

- **分割クラス**:
  - `#health-without-store-portal` — まなびばの保存先が例外を投げる間の死活確認
  - `#health-without-store-learning` — 学び側の保存先が配備に結びついていない間の死活確認
- **尽きている根拠**: 「応答しない」は UC の表の 1 つのセルで、原因は（壊れている）（配備に結びついていない）の 2 つ。配備も学び側とまなびばの 2 つで、2 クラスが原因と配備を 1 つずつ組んで両方の原因を覆う（死活確認が保存先を引かないことの観測は、どちらの原因でも同じ 1 点に縮む）。
- **境界の扱い**: 保存先が応答する間の死活確認は UC-015 の REQ-213 が持ち、この文は「応答しない間も」の側だけを述べる。学びの key が与えられていない・登録簿に無い学び側の配備の死活確認は REQ-354 が持ち（保存先の状態を問わず断る）、この文の入力に取らない。
- **検証しない**: 死活確認が認証を要さないこと（REQ-255 の `#public-route-not-refused` と UC-015 が持つ）。保存先が応答しないことを死活確認が知らせること — 文が「生きていることを示す」と言う通り、知らせないのが正。
- **参照先**: `tests/portal/onerror.test.ts::想定していない例外（まなびば）`、`tests/server/repay_UC-017_guard_api_boundary.test.ts::REQ-260 保存先が応答しない間の死活確認`（学び側。結びついていない・壊れている の両方）、`tests/server/db.test.ts::データの保存先（D1）が応答しない配備`（学び側。死活確認が保存先を 1 度も引かないこと）。
