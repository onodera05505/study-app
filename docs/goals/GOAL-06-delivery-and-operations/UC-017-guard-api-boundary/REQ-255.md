# REQ-255

> 認証を要する応答を求める要求に、通るトークンまたはセッションが添えられていないとき、学び側とまなびばはその応答を返さず、要求された変更も行わないまま、日本語の理由を 1 つ添えて断る。

## 検証方針

- **分割クラス**:
  - `#credential-absent` — 認証を要する経路に、トークンもセッションも添えずに届いた要求
  - `#credential-malformed` — トークンの形になっていない文字列を添えた要求
  - `#credential-wrong-secret` — 別の秘密で署名されたトークンを添えた要求
  - `#credential-expired` — 期限が過ぎたトークンまたはセッションを添えた要求
  - `#credential-revoked` — 管理者の再設定で消されたセッションを添えた要求
  - `#mutating-route-refused` — 変更を求める経路（送信・記録）も、処理に進める前に断る
  - `#portal-session-absent` — まなびば側の認証を要する経路に、セッションが無い要求（学び側と同じ形の断り）
  - `#public-route-not-refused` — 認証を要さない経路（死活確認・ログインの形）は断りの対象にしない、条件の外側の境界
  - `#precedes-body-check` — 通るものが無く、かつ本文も決められた形を満たさない要求で、本文の断りより先に認証の断りが立つ（UC の表 2 行目 2 列目。R-1207）
- **尽きている根拠**: 要求に添えられたものは（何も無い）（在るが通らない）の 2 つで、UC の表の 3 行目が「通らない」を 壊れている・別の秘密・期限切れ・管理者の再設定で消された の 4 つに割る ＝ クラス 1〜5。経路の側は（認証を要する取得）（認証を要する変更）（認証を要さない）の 3 つで、前 2 つをクラス 1〜5 と 6 が、3 つ目を境界のクラス 8 が取る。配備は学び側とまなびばの 2 つで、まなびば側をクラス 7 が取る。2 つの断りが同時に立ちうる組はクラス 9 の 1 組だけ（知らない経路は REQ-256 が、処理の途中の失敗は UC の表で 不可）。
- **境界の扱い**: 断る側と断らない側の切れ目は「その経路が認証を要するか」で、要さない経路の一覧の正本はサーバの経路の定義（BR-001・R-102）。クラス 8 が断らない側の端を取る。
- **検証しない**: 断りの文言そのもの（各 UC の契約の `errors` と実装が形の正本。R-102）。断った要求が保存先に何も残していないことの直接の観測（単体では保存先を束ねないので観測できない。本番相当の `scripts/check_api.py`・`scripts/check_portal_api.py` が見る）。トークンとセッションの作り（署名の仕方・期限の持ち方）は通る／通らないの判定の内側で、外から観測できない（R-401）。配備にトークンの署名の秘密が無いときの断りは REQ-275 が持つ（この要件は添えられたものを確かめられる配備の話）。
- **参照先**: `tests/server/protection.test.ts::認証の境界（保護された経路と公開の経路）`（経路の一覧は手書きせず、サーバが登録した経路の表から導いて全件を断言する。認証を要さない側の一覧も同じ 2 本が見るので、経路を足して公開側に入れたときはこの 2 本が赤になる）、`tests/server/app.test.ts::認証の境界`、`tests/server/feedback.test.ts::フィードバックの受け口の入力検証（UC-010）`、`tests/server/repay_UC-017_guard_api_boundary.test.ts::REQ-255 通るトークンが無い要求の断り`（学び側。別の秘密・期限切れ・本文の検査との先後）、`tests/portal/repay_UC-017_guard_api_boundary.test.ts::REQ-255 通るセッションが無い要求の断り`（まなびば。期限切れ・管理者の再設定で消されたセッション・セッションが無い要求と学び側の断りの形の一致・本文の検査との先後）。
