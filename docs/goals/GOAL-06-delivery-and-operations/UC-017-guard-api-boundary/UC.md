# UC-017 学びとまなびばの要求の受け口を一様に守る

## 概要

学び側とまなびばが、届いた要求を本人と分かるかどうかで振り分け、断るときはどの配備でも同じ形で断り、
内部の事情を明かさないことを、どの学びのどの経路でも一様に満たす。配信した本番が守られていることの土台で、
個々の経路の内容は各 UC が持つ。

## 事前条件

- 学び側とまなびばが本番に配備され、それぞれ配備ごとのデータの保存先に結びついている
- 利用者の端末が、学び側の要求に添えるトークン、またはまなびばの要求に添えるセッションを持ちうる（発行は UC-013 の範囲）
- 配備に、登録簿のどの学びとして応えるかを決める学びの key が与えられうる（学び側だけ）
- 適用される業務規則: BR-001, BR-002, BR-005, BR-014

## 主シナリオ

1. システムが、学び側とまなびばへの要求を受け取り、添えられたトークンまたはセッションが通るかを確かめる → BR-001
2. システムが、要求の本文が決められた形を満たすかを確かめる
3. システムが、本人と分かった要求だけを処理に進め、その本人の応答を返す
4. システムが、返すどの応答にも定められたセキュリティヘッダを載せる
5. システムが、認証を要さない死活確認には、データの保存先を引かずに生きていることを示す応答を返す
6. システムが、断るときは断りの理由に当たる形で返し、内部の事情を明かさない → BR-002
7. システムが、断りと届かなかった要求を、画面で日本語の 1 文として利用者に伝える → BR-014

## 事後条件

- 成功時: 学び側とまなびばが、本人と分かった要求にだけ認証を要する応答を返しており、断りはどれも日本語の 1 文として利用者に伝わり、どの応答にも内部の事情が出ておらず定められたセキュリティヘッダが載っている。死活確認はデータの保存先の状態に依らず生きていることを示す
- 失敗時: いかなる状態変更も残っていない（部分適用なし。断った要求は本人の記録も学びのデータも変えない）

## 要件

### REQ-255

- pattern: Unwanted behaviour
- br: BR-001, BR-044
- status: active

> 認証を要する応答を求める要求に、通るトークンまたはセッションが添えられていないとき、まなびばと、与えられた学びの key が登録簿にありトークンの署名の秘密が与えられた学び側の配備は、その応答を返さず、要求された変更も行わないまま、日本語の理由を 1 つ添えて断る。

#### 検証方針

- **分割クラス**:
  - `#credential-absent` — 認証を要する経路に、トークンもセッションも添えずに届いた要求
  - `#credential-malformed` — トークンの形になっていない文字列を添えた要求
  - `#credential-wrong-secret` — 別の秘密で署名されたトークンを添えた要求
  - `#credential-expired` — 期限が過ぎたトークンまたはセッションを添えた要求
  - `#credential-revoked` — 管理者の再設定で消されたセッションを添えた要求
  - `#mutating-route-refused` — 変更を求める経路（送信・記録）も、処理に進める前に断る
  - `#portal-session-absent` — まなびば側の認証を要する経路に、セッションが無い要求（学び側と同じ形の断り）
  - `#public-route-not-refused` — 認証を要さない経路（死活確認・ログインの形）は断りの対象にしない、条件の外側の境界
  - `#precedes-body-check` — 通るものが無く、かつ本文も決められた形を満たさない要求で、本文の断りより先に認証の断りが立つ（UC の表 2 行目 2 列目。R-1207）
- **尽きている根拠**: 要求に添えられたものは（何も無い）（在るが通らない）の 2 つで、UC の表の 3 行目が「通らない」を 壊れている・別の秘密・期限切れ・管理者の再設定で消された の 4 つに割る ＝ クラス 1〜5。経路の側は（認証を要する取得）（認証を要する変更）（認証を要さない）の 3 つで、前 2 つをクラス 1〜5 と 6 が、3 つ目を境界のクラス 8 が取る。配備は学び側とまなびばの 2 つで、まなびば側をクラス 7 が取る。2 つの断りが同時に立ちうる組はクラス 9 の 1 組だけ（知らない経路は REQ-256 が、処理の途中の失敗は UC の表で 不可）。
- **境界の扱い**: 断る側と断らない側の切れ目は「その経路が認証を要するか」で、要さない経路の一覧の正本はサーバの経路の定義（BR-001・R-102）。クラス 8 が断らない側の端を取る。
- **検証しない**: 断りの文言そのもの（各 UC の契約の `errors` と実装が形の正本。R-102）。断った要求が保存先に何も残していないことの直接の観測（単体では保存先を束ねないので観測できない。本番相当の `scripts/check_api.py`・`scripts/check_portal_api.py` が見る）。トークンとセッションの作り（署名の仕方・期限の持ち方）は通る／通らないの判定の内側で、外から観測できない（R-401）。配備にトークンの署名の秘密が無いときの断りは REQ-275 が、学びの key が与えられていない・登録簿に無い学び側の配備の断りは REQ-354 が持つ（この要件は、どの学びとして応えるかが定まり、添えられたものを確かめられる配備の話）。

### REQ-256

- pattern: Unwanted behaviour
- status: active

> 学び側とまなびばが受け持たない /api の経路への要求を受けたとき、見つからないことを日本語の理由を 1 つ添えて断り、本人として呼ばれたかどうかで断りを変えない。

#### 検証方針

- **分割クラス**:
  - `#unknown-path-anonymous` — 本人と分からない要求が、学び側の受け持たない /api の経路を呼ぶ
  - `#unknown-path-authenticated` — 通るトークンを添えた要求が同じ経路を呼ぶ（断りが変わらない）
  - `#unknown-path-portal` — まなびばの受け持たない /api の経路を呼ぶ
  - `#unknown-path-no-signing-secret` — トークンの署名の秘密が無い配備が、受け持たない /api の経路を呼ばれる（設定が無いことによる断りに変わらない）
  - `#unknown-path-unresolved-key` — 学びの key が与えられていない、または登録簿に無い配備が、受け持たない /api の経路を呼ばれる（設定が無いことによる断り（REQ-354）に変わらない）
- **尽きている根拠**: 経路は（受け持つ）（受け持たない）の 2 つで、受け持つ側は各 UC の operation が持つ。受け持たない側を分ける軸は「本人として呼ばれたか」の 2 値だけで、文が「断りを変えない」と言うのはこの 2 つの比較そのもの（クラス 1・2）。配備は学び側とまなびばの 2 つで、まなびば側をクラス 3 が取る。学び側の配備はさらに設定が（そろう）（署名の秘密が無い）（学びの key が解決できない）で分かれ、後の 2 つがこの経路に別の断りを差し込める位置にあるのでクラス 4・5 が取る。
- **境界の扱い**: クラス 1 は認証の前置きが掛かる /api 配下を匿名で呼び、断りが 401 に変わらないことを見る（前置きの外側にある /api/auth/* 配下は匿名でも断りが変わりようがないので、クラス 1 の入力には取らない）。受け持つ経路の一覧の正本はサーバの経路の定義（R-102）。
- **検証しない**: /api の外の経路（画面の静的ファイルと SPA の受け口）— 断りではなく画面を返す経路で、この文の射程外。断りの文言そのもの（実装が正本。R-102）。

### REQ-257

- pattern: Unwanted behaviour
- status: active

> 要求の本文が決められた形を満たさないとき、まなびばと、与えられた学びの key が登録簿にある学び側の配備は、その本文を処理に進めず、どの項目が満たされていないかが分かる日本語の理由を添えて断る。

#### 検証方針

- **分割クラス**:
  - `#not-json` — 本文が JSON として読めない
  - `#field-missing` — 契約が `required` に挙げる項目が本文に無い
  - `#wrong-type` — 項目の値が契約の型でない
  - `#out-of-range` — 項目の値が契約の形・長さ・範囲の外
  - `#not-processed` — 断った本文は処理に進まない（保存先を引く段に届かない）
  - `#reason-names-the-field` — 断りの理由が、満たされていない項目を日本語で指し、スキーマの英語の文言を出さない
- **尽きている根拠**: 本文は（JSON として読めない）（読めるが項目が無い）（項目の型が違う）（型は合うが範囲の外）（すべて決めの内）の 5 つに分かれ、最後だけが各 UC の成功側の要件の領域で、残り 4 つをクラス 1〜4 が 1 対 1 で取る。断ったときの観測は「進まないこと」と「理由の形」の 2 点（クラス 5・6）。
- **境界の扱い**: 範囲の両端の値そのものは各 operation の `request` が持つ（R-102）。断る側の端をクラス 4 が取り、通る側の端は各 UC の成功側の要件。
- **検証しない**: 項目ごとの文言の正確な語（利用者に見える文は別の検査が見る。R-102）。認証を要する経路で通るものが無く本文も形を満たさない要求の先後 — 先に立つのは認証の断りで、持ち主は REQ-255（`#precedes-body-check`）。署名の秘密が無い配備で本文も形を満たさない要求の先後 — 認証を要さず本文を取る経路は UC-013 の発行の経路 `signInWithCode` の 1 本だけで、先に立つのは配備に設定が無いことによる断り（持ち主は REQ-274）、認証を要する経路では REQ-275 なので、この配備ではこの文の対象になる入力が無い。学び側のパスワードでのログイン・登録の経路は受け持たない経路で、本文の形を問わず REQ-256 が見つからないことで断る（この文の入力に取らない）。学びの key が与えられていない・登録簿に無い配備で本文も形を満たさない要求 — 持ち主は REQ-354。

### REQ-258

- pattern: Unwanted behaviour
- br: BR-002
- status: active

> 要求の処理の途中で想定していない失敗が起きたとき、学び側とまなびばは、断りの理由の文を要求の内容と失敗の中身によって変わらない固定の日本語の 1 文にし、失敗の中身を応答に出さない。

#### 検証方針

- **分割クラス**:
  - `#learning-internal-fixed` — 学び側で処理の途中に想定していない失敗が起きた要求
  - `#portal-internal-fixed` — まなびばで処理の途中に想定していない失敗が起きた要求
  - `#same-text-regardless-of-input` — 同じ失敗に違う入力を与えても、返る 1 文が変わらない
- **尽きている根拠**: 「想定していない失敗」は外から種類を指定できないので、分けられる軸は（配備が学び側かまなびばか）の 2 つ（クラス 1・2）と（同じ失敗に別の入力を与えたか）の 1 つ（クラス 3）だけ。失敗の中身が文に映らないことは、クラス 1・2 が本文に内部の語（例外の文・種類・呼び出しの履歴）が出ないことで取る。
- **境界の扱い**: 想定している失敗（認証の断り・本文の断り・知らない経路）は REQ-255〜257 が持ち、この文は残りの全部を 1 つの固定の 1 文に倒す側だけを述べる。断りの応答が持つ種類の名前は REQ-573 が持ち、この文は理由の文と失敗の中身の出し方だけを述べる。
- **検証しない**: 固定の 1 文の語そのもの（実装が正本。R-102）。失敗の中身を運用の記録に残すこと（利用者に返る応答の外で、この文が述べていない）。途中で書きかけた変更が残らないこと（経路ごとの事後条件で、各 UC の領域）。

### REQ-259

- pattern: Ubiquitous
- status: active

> 学び側とまなびばは、認証を要さない経路の応答・本人として通った要求の応答・断りの応答のいずれにも、定められたセキュリティヘッダをすべて載せて返す。

#### 検証方針

- **分割クラス**:
  - `#headers-on-public` — 認証を要さない経路の応答
  - `#headers-on-refusal` — 断りの応答（認証の断り）
  - `#headers-on-authenticated` — 本人として通った要求の応答
  - `#headers-on-portal` — まなびばの応答（認証を要さない側と本人の側の両方）
- **尽きている根拠**: 文が挙げる応答の種類は（認証を要さない）（本人として通った）（断り）の 3 つで、クラス 1〜3 が 1 対 1 に取る。配備は学び側とまなびばの 2 つで、まなびば側をクラス 4 が取る。述語は「すべて載せて返す」なので、1 つの応答についてヘッダの集合の全要素を見れば尽きる（集合の正本は実装の応答の組み立て。R-102）。
- **境界の扱い**: 載せる／載せないの切れ目は無く（どの応答にも載る）、境界は応答の種類の側にしか無い。
- **検証しない**: ヘッダの値が外部の基準を満たすか（NFR-001 の計測が見る）。応答の本文の中身（この文はヘッダだけを述べる）。

### REQ-260

- pattern: State-driven
- status: active

> 配備のデータの保存先が応答しない間も、まなびばと、与えられた学びの key が登録簿にある学び側の配備の死活確認は、生きていることを示す応答を返す。

#### 検証方針

- **分割クラス**:
  - `#health-without-store-portal` — まなびばの保存先が例外を投げる間の死活確認
  - `#health-without-store-learning` — 学び側の保存先が配備に結びついていない間の死活確認
- **尽きている根拠**: 「応答しない」は UC の表の 1 つのセルで、原因は（壊れている）（配備に結びついていない）の 2 つ。配備も学び側とまなびばの 2 つで、2 クラスが原因と配備を 1 つずつ組んで両方の原因を覆う（死活確認が保存先を引かないことの観測は、どちらの原因でも同じ 1 点に縮む）。
- **境界の扱い**: 保存先が応答する間の死活確認は UC-015 の REQ-213 が持ち、この文は「応答しない間も」の側だけを述べる。学びの key が与えられていない・登録簿に無い学び側の配備の死活確認は REQ-354 が持ち（保存先の状態を問わず断る）、この文の入力に取らない。
- **検証しない**: 死活確認が認証を要さないこと（REQ-255 の `#public-route-not-refused` と UC-015 が持つ）。保存先が応答しないことを死活確認が知らせること — 文が「生きていることを示す」と言う通り、知らせないのが正。

### REQ-261

- pattern: Event-driven
- br: BR-014
- status: active

> 学び側への要求が失敗の応答で返され、その断りに別の案内を出すか、その失敗を示さないと決めた要件がその画面に無いとき、画面は、その応答の本文に添えられた理由を利用者に見える文として示し、理由が添えられていなければ日本語の 1 文を示す。

#### 検証方針

- **分割クラス**:
  - `#reason-on-screen` — 失敗の応答の本文に理由が添えられている（その理由の文が画面に出る。本文に理由のほかの項目があっても、画面に出るのは理由の文だけ）
  - `#fallback-on-screen` — 失敗の応答だが本文に理由が無い（日本語の 1 文が画面に出て、本文の中身は画面に出ない）
- **尽きている根拠**: この文の入力は失敗の応答の本文が理由を持つか否かの 2 値で、UC の表「画面が学び側への要求に対して受けたもの」の 2 つのセルがそのまま 2 クラス。応答そのものが返らない場合は REQ-262 の領域。
- **境界の扱い**: 「理由が無い」は本文に理由の項目が無い場合と本文が読めない場合（中継機の HTML など）の両方で、画面に出る文がどちらも同じ 1 文に倒れるので 1 クラスに畳む。各 UC の要件が特定の断りに別の案内を決めている場合（進行中のテストがある断りの REQ-110・REQ-143・REQ-056、前回の続きの導線から開いた論点が無い REQ-342、期限切れの REQ-197 など）と、その失敗を示さないと決めている場合（取得できなかった用語集を空の用語集として扱う REQ-012、進行中のテストの有無が取れていない間はホームに案内を出さない REQ-093、ロードマップの取れなかった部分を示さない REQ-136、ログインした画面で認証の形の問い合わせが失敗したときにまなびばへの導線を出さない REQ-566 など）は、その要件が先で、この文の入力に取らない。観測は画面に出た文で行い、失敗を受ける画面のうち 1 つを描いて見る。
- **検証しない**: 倒したときの 1 文の語そのもの（実装が正本。R-102）。理由を出す場所と、読み直す手段・押し直せることを添えるか（画面ごとに違い、各 UC の要件 — REQ-100・REQ-033・REQ-157 など — が BR-014 の下で持つ。BR-014 自体は人のレビュー）。失敗が画面の部品にどんな形で渡るか（投げる型・状態コード・本文を持つこと）は画面から観測できない設計（R-401）。

> 学び側への要求が相手に届かず応答が返らないとき、画面は通信できなかったことを伝える固定の日本語の 1 文を利用者に伝え、内部の失敗の文をそのまま出さない。

### REQ-275

- pattern: Unwanted behaviour
- br: BR-001
- status: active

> 与えられた学びの key が登録簿にあり、トークンの署名の秘密が与えられていない学び側の配備は、認証を要する要求に添えられたトークンを読まず、求められた応答も要求された変更も行わないまま、配備に設定が無いことに当たる形で断る。

#### 検証方針

- **分割クラス**:
  - `#token-present-refused` — 署名の秘密が無い配備に、トークンを添えた認証を要する要求が来た状態
  - `#token-absent-refused` — 同じ配備に、トークンを添えない認証を要する要求が来た状態（断りは添えたときと同じ形）
  - `#public-route-not-refused` — 同じ配備でも、認証を要さない経路（死活確認と、ログインの形の問い合わせ）は秘密の不足では断られない（条件の外側の境界）
- **尽きている根拠**: この配備に来る要求は（認証を要する）（要さない）の 2 つで、要する側は添えられたものが（在る）（無い）の 2 値 ＝ クラス 1・2、要さない側の端をクラス 3 が取る。添えられたものが在る側は、署名の秘密が無い配備では通る／通らないを判じないので 1 クラスにまとまる。受け持たない経路はこの文の射程に入らない（REQ-256 が先で、見つからないことで断る）。学びの key が与えられていない・登録簿に無い配備もこの文の射程に入らない（REQ-354 が持ち、署名の秘密の有無を問わず断る）。
- **境界の扱い**: 断る側と断らない側の切れ目は「その経路が認証を要するか」で、要さない経路の一覧の正本はサーバの経路の定義（BR-001・R-102）。
- **検証しない**: 断りの本文が足りない秘密を明かさないこと（REQ-206 のクラス `#same-text-as-other-not-configured` が見る）。まなびば側の振る舞い（まなびばのセッションはトークンの署名の秘密に依らない）。トークンを発行する側の断りは REQ-274 が持つ。

- status: active

### REQ-354

- pattern: Unwanted behaviour
- br: BR-005
- status: active

> 配備に学びの key が与えられていないか、与えられた key が登録簿に無いとき、学び側は既定の学びに倒さず、死活確認を含む受け持つ /api の経路へのどの要求にも、配備に設定が無いことに当たる形で断る。

#### 検証方針

- **分割クラス**:
  - `#unknown-key-refused` — 登録簿に無い key を与えた配備の、受け持つ /api の経路への要求（どの学びとしても応えず、設定が無いことに当たる形で断る）
  - `#missing-key-refused` — key を与えていない配備の、受け持つ /api の経路への要求（同上）
  - `#health-also-refused` — そうした配備の死活確認（データの保存先が応答するかを問わず、生きていることを示す応答を返さない。本番の検査が REQ-217 で挙げられる側に落ちる）
  - `#auth-config-also-refused` — そうした配備への認証の形の問い合わせ（答える対象の学びが定まらないので、認証の形を答えずに断る）
  - `#precedes-other-refusals` — そうした配備で、認証を要する経路にトークンを添えず、本文も決められた形を満たさず、トークンの署名の秘密も無い要求（認証の断り・本文の断り・署名の秘密の不足の断りのどれでもなく、この断りが立つ）
- **尽きている根拠**: 解決できない key は「無い」と「登録簿に無い」の 2 つに尽き、断る対象が認証を要さない経路まで及ぶことを、データの保存先を引かない死活確認と、配備の設定を答える認証の形の問い合わせの 2 クラスで押さえる（認証を要する経路と要さない経路の差は、断りが key の解決より後ろに無いことでどれも同じ観測に落ちる）。同じ入力に他の断りが重なりうる軸は、UC の表 1 の添えられたもの・本文の形・署名の秘密の 3 つで、3 つが全部重なる入力を 1 クラスが取る（REQ-255・REQ-257・REQ-275・REQ-274・REQ-205・UC-015 の REQ-213 は、どれも学びの key が登録簿にある配備に射程を切っている）。受け持たない /api の経路はこの文の射程に入らない（REQ-256 が先で、key の状態を問わず見つからないことで断る）。死活確認はデータの保存先の状態を問わずこの文が先で、REQ-260 は key が登録簿にある配備だけを述べる。
- **検証しない**: 断りの本文の文言（BR-002 の射程）。key の値を配備に与える手順（配備の手続き `scripts/deploy-pages.sh` が登録簿から組む）。
