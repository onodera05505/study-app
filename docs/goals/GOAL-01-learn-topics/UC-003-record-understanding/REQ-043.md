# REQ-043

> 利用者が次に学ぶの候補を求めたとき、システムは、過去問が紐づく論点だけを候補とし、その学びの種類の並びに従った順で返す。

## 検証方針

- **分割クラス**:
  - `#only-topics-with-questions` — 過去問が紐づかない論点は候補に入らない
  - `#order-follows-learning-type` — 候補の順が、その学びの種類の並びに従う
  - `#tie-by-field` — 資格対策の学びで出題頻度が同じで分野が違う候補どうしは、シラバスの分野の順に並ぶ
  - `#tie-by-item` — 出題頻度と分野が同じで項目が違う候補どうしは、シラバスの項目の順に並ぶ
  - `#tie-by-id` — 出題頻度と項目が同じ候補どうしは、論点の ID の順に並ぶ
- **尽きている根拠**: 候補に入るかは「過去問が紐づくか」の二分（まだ理解していないことは BR-030 の定義で、候補が尽きた状態は REQ-046 が持つ）で、入った候補の観測点は順だけ。資格対策の並びの中の順は、2 つの候補の出題頻度が違うか（`#order-follows-learning-type`）、同じなら分野・項目・ID のどこで初めて違うか（BR-031）で尽きる。
- **境界の扱い**: 分野と項目の順の期待値は、正本の `data/<学びの key>/syllabus.json` の項目をそのまま仕込んで、分野が初めて現れる順・項目の number の順で組む。分野の順が違う ip と ap の 2 つの学びで同じ検査を回し（ap の登録簿の分野の並びはシラバスと逆）、同頻度の候補は ID の順・名前の順が期待の順と一致しないように置く。
- **検証しない**: 項目の順と分野の順が食い違うシラバス（今のシラバスはどの学びも分野ごとに項目が続いて並ぶ）。実データでの実際の並びと件数は `scripts/check_api.py` が本番相当で見る。ロードマップ型の学ぶ順は GOAL-03 の範囲。候補の上限の値は契約の `nextTopics` が持つ。
