# REQ-068

> 送った回答が受け付けられずに断られたとき、システムは、現在の問題を取り直し、取り直した結果（終わっている・現在の問題はどれか）に従って示し、取り直した位置が送った位置と違うときは表示がずれていたことを利用者に伝える。

## 検証方針

- **分割クラス**:
  - `#rejected-refetch-finished` — 断られて取り直した結果が「終わっている」とき、断られた回答を採点したことにせず、取り直した結果に従って締めの流れへ進む
  - `#stale-idx-refetch` — 断られて取り直した位置が送った位置と違うとき、表示がずれていたことを伝え、取り直した問題と進み具合で示す
- **尽きている根拠**: 断りの本文は契約の `ErrorBody` だけで断られた理由を区別しないので（BR-022）、断られたあとの振る舞いは取り直した `getCurrentQuestion` の応答だけで決まる。その応答は `finished` の 2 値に尽きる。true 側が「終わっている」で、false 側は現在の問題が返る側＝その位置は送った位置と違う（同じ位置が現在の問題として返るなら、その回答は断られていない）。よって 2 クラスで尽き、「表示がずれていたことを伝える」は後者だけが持つ。
- **境界の扱い**: 契約で `expired` が入るのは `finished: true` の応答だけなので、時間切れは「終わっている」側の内訳であって別のクラスにならない（この UC の演習は制限時間を持たない）。取り直しそのものが断られたときの画面の振る舞いは、この文の射程外（持ち主の REQ は無い）。
- **検証しない**: 断られた理由の内訳（契約 `answerQuestion` の 4 つの `CONFLICT`。本文が区別しないので画面からは観測できず、優先は `errors` の並びが持つ＝R-1207）。取り直した結果そのものの正しさ（サーバ側。REQ-058・REQ-067・REQ-119 が持つ）。断りの本文の文言（サーバの応答が正本）。締めの成否と結果の画面の振る舞い（REQ-073・REQ-074 が持つ。時間切れで締められた旨の文は結果の画面＝REQ-124 が示す）。
