# REQ-033

> 論点の教材が取れなかったとき、システムは、前回の続きの導線から開いた論点がもう無いと分かった場合（REQ-342 が持つ）を除き、読み込み中である旨の表示を残さず、教材と紐づく過去問の代わりに取れなかったことを示し、その論点の教材を取り直す手段を添える。

## 検証方針

- **分割クラス**:
  - `#detail-fetch-failed` — 論点を開いたあと論点の教材の取得が失敗した入力（論点の一覧などから開いた場合と、前回の続きの導線から開いて `NOT_FOUND` 以外の失敗で取れなかった場合。読み込み中を残さず、教材と紐づく過去問の代わりに取れなかったことを示し、取り直す手段を添える）
- **尽きている根拠**: 取得の結果は成功と失敗の 2 つで、成功は REQ-023 が持つ。失敗のうち、前回の続きの導線から開いて契約の `NOT_FOUND` が返った入力は REQ-342 が持つ。残りの失敗は、入口と理由が変わっても「読み込み中を残さず、教材と紐づく過去問の代わりに取れなかったことを示し、取り直す手段を添える」が同じなので 1 クラス（前回の続きに覚えた論点を導線を経ずに開いて `NOT_FOUND` になった入力も、導線から開いて通信の失敗になった入力も、導線から開いたあと別の論点を開き、履歴で戻った論点が `NOT_FOUND` になった入力（導線を選んでおらず、覚えた前回の続きは今もある論点）も、このクラスの境目の点として見る）。
- **検証しない**: 前回の続きの導線から開いた論点の `NOT_FOUND`（REQ-342 が持つ）。契約の `INVALID_INPUT`・`NOT_FOUND` と通信の失敗の区別（要件は取れなかったことを示すまでで、区別を決めていない）。失敗の理由ごとの文言の違い（文言の正本は画面のコード）。取り直す手段の見た目と置き場所（要件は添えることだけを言う）。
