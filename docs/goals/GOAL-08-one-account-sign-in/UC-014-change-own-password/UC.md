# UC-014 自分のパスワードを変える

## 概要

利用者が、まなびばで自分のアカウントのパスワードを、現在のパスワードを示してから自分で新しいものに入れ替える。

## 事前条件

- 利用者（ACT-01）にまなびばのアカウントがあり、この端末でまなびばにログイン中である（名乗って入るまでは UC-013 の範囲）
- アカウントは管理者が作ったもので、利用者が自分で作ることはできない（GOAL-05 の範囲）
- 適用される業務規則: BR-002, BR-007, BR-039

## 主シナリオ

1. 利用者がまなびばで自分のアカウントの欄を開く
2. 利用者が現在のパスワードと新しいパスワードを送る
3. まなびばが現在のパスワードを確かめる
4. まなびばが本人のパスワードを新しいものに入れ替える
5. まなびばが、パスワードが変わったことを利用者に伝える

## 例外系の走査（4 分類）

| 軸 | 該当ステップ | 導出 |
| --- | --- | --- |
| 権限 | 2・4 | 変えられるのは自分のアカウントのパスワードだけで、本人と分からない要求は受けない → 表 3 行目の 不可。他人のパスワードの再設定は GOAL-05 の範囲 |
| 不変条件違反 | 3・4 | 現在のパスワードが合わなければ入れ替えない → REQ-210。決められた形を満たさない本文では入れ替えない → REQ-211。入れ替えた新しいパスワードは、同じパスワードでだけ照合に通り、保存し直すたびに一致しない記録で残る → REQ-290（BR-039） |
| 並行性 | 4 | 同じ本人が他の端末でもまなびばを使っている間に変えても、その端末のログインは残る → REQ-212 |

## 事後条件

- 成功時: 新しいパスワードでまなびばにログインでき、前のパスワードでは入れず、ログイン中の端末はそのまま使える
- 失敗時: いかなる状態変更も残っていない（部分適用なし。パスワードは前のまま残り、前のパスワードで引き続きログインできる）

## 要件

### REQ-209

- pattern: Event-driven
- status: active

> ログイン中の利用者が、合う現在のパスワードとともに新しいパスワードを送ったとき、まなびばは本人のパスワードを新しいものに入れ替え、以後は新しいパスワードでだけログインできる。

#### 検証方針

- **分割クラス**:
  - `#replaced` — 合う現在のパスワードと決めの長さの新しいパスワードを送ると、入れ替えが受け付けられる状態（契約 `changeOwnPassword` の成功）
  - `#new-password-logs-in` — 入れ替えのあと、新しいパスワードでまなびばにログインできる状態
  - `#old-password-rejected` — 入れ替えのあと、前のパスワードではログインできない状態（「新しいパスワードでだけ」の後段）
  - `#min-length-passes` — 新しいパスワードが決めの長さの下限ちょうどのとき入れ替わる、通る側の境界
  - `#max-length-passes` — 新しいパスワードが決めの長さの上限ちょうどのとき入れ替わる、通る側の境界
  - `#next-equals-current` — 新しいパスワードが現在のパスワードと同じ値のときも、契約の `errors` に断る entry が無いため入れ替えとして通る状態
  - `#only-own-account` — 入れ替わるのは要求を送った本人のアカウントだけで、他のアカウントのパスワードは変わらない状態
- **尽きている根拠**: `changeOwnPassword` の入力は（現在のパスワードが本人のものと合う／合わない）×（新しいパスワードが決めの長さの内／外・空）の 2 軸しかなく、この要件は「合う × 内」の 1 区画だけを持つ（合わないは REQ-210、長さの外・空は REQ-211）。その区画の中で振る舞いが変わりうる点は長さの両端と新旧が同じ値の 3 つに縮み、入れ替わったことの観測はログインの可否（新・旧）と変わる範囲（本人のアカウントだけ）で尽きる。
- **境界の扱い**: 決めの長さの値そのものは契約 `changeOwnPassword.request.properties.next` が持つ（R-102）。通る側の両端を `#min-length-passes`・`#max-length-passes` が取り、外側の両端は REQ-211。
- **検証しない**: パスワードの記録の形（照合・保存し直したときの不一致・配備先の上限は REQ-290 のクラスが持ち、記録の作り方そのものは R-401）。成功の応答の本文（契約の共有の形が持つ。R-102）。入れ替えを送る画面の導線（UC の事前条件で、この要件の外）。

### REQ-210

- pattern: Unwanted behaviour
- br: BR-002
- status: active

> 現在のパスワードが合わない変更の要求を受けたとき、まなびばはパスワードを変えずに断り、前のパスワードで引き続きログインできる。

#### 検証方針

- **分割クラス**:
  - `#wrong-current` — どのアカウントのものでもない値を現在のパスワードとして添えた要求が断られる状態（契約 `errors` の 3 件目 `UNAUTHENTICATED`）
  - `#other-account-password` — 他のアカウントのパスワードと合う値を添えても、本人のものではないので断られる状態
  - `#password-unchanged` — 断ったあと、本人のパスワードが前のまま残っている状態（部分適用なし）
  - `#old-password-still-works` — 断ったあと、前のパスワードでまなびばにログインできる状態
- **尽きている根拠**: 現在のパスワードは（本人のものと合う）（合わない）の 2 つで、合う側は REQ-209・REQ-212 が持つ。「合わない」はどのアカウントのものでもない値と他のアカウントのものと合う値に分かれ、どちらも本人のものではないので同じ断りになることを 2 つのクラスが取る。断ったあとの観測は事後条件（失敗時）の 2 つ — パスワードが前のまま・前のパスワードで引き続きログインできる — で尽きる。
- **境界の扱い**: 空の現在のパスワードは「合わない」ではなく契約 `errors` の 2 件目 `INVALID_INPUT` の領域で、REQ-211 が持つ。
- **検証しない**: 断りの本文（BR-002 が形を決め、アカウントの有無や内部の事情で文を変えないことは BR-002 側の検査が見る。R-101）。`INVALID_INPUT` が先に立つ入力（契約 `errors` の 2 件目と 3 件目が同時に当たる要求）は REQ-211 の `#precedes-wrong-current` が持つ。合わない要求を繰り返したときの回数の上限や待ち時間（契約に entry が無く、要件も言わない）。

### REQ-211

- pattern: Unwanted behaviour
- status: active

> パスワードの変更の要求の本文が決められた形を満たさないとき、まなびばはパスワードを変えずに断る。

#### 検証方針

- **分割クラス**:
  - `#next-too-short` — 新しいパスワードが決めの長さの下限より短い、断る側の境界
  - `#next-too-long` — 新しいパスワードが決めの長さの上限を超える、断る側の境界
  - `#next-empty` — 新しいパスワードの欄が空のまま送られた状態
  - `#current-empty` — 現在のパスワードの欄が空のまま送られた状態
  - `#field-missing` — 現在または新しいパスワードの欄そのものが本文に無い状態（契約 `request.required`）
  - `#wrong-type` — 欄の値が契約の型（文字列）でない状態
  - `#not-json` — 本文が JSON として読めない状態（契約 `errors` の 2 件目の `when` の 1 つ目）
  - `#password-unchanged` — 断ったあと、本人のパスワードが前のまま残り、前のパスワードで引き続きログインできる状態（部分適用なし）
  - `#precedes-wrong-current` — 現在のパスワードが合わず、かつ新しいパスワードが決めの長さの外である要求で、先に `INVALID_INPUT` が立つこと（契約 `errors` の 2 件目と 3 件目の隣接。R-1207）
- **尽きている根拠**: 本文は（JSON として読めない）（読めるが欄が無い）（欄の型が違う）（欄が空）（新しいパスワードの長さが範囲の外）（すべて決めの内）の 6 つに分かれ、最後だけが REQ-209・REQ-210 の領域で、残り 5 つをクラスが 1 対 1 で取る。長さの外は下限より短い・上限より長いの 2 方向しかなく、空は現在・新しいの 2 つの欄しかない。断ったあとの観測は事後条件（失敗時）の 1 点に縮む。
- **境界の扱い**: 決めの長さの値そのものは契約 `changeOwnPassword.request.properties.next` の `minLength`・`maxLength` が持つ（R-102）。断る側の両端を `#next-too-short`・`#next-too-long` が取り、通る側の両端は REQ-209。
- **検証しない**: 断りの本文の文言と「どの項目がどう悪いか」の言い方（契約が形を持ち、利用者に見える文は別の検査が見る。R-102）。セッションが無い要求で本文も決めの外である先後（契約 `errors` の 1 件目と 2 件目の隣接）— 1 件目の `UNAUTHENTICATED` の持ち主は UC-017 の REQ-255 で、この先後はその `#precedes-body-check` が取る（この UC の射程外）。

### REQ-212

- pattern: Event-driven
- br: BR-007
- status: active

> 本人が自分のパスワードを変えたとき、その本人がログイン中の端末は変更した端末も他の端末もまなびばを引き続き使え、すでに配られた学び側のトークンもそのまま通る。

#### 検証方針

- **分割クラス**:
  - `#changing-device-session-kept` — パスワードを変えた端末のセッションが、変更のあともそのまま通る状態
  - `#other-device-session-kept` — 同じ本人が他の端末で変更の前から持っているセッションが、変更のあともそのまま通る状態（BR-007 の「本人による変更」の側）
  - `#issued-token-still-passes` — 変更の前に学び側が配ったトークンで、変更のあとも学びの要求が通る状態
  - `#other-account-sessions-untouched` — 他のアカウントのセッションは変更に触られない状態（切ってよい範囲の外側）
- **尽きている根拠**: 変更のあとも本人として通り続ける経路は（変えた端末のまなびばのセッション）（他の端末のまなびばのセッション）（すでに配られた学び側のトークン）の 3 つだけで、クラスがその 3 つに 1 対 1 で当たる。残りは「切ってはいけない範囲の外」で、他のアカウントのセッションが `#other-account-sessions-untouched` として 1 つ。セッションの本数（1 本か 2 本以上か）では振る舞いが変わらない — BR-007 は変えた人が本人か管理者かで分かれ、本数では分かれない — ので本数は増やさない。
- **境界の扱い**: 期限が過ぎたセッションは変更とは関わりなく通らず、この要件の外（UC の表の 3 行目）。
- **検証しない**: 管理者が他人のパスワードを再設定したときに全ての端末のログインを切る側（同じ BR-007 だがこの UC の外で、GOAL-05 が持つ）。学び側のトークンの期限が切れたあとの振る舞い（UC-013 の範囲）。変更に合わせてトークンを失効させること（本人の決定でそのまま通すため、そもそも振る舞いとして無い）。

### REQ-290

- pattern: Ubiquitous
- br: BR-039
- status: active

> まなびばのパスワードの記録は、配備先の実行環境が課す上限の内の計算で作られて同じパスワードを保存し直すと前の記録と一致せず、その照合は上限の内の計算で同じパスワードにだけ通り、違うパスワード・記録として成り立たない値・上限を超える計算を求める記録には失敗せずに通らないと答える。

#### 検証方針

- **分割クラス**:
  - `#same-password-matches` — 保存した記録が、保存したときと同じパスワードで照合に通る状態
  - `#other-password-rejected` — 成り立つ記録に違うパスワードを照合すると通らない状態
  - `#broken-record-too-few-fields` — 欄の数が足りない記録の照合が、例外でなく「通らない」と答える状態
  - `#broken-record-too-many-fields` — 成り立つ記録の後ろに欄が余分に付いた記録の照合が、正しいパスワードでも例外でなく「通らない」と答える状態
  - `#broken-record-derived-length` — 導出の値の欄が 16 進だが長さが違う記録の照合が、正しいパスワードでも例外でなく「通らない」と答える状態
  - `#broken-record-non-numeric-cost` — 計算量の欄が数でない記録の照合が、例外でなく「通らない」と答える状態
  - `#broken-record-non-hex-field` — 16 進でない欄を持つ記録の照合が、例外でなく「通らない」と答える状態
  - `#broken-record-empty-field` — 空の欄を持つ記録の照合が、例外でなく「通らない」と答える状態
  - `#over-limit-record-rejected` — 上限を超える計算を求める記録の照合が、上限を超える計算に進まずに「通らない」と答える状態
  - `#same-password-distinct-records` — 同じパスワードを 2 度保存した記録どうしが一致しない状態
  - `#create-within-runtime-limit` — 記録を作るときに導出の計算（Web Crypto の導出）へ渡る計算量が上限の内である状態
  - `#verify-within-runtime-limit` — 上限ちょうどの計算量の記録を照合するとき、導出の計算へ渡る計算量が上限の内で、照合が答えを返す状態
  - `#persist-v1-compat` — 配備された版が作った記録の見本（`contracts/fixtures/` に追記だけで置く。本番の保存先に今ある記録と同じ形）が、今のコードで、作ったときのパスワードでだけ照合に通る状態（BR-039 の時間の境界。R-1202）
- **尽きている根拠**: 文の述語は（作る側の計算量）（保存し直したときの記録どうし）（照合の答え）（照合の計算量）の 4 つ。照合の答えは、通る側が同じパスワードの 1 つ、通らない側が（違うパスワード）（成り立たない記録）（上限を超える記録）の 3 つ。成り立たない記録は、記録の欄の読み方が分かれる点ごとに代表を 1 つ取る（欄が足りない・欄が多すぎる・計算量の欄・16 進の欄・導出の値の長さ・空の欄）。欄が足りない側と多すぎる側は、読み方の分かれ方が違うので別の同値類にする（R-1105）。
- **境界の扱い**: 上限の値の正本は `scripts/check_source.py` の上限の定数（不変条件 O5）。計算量は記録の欄ではなく導出の計算へ渡る値で観測する。照合の側は上限ちょうど（`#verify-within-runtime-limit`）が通る側の端、上限を 1 超えた記録（`#over-limit-record-rejected`）が外側の端。「通らない」は照合の答えが偽であることで、例外・想定外の失敗はどのクラスでも答えにならない。
- **検証しない**: 新しく作る記録の作り方（関数・ソルトの長さ・作る側の計算量の値そのもの）。実装を差し替えても文は変わらない（R-401）、値の正本はコード（R-102）。ただし配備された版が作った記録を読む側は義務で、`#persist-v1-compat` が見る（形の正本は見本。BR-039）。
