# REQ-210

> 現在のパスワードが合わない変更の要求を受けたとき、まなびばはパスワードを変えずに断り、前のパスワードで引き続きログインできる。

## 検証方針

- **分割クラス**:
  - `#wrong-current` — どのアカウントのものでもない値を現在のパスワードとして添えた要求が断られる状態（契約 `errors` の 3 件目 `UNAUTHENTICATED`）
  - `#other-account-password` — 他のアカウントのパスワードと合う値を添えても、本人のものではないので断られる状態
  - `#password-unchanged` — 断ったあと、本人のパスワードが前のまま残っている状態（部分適用なし）
  - `#old-password-still-works` — 断ったあと、前のパスワードでまなびばにログインできる状態
- **尽きている根拠**: 現在のパスワードは（本人のものと合う）（合わない）の 2 つで、合う側は REQ-209・REQ-212 が持つ。「合わない」はどのアカウントのものでもない値と他のアカウントのものと合う値に分かれ、どちらも本人のものではないので同じ断りになることを 2 つのクラスが取る。断ったあとの観測は事後条件（失敗時）の 2 つ — パスワードが前のまま・前のパスワードで引き続きログインできる — で尽きる。
- **境界の扱い**: 空の現在のパスワードは「合わない」ではなく契約 `errors` の 2 件目 `INVALID_INPUT` の領域で、REQ-211 が持つ。
- **検証しない**: 断りの本文（BR-002 が形を決め、アカウントの有無や内部の事情で文を変えないことは BR-002 側の検査が見る。R-101）。`INVALID_INPUT` が先に立つ入力（契約 `errors` の 2 件目と 3 件目が同時に当たる要求）は REQ-211 の `#precedes-wrong-current` が持つ。合わない要求を繰り返したときの回数の上限や待ち時間（契約に entry が無く、要件も言わない）。
- **参照先**: 単体のテストは無い（学び側の `tests/server/auth.test.ts` の照合は学び側のパスワードの経路で、まなびばの入れ替えとは別物）。本番相当では `scripts/check_portal_api.py::check_me_password_and_logout` が現在のパスワード違いの断りを見るが、system suite なので `@covers` を持たない ＝ 全クラス未被覆。
