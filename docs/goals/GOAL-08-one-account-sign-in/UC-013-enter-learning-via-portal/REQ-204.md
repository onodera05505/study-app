# REQ-204

> 学び側は、配備にまなびばの場所や秘密が与えられているかどうかを問わず、学び側のパスワードでのログインと登録を受け付けず、その入力を求める欄も画面に出さない。

## 検証方針

- **分割クラス**:
  - `#password-login-not-served` — UC の表「学び側の認証の受け口」のどの行の配備でも、学び側のパスワードでのログインの求めが、受け持たない経路への要求と同じ断り（REQ-256）になり、トークンも本人の記録もできない状態
  - `#register-not-served` — 同じどの行の配備でも、学び側の登録の求めが同じ断りになり、トークンも本人の記録もできない状態
  - `#no-password-form` — 同じどの行の配備でも、ログイン画面にパスワードと登録の入力の欄が無い状態
- **尽きている根拠**: 学び側のパスワードで本人を得る入口は、ログインと登録の求め（サーバ）とその入力の欄（画面）の 3 つで尽きる。配備の側は表の受け口の 4 行で、文が配備の設定を条件にしないので、各クラスが 4 行を代表点に取る。
- **検証しない**: 本物のまなびばとの往復（検査用の配備にはまなびばの場所として手元の SSO の偽物を与え、検査の本人はその偽物が換えた使い捨てコードからだけ作る。本物との往復は本番の検査 UC-015 が見る。`docs/verification/GLOBAL.md`）。断りの文面（REQ-256 と契約の errorCodes が形の正本。R-102）。
- **参照先**: `tests/server/UC-013_password_route_not_served.test.ts`（`#password-login-not-served`・`#register-not-served`）、`tests/client/screens.test.tsx::ログイン画面（UC-013）`（`#no-password-form`）。検査用の配備の検査の本人の作り方は system suite の `scripts/check_api.py::account`（`@covers` の対象外）。
