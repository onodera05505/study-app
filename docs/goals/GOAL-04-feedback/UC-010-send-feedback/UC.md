# UC-010 開いていた画面を添えてフィードバックを送る

## 概要

利用者が、直前に開いていた画面（論点・問題を含む）を添え先として、種類を選んだ自由記述のフィードバックを送り、受付文だけを受け取る。

## 事前条件

- 利用者（ACT-01）がログインしており、学びを 1 つ選んでいる（ログインとトークンの扱いは GOAL-08 の範囲）
- 送られたフィードバックを溜める場所があり、初期データの再投入で消えない
- 溜まったフィードバックを開発側が読み、処理済みにする側はこの UC の範囲外（運用のスクリプトが持つ）
- 適用される業務規則: BR-001, BR-010, BR-011, BR-012, BR-014, BR-032

## 主シナリオ

1. 利用者が学びの画面を開く
2. システムが、開いた画面を直前に開いていた画面として端末に 1 件だけ覚え、その画面が論点や問題を読み終えたら同じ記録にその論点と問題も足す
3. 利用者がフィードバックの画面を開く
4. システムが、覚えている直前に開いていた画面を人が読む名前つきで添え先として示し、添えるかどうかを選べるようにする
5. 利用者がフィードバックの種類を 1 つ選び、本文を書く
6. 利用者が送る
7. システムが、本文・種類・添え先を利用者に紐づけて未処理のフィードバックとして残し、受け付けたことだけを返す（その場の応答は返さない）
8. システムが、受付文と、もう 1 件送る導線・添え先の画面へ戻る導線を出し、書いた本文を残さない

## 事後条件

- 成功時: 送った本文・種類・添え先が本人のフィードバックとして未処理のまま残り、画面には受付文と、もう 1 件送る導線・添え先の画面へ戻る導線が出ていて、書いた本文は残っていない（その場の応答は返っていない）

### REQ-146

- pattern: Event-driven
- br: BR-010, BR-011, BR-012
- status: active

> 利用者が学びの画面へ移ったとき、システムはその画面の場所と人が読む名前を添え先として端末に 1 件だけ覚え、それまで覚えていた添え先は残さない。

#### 検証方針

- **分割クラス**:
  - `#remember-page` — 学びの画面へ移ったとき、その画面の場所と人が読む名前が添え先として読み出せる入力
  - `#replace-previous` — すでに添え先を覚えている状態で別の学びの画面へ移る入力（残るのは最後に移った画面だけ）
- **尽きている根拠**: 学びの画面へ移る入力は「まだ覚えていない」「すでに覚えている」の 2 つで尽き、覚える値の形は `contract.yaml` の `LastPage` が持つ（R-102）。
- **検証しない**: 端末が覚えられないとき（BR-011。UC.md の表 1 のこのセルは REQ ではなく BR-011 に当たる）。トークンを捨てるときに添え先も捨てること（BR-010。トークンを捨てる 1 か所が持ち、UC-013 の範囲）。

### REQ-147

- pattern: Event-driven
- status: active

> 利用者がフィードバックの画面へ移ったとき、システムは覚えている添え先を書き換えない。

#### 検証方針

- **分割クラス**:
  - `#keep-remembered` — 添え先を覚えている状態でフィードバックの画面へ移る入力（移る前の添え先がそのまま残る）
  - `#keep-none` — 添え先を覚えていない状態でフィードバックの画面へ移る入力（フィードバックの画面自身が添え先にならない）
- **尽きている根拠**: UC.md の表 1 の「フィードバックの画面へ移る」列は添え先の全状態で REQ-147 を指し、「書き換えない」の観測は移る前の値が残るか（覚えている）／添え先ができないか（覚えていない）の 2 つで尽きる。
- **検証しない**: 覚えた値が読めない状態・端末が覚えられない状態（BR-011）。

### REQ-148

- pattern: Unwanted behaviour
- br: BR-011
- status: active

> 添え先を覚えていない状態、または覚えた値が読めない状態で、開いている画面が論点や問題を読み終えたとき、システムは論点と問題だけの添え先を作らない。

#### 検証方針

- **分割クラス**:
  - `#annotate-without-record` — 添え先を覚えていない状態で、開いている画面が論点・問題を読み終える入力
  - `#annotate-with-unreadable-record` — 覚えた値が読めない状態で、開いている画面が論点・問題を読み終える入力
- **尽きている根拠**: 「添え先を作らない」が問われる前状態は、記憶が空か、記憶はあるが読めないかの 2 つ（UC.md の表 1 で REQ-148 を指す 2 行）。読める記憶がある状態は REQ-149 が持つ。
- **境界の扱い**: 足そうとする値（論点だけ・問題だけ・人が読む名前だけ）は `annotateLastPage` の request が持ち、どの値でも添え先ができないことは同じクラスの代表値。
- **検証しない**: 端末が覚えられないとき（BR-011）。

### REQ-149

- pattern: Event-driven
- status: active

> 添え先を覚えている状態で、開いている画面が論点や問題を読み終えたとき、システムは覚えている添え先に、その論点と問題および人が読む名前を足し、覚えている画面は変えない。

#### 検証方針

- **分割クラス**:
  - `#annotate-fresh` — 画面だけを覚えている添え先に、読み終えた論点または問題と人が読む名前を足す入力（覚えている場所は変わらない）
  - `#annotate-again` — すでに論点・問題を足してある添え先に、もう一度足す入力（最後に読み終えた物に置き換わる）
- **尽きている根拠**: UC.md の表 1 で REQ-149 を指すのは「画面を覚えている」「画面と論点・問題を覚えている」の 2 行で、それが 2 クラスに 1 対 1。足す対象は `annotateLastPage` の request の論点と問題の 2 つで、どちらも同じクラスの代表値（契約の例 `okTopic` / `okQuestion`）。
- **境界の扱い**: 置き換わるのは同じ鍵（論点どうし・問題どうし）だけで、論点を足したあとに問題を足すと論点と問題の両方が残る（契約の例 `readLastPage` の `okTopicThenQuestion`。`#annotate-again` の代表値に含める）。
- **検証しない**: 契約の request の外の入力（場所や範囲外の値。`annotateLastPage` の request が閉じた形で受け付けないので、呼び出し側の型が持つ）。記憶が読めない・書けないとき（BR-011。何も足さないだけ）。

- status: active

  - `#send-without-attachment` — 添え先を覚えていない状態で本文だけを送る入力

- **検証しない**: 覚えた値が読めない・端末が覚えられない状態（BR-011。UC.md の表 1 はそのセルを BR-011 に当てている）。

### REQ-152

- pattern: State-driven
- br: BR-012
- status: active

> 添え先を覚えている間、フィードバックの画面はその添え先を人が読む名前つきで示し、利用者が添える・添えないを選べるようにする。

#### 検証方針

- **分割クラス**:
  - `#show-attachment-label` — 覚えている添え先が、人が読む名前つきでフィードバックの画面に出る入力
  - `#attach-included` — 添えることを選んで送る入力（覚えている添え先の場所と論点・問題が送信に載る）
  - `#attach-excluded` — 添えないことを選んで送る入力（添え先が送信に載らない）
- **尽きている根拠**: 「覚えている間」の観測は、示すこと・添えること・添えないことの 3 つで、REQ の文の帰結に 1 対 1。添える値の形は `submitFeedback` の request の `page`・`topicId`・`questionId` が持つ（R-102）。
- **検証しない**: 添え先を別の端末・別の人に出さないこと（BR-012。端末の記憶が端末の外へ出ない作りそのもので、機械の門は無い）。

### REQ-153

- pattern: State-driven
- br: BR-010, BR-011
- status: active

> フィードバックを送り終えていない間、システムは書きかけの本文を下書きとして端末に残し、利用者がフィードバックの画面を離れて戻ったときはその下書きから本文を書き続けられるようにする。

#### 検証方針

- **分割クラス**:
  - `#draft-kept` — 本文を書いている間の入力（書きかけの本文が下書きとして端末に残る）
  - `#draft-restored` — フィードバックの画面を離れて戻る入力（残っている下書きから本文を書き続けられる）
  - `#draft-absent` — 下書きが無い、または読めない状態で画面を開く入力（本文は空で始まる）
  - `#draft-write-blocked` — 下書きを端末に書けない状態で本文を書く入力（書く操作が名前を持つ失敗を渡しても、本文を書き続けられ、送れる。BR-011）
- **尽きている根拠**: `saveFeedbackDraft` / `readFeedbackDraft` に対する入力は「残す」「読んで戻す」「無い・読めない」の 3 つと、残す側で端末に書けない 1 つで尽きる（契約の例 `ok` / `none` / `unavailable`、`saveFeedbackDraft` の `unavailable`）。
- **境界の扱い**: 下書きを捨てる入口は本文が空の `saveFeedbackDraft`（契約の例 `cleared`。OQ-114）。受付後の片付けは REQ-155 が持つ。
- **検証しない**: 選んだ種類を下書きに残すこと（`saveFeedbackDraft` の request は本文だけを持つ）。

### REQ-154

- pattern: State-driven
- status: active

> 本文とフィードバックの種類のどちらかが欠けている間、フィードバックの画面は送る操作を受け付けない。

#### 検証方針

- **分割クラス**:
  - `#body-missing` — 種類は選んだが本文が空（空白だけを含む）の入力
  - `#kind-missing` — 本文はあるが種類を選んでいない入力
  - `#becomes-sendable` — 本文と種類がそろった入力（送る操作を受け付ける側に変わる）
- **尽きている根拠**: 入力は本文の有無 × 種類の有無の 4 通りで、UC.md の表 2 の「何も入っていない」行は本文欠けと種類欠けの重なりなので別クラスにしない（どちらのクラスの代表値でも観測は同じ「受け付けない」）。そろった 1 通りが `#becomes-sendable`。
- **境界の扱い**: 空白だけの本文は欠けている側に入れる（`submitFeedback` の request が前後の空白を落としてから長さを見る）。
- **検証しない**: 画面が選ばせる種類の集合（`submitFeedback` の `kind` の enum が持つ。R-102）。種類の鍵の無い送信を受け口が断ること（REQ-160#kind-missing）。

### REQ-155

- pattern: Event-driven
- status: active

> 送ったフィードバックが受け付けられたとき、システムは受付文だけを出し、その場の応答は返さず、書いた本文と選んだ種類を画面にも端末の下書きにも残さない。

#### 検証方針

- **分割クラス**:
  - `#accepted-shows-thanks` — 受け付けられた入力（受付文が出て、書いた本文が画面に残らない）
  - `#accepted-clears-draft` — 受け付けられたあとに画面を離れて戻る入力（本文と種類が端末の下書きから戻らない）
  - `#no-inline-reply` — 受け付けられた入力のうち、受付文のほかにその場の応答を出さないことを見る側
- **尽きている根拠**: 受付という 1 つのイベントに対する観測は、出す物（受付文）・出さない物（その場の応答）・残さない物（画面と端末の下書き）の 3 つで、REQ の文の帰結に 1 対 1。
- **検証しない**: 受付文の文言そのもの（実装が正本。R-102）。

### REQ-156

- pattern: Unwanted behaviour
- status: active

> 送信中の利用者が重ねて送ろうとしたとき、システムは新たな送信を行わず、その 1 回の操作からフィードバックが 2 件残ることはない。

#### 検証方針

- **分割クラス**:
  - `#double-submit` — 送信中にもう一度送る操作をする入力（送信は 1 回だけで、その操作からフィードバックが 2 件残らない）
- **尽きている根拠**: 重ねる操作は UC.md の表 2 の「送信中」の 1 状態でだけ起こり、観測は送信の回数が 1 であることだけ。
- **検証しない**: 送信中にフィードバックの画面を離れたときの扱い（REQ-349）。

### REQ-157

- pattern: Unwanted behaviour
- br: BR-014
- status: active

> 送信が拒まれたとき、または届かなかったとき、システムは日本語の理由を出し、書いた本文と選んだ種類を残したまま利用者が送り直せるようにする。

#### 検証方針

- **分割クラス**:
  - `#rejected-by-receiver` — 受け口が断りを返した入力（日本語の理由が出て、本文と種類が画面に残り、もう一度送れる）
  - `#not-delivered` — 送信が届かない入力（応答そのものが無い）
- **尽きている根拠**: UC.md の表 2 の「送信が拒まれる・届かない」は、受け口が理由を返した場合と応答そのものが無い場合の 2 つで尽きる（前者の断りのコードは `submitFeedback` の `errors` が持つ）。
- **検証しない**: 断りのコードごとの文言（日本語であることだけを見る。文言の正本は実装。BR-014 はコードごとの出し分けを決めていない）。

### REQ-158

- pattern: State-driven
- status: active

> 受付文が出ている間、システムはもう 1 件送る導線と、添え先があるときはその画面へ戻る導線を出し、利用者が選んだ導線の行き先を出す。

#### 検証方針

- **分割クラス**:
  - `#send-another` — 受付文が出ている状態で、もう 1 件送る導線を選ぶ入力（本文を書く場が出る）
  - `#back-to-attachment` — 添え先がある状態で、添え先の画面へ戻る導線を選ぶ入力（その画面が出る）
  - `#no-attachment-no-back` — 添え先が無い状態で受付文が出ている入力（戻る導線を出さない）
- **尽きている根拠**: 受付文が出ている状態の導線は「もう 1 件送る」（常に出る）と「添え先へ戻る」（添え先の有無で出る・出ない）の 2 本しかなく、その積が 3 クラス。

### REQ-160

- pattern: Unwanted behaviour
- status: active

> 本文かフィードバックの種類が欠けた送信、または本文・種類・添え先のいずれかが決められた形でない送信が届いたとき、フィードバックの受け口はその送信を拒み、日本語の理由を返し、フィードバックを残さない。

#### 検証方針

- **分割クラス**:
  - `#body-empty` — 本文が無い・空・空白だけの送信
  - `#body-too-long` — 本文が上限を超える送信
  - `#body-wrong-type` — 本文の型が違う、または本文ごと決められた形でない送信
  - `#kind-missing` — 種類の鍵が無い送信（既定の種類に倒さず断る。契約の例 `missingKind`）
  - `#kind-not-allowed` — 決められていない種類の送信
  - `#attachment-wrong-shape` — 添え先（場所・論点・問題）が決められた形でない送信
  - `#nothing-stored` — 断られた送信がフィードバックとして残っていないことを見る側
  - `#invalid-before-rate-limit` — 上限に達している利用者からの、形が決められていない送信（上限の理由より先に形の理由で断る）

- **境界の扱い**: 本文の長さは上限ちょうどを通し、1 字超えを断る（上限の値は契約が持つ。R-102）。認証なしかつ本文が空の送信は、本文の理由より先に認証で断る（契約の例 `noTokenAndEmptyBody`。先後は `errors` の並びが持つ。R-1207）。
- **検証しない**: 理由の文そのもの（日本語であることだけを見る。文言の正本は実装）。

### REQ-161

- pattern: State-driven
- status: active

> 同じ利用者について直近 1 日に受け付けたフィードバックが上限に達している間、フィードバックの受け口は新しい送信を拒み、日本語の理由を返し、フィードバックを残さない。

  - `#nothing-stored` — 上限で断られた送信がフィードバックとして残っていないことを見る側

### REQ-242

- pattern: Unwanted behaviour
- br: BR-011
- status: active

> 端末が添え先を覚えられないとき、または覚えた値が読めないとき、システムは添え先を覚えていないものとして扱い、画面の移りとフィードバックを送ることを止めない。

#### 検証方針

- **分割クラス**:
  - `#unreadable-value` — 覚えた添え先が読めない値になっている（添え先を覚えていない扱いになり、画面が止まらない）
  - `#cannot-remember` — 端末が添え先を覚えられない（覚える操作が断りの種類の名前を持つ失敗を渡しても、画面の移りが止まらず、添え先を覚えていない扱いになる）
  - `#annotate-blocked` — 開いた画面が論点・問題を読み終えて添え先に足すときに端末の記憶が使えない（足す操作が名前を持つ失敗を渡しても、その画面が止まらない）
  - `#read-blocked-feedback` — フィードバックの画面が端末の記憶から添え先を読めない（読む操作が名前を持つ失敗を渡しても、添え先を示さず、フィードバックを送ることが止まらない）
- **尽きている根拠**: 端末の記憶で失敗しうる経路は読みと書きの 2 つで、BR-011 はその両方を「その機能を出さないだけにする」に畳む。添え先に触る場面は、学びの画面へ移る（覚える）・読み終えて足す・フィードバックの画面で読む、の 3 つで、覚えられない側をクラス 2・3、読めない側をクラス 1（値が読めない）と 4（記憶が読めない）が取る。読めた・書けた側は REQ-146・REQ-148・REQ-149 が持つ。
- **境界の扱い**: 読める値と読めない値の境目は記憶の中身の形だけで、値の大小の境界を持たない。
- **検証しない**: 添え先が無いままフィードバックを送れること（REQ-148 が添えるものが無い場合を持つ）。端末の記憶が使えない理由（設定・容量）の区別。記憶の鍵の名前（R-102）。

> 送信中に利用者がフィードバックの画面を離れたとき、システムはその送信を取り消さず、受け付けられれば端末の下書きを残さず、拒まれるか届かなければ書いた本文を端末の下書きに残す。
