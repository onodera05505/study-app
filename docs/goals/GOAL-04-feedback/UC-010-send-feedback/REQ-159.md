# REQ-159

> 本文とフィードバックの種類がそろった送信が届いたとき、フィードバックの受け口は、その本文・種類・添え先を送った利用者に紐づけて未処理のフィードバックとして残し、受け付けたことだけを返す。

## 検証方針

- **分割クラス**:
  - `#accept-and-store` — 本文と種類がそろった送信（送った本人の未処理のフィードバックとして残り、受付の id だけが返る）
  - `#attachment-stored` — 添え先（場所・論点・問題）を添えた送信（その添え先ごと残る）
  - `#no-attachment-accepted` — 添え先の無い送信（受け付けて残す）
- **尽きている根拠**: そろった送信の入力差は添え先の有無とその中身（`submitFeedback` の `page`・`topicId`・`questionId`）だけで、契約の例 `ok` / `okWithQuestion` がその代表値。返す物は受付の id 1 つ（契約の response）。
- **検証しない**: 保存先の表と列・本人の紐づけ方（R-102。`src/server/db/schema.ts` が正本）。初期データの再投入でフィードバックが消えないこと（BR-032。`scripts/check_seed.py` と `scripts/seed_remote.sh` が門）。種類の鍵が無い送信（REQ-160 が断る側に持つ）。
- **参照先**: `tests/server/repay_UC-010_feedback_receiver.test.ts::フィードバックの受け口の保存と上限（UC-010）`（偽の D1 で、受付の id と feedback への INSERT に束ねた値を見る。本番相当の保存先での中身は `scripts/check_api.py`）
