# 応用情報技術者試験（午前）を追加する

IT パスポートと**同じコードベース・別データ・別デプロイ**で運用する。
午前試験は高度試験の午前 I と共通問題なので、これを潰すと IT ストラテジスト
などの午前 I 対策も兼ねる。

## なぜ同梱しないのか

1つのアプリで試験を切り替える形にすると、`topics` / `syllabus_items` /
`past_questions` / `progress` / `sessions` の全部に試験の軸が増え、
`/fields` `/categories` `/topics` `/me` とセッション生成が全部影響を受ける。
得られるのは「ログインが1つで済む」程度で、割に合わない。

**IT パスポート側には別のユーザーの進捗が入っている。** 個人用の都合で、
動いているものの体験に「試験を選ぶ」導線を足すべきではない。

コードは共通で問題ない。試験ごとに違うのはデータと少数の設定だけ。

## ディレクトリ

```
data/ip/     IT パスポート（既存。data/ から移設した）
data/ap/     応用情報
```

全スクリプトに `--data` があるので、`--data data/ap` を渡せば同じ流れで動く。
移設時は seed を再生成して、管理ユーザ行を除いて完全一致することを確認済み。

## IT パスポートとの違い

### 分野が公式に付いている（重要）

`CLAUDE.md` の「IPA の公開問題に分野タグは無い」は **IT パスポートの話**。
応用情報の解答例 PDF には「問番号 / 正解 / 分野」の3列があり、分野は
Ｔ（テクノロジ系）Ｍ（マネジメント系）Ｓ（ストラテジ系）で入っている。

- **分野の分類作業が不要**。しかも公式なので誤りようがない
- 出題比率も確定する。5回とも 問1〜50 テクノロジ、問51〜60 マネジメント、
  問61〜80 ストラテジ（62.5% / 25% / 12.5%）。模試の構成比にそのまま使える

分類で自前判断が要るのは**中分類と小分類、そして論点**だけになる。

### シラバスの階層が1段深い

| | 階層 | 項目数 |
| --- | --- | --- |
| IT パスポート | 分野 → 大分類 → 中分類 → 項目 | 63 |
| 応用情報 | 分野 → 大分類 → 中分類 → 小分類 →（n）→ ① | 96 |

用語例は最深部（① や（n））に付いているが、**小分類にまとめて持たせている**。
論点を紐づける受け皿がこれ以上細かいと、1問を1つに割り当てられなくなる。

アプリで「単元」として見せるのは中分類（23個）。IT パスポートと同じ。

### 配布場所が違う

| | 場所 | URL の作り方 |
| --- | --- | --- |
| IT パスポート | CBT の公開問題ページ | 回ごとに固定。組み立てられる |
| 応用情報 | 年度別ページの添付 | 添付ディレクトリ名が年度ごとに変わる。**ページを読んでリンクを拾う** |

そのため取得スクリプトは別（`fetch_pdfs_ap.py`）。

## 落とし穴（この試験特有）

### 冊子に正誤表が挟まっている回がある

平成29年度秋期がそれ（p002 が正誤表で、問79 に公式訂正2箇所）。冊子の印刷は誤植のままなので、
**読み取りに忠実なほど誤植を転記してしまう**。回を足したら冒頭ページに正誤表が無いか確認し、
あれば該当問に訂正を適用して `notes` に経緯を書く（訂正後が正文。`modified` は立てない）。

### 解答例 PDF にテキストレイヤーが無い回がある

令和4年度春期がそれ。`extract_answer_keys_ap.py` は 0 問と報告する。**回を足したら
「正解 80/80」を必ず確認すること。** 0 問なら、その回はスキャン画像。

対処はページ画像にして人が読み、`data/ap/answer_keys_manual.json` に書く。
自動抽出の結果へマージされるので、スクリプトを再実行しても消えない。
古い年度ほど起きやすいと思われる。

### 大きな JSON を1回で書かせると落ちることがある

教材の担当が「8論点ぶんを1回の Write」で書こうとして、書き出す直前に接続が切れる事故が
連続した（API 側の不安定期）。**4論点を Write → 残りを Edit で追記**に分けさせると通った。
再実行するときは、まず出力ファイルの有無を確認する（書けてから落ちた例もある）。

### 同綴りで別概念の論点が機械統合される

`ARP`（プロトコル）と `arp`（コマンド）が、照合キーの `.lower()` で1つの論点に
統合された。出題頻度＝重要度の設計なので、別概念が混ざると重要度が誤る。
検知は `check_materials.py` の「論点名が不一致」。詳しくは `build_topics.py` の冒頭。

分類の担当に「同綴りで別概念なら補足を付けて区別せよ」と伝えておくと予防できる。

### 担当が途中まで書いて止まる（最頻出）

Write は通ったが Edit の追記中に接続が切れる、という止まり方が一番多い。**報告は
「完了」と言ってくる**ので、報告文を信じてはいけない。次の3つで機械的に見つかる。

- 読み取り … `merge_questions.py` が「問題数 67/80」と欠番を出す
- 分類 … `check_classified.py` が「分類されていない問 N 件」を出す
- 教材 … `check_materials.py` が「担当バンドルと論点が違う（書かれていない …）」を出す

見つけたら**欠けた範囲だけ**を新しい担当に任せる。読み取り・分類は新しいチャンク名／
バッチ名で出させ（既存ファイルを上書きさせない）、教材は既存ファイルへ Edit で追記させる。

**止まったと思った担当が後から完走することがある。** 補完の担当と衝突するので、
完了通知が来たら実ファイルを見て、埋まっていれば補完側を TaskStop で止める。

### API の利用上限で担当が一斉に止まる

2026-08-31 夜、教材担当 11 体のうち 9 体が `session limit`（HTTP 429）で同時に止まった。
止まり方は「前半4論点の Write は通り、後半の Edit 前で切れる」で、上の「途中まで書いて止まる」と同じ。
`check_materials.py` の「書かれていない [...]」で欠けた論点が機械的に出るので、上限が回復してから
**欠けた後半だけ**を新しい担当に Edit で追記させれば済む（実際 4 体で 16 論点を補完した）。

### 報告と成果物が食い違う

同じ担当から**内容の違う完了報告が2回届く**ことがある（1回目が途中経過）。論点名を
まるごと取り違えた報告もあった。担当への指示に次の検証コマンドを入れて出力を貼らせ、
親側でも同じ照合をすると確実。

```bash
python3 -c "import json;b=json.load(open('data/ap/material_bundles/bundle_74.json'));m=json.load(open('data/ap/materials_v2/bundle_74.json'));bb=[(t['topic_id'],t['term']) for t in b['topics']];mm=[(x['topic_id'],x['term']) for x in m['materials']];print('MATCH', bb==mm)"
```

### D1 への投入が Authentication error で落ちることがある

`wrangler d1 execute --remote` が `Authentication error [code: 10000]` を返すことがある。
**DB は元の状態に戻るので、そのまま再実行してよい**（実際、1回目失敗・2回目成功だった）。
投入後は件数を SELECT して確かめること。
