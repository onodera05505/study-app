# ADR-0013 道具の中の読み書きの操作 — 操作ごとに呼べる関数を入口にし、名前を持つ失敗を渡す

## Context

作り手の道具が置き場のファイルを読み書きする操作（契約の `transport: local-store`・`direction: outbound`・`owned: true`。`read…`・`write…` の名前を持つ）は、契約に `request`・`response`・`errors`・実例を持つ。

入口の規則（`CLAUDE.md` の「操作 → 入口」）は、これらを「その操作を `@operation` で持つ道具を回し、契約が名指す置き場のファイルで見る」と読んでいた。道具を丸ごと回すと、道具が出す断りの名前（ADR-0012）は道具を回す操作の `errors` の物で、中の読み書き 1 つの `errors` の名前（置き場に無い・形が読めない・書けない）は外から見分けられない。注釈も 1 対 1 でなく、1 つの操作の `@operation` が 2 か所にあったり、1 つの関数が 2〜3 の操作を持ったりする。

契約の実例を実装に当てる確かめ（UC-033）は、実例を 1 件ずつ実装に渡し、失敗例を名前で照らす。原本の contract-run の README は、受け渡し役が実装を import して呼ぶことを求め、`local-store`・`outbound`・`owned: true` の操作を自分の形として持つ例を置いている。

本人は 2026-11-18 に、道具の中の読み書きを操作ごとに呼べる関数に整え、確かめが関数として直接呼ぶこと、道具の動きと人が見る出力を変えないことを決めた。

## Decision

- **道具の中の読み書きの操作は、1 操作に 1 つの Python の関数を入口に持つ。** 関数は `scripts/` のファイルの最上位に置き、名前は操作名を snake_case にした物で、直上に `@operation UC-nnn#操作名` を持つ。`@operation` は 1 操作に 1 か所だけ置く。
- **関数は、契約の `request` の項目をその名前のままキーワード引数で受け、`response` の形の値を返す。**
- **契約の `errors` に当たる失敗は、断りの種類の名前を `code` に持つ例外で渡す。** 端末の記憶の操作と同じ鍵で読む（ADR-0012）。名前は名前の出所のファイルの物だけ。
- **道具は、この関数を通して読み書きする。** 読み書きの失敗を、道具を回す操作の断り（標準出力の形）や今までの扱い（無いとして進む・空として進む）へ畳むのは道具の側で、道具を回したときの動きと人が見る出力は変えない。
- **道具が同じ種類の読み書きをまとめて行うとき（図をまとめて描くなど）は、操作の関数と道具が同じ部品を使う。** 道具が関数を 1 件ずつ呼ぶ形にはしない。1 件ずつ呼ぶと、道具の掛かる時間と「1 つでも整わなければ何もしない」動きが変わる。
- 入口の規則の「道具の中の読み書き」の行をこの読みに書き換える。関数のあるファイルは、`@operation` の注釈の行から引く（契約の操作と注釈の対応は C21 が保証する）。

## Consequences

- よい: 読み書き 1 つずつの失敗の種類を、契約の実例で名前ごとに確かめられる。
- よい: 契約の操作と入口の関数が 1 対 1 になり、どの関数がどの操作かを注釈だけで引ける。
- 悪い: TypeScript の受け渡し役から Python の関数を呼ぶ橋が要り、実例のたびに Python を起こす分だけ確かめが遅くなる。
- 悪い: キーワード引数の名前が契約の項目の名前に縛られ、Python の書き方と違う名前（大文字まじり）が関数の引数に出る。
- 悪い: 関数が契約の形で返すので、道具の内側で使いやすい形と違う所は、道具の側で読み替える。
- 悪い: 道具が本当にこの関数（まとめて行う所では同じ部品）を通して読み書きしているかは、機械では止まらない。審査の担当が見る（R-901）。

## 却下した選択肢

- **道具を丸ごと回し、置き場のファイルで見る（これまでの読み）**: 読み書き 1 つの失敗の種類が道具の終了から見分けられず、失敗例を名前で照らせない。
- **読み書きのたびに、断りの形を標準出力へ出す**: 道具を回す操作の断りと混ざり、人が見る出力が変わる。
- **受け渡し役が、道具の終了の状態と文から名前を推し量る**: 推し量りの表が契約の写しになる（R-101 に反する。ADR-0012 と同じ理由）。
