# ADR-0011 境界の読み方 — どの経路にも同じ形で立つ断りは、operation の errors に挙げず、受け口のユースケースの要件が持つ

## Context

ADR-0001 の決め 8 は、失敗条件の評価順を各 operation の `errors` の並びだけが持つと決めている（R-1207）。

学び側とまなびばの受け口には、1 つの operation に属さず、受け持つどの経路にも同じ形で立つ断りがある。

- 学びの key が無い・登録簿に無い学び側の配備での断り（UC-017 の REQ-354。死活確認を含む受け持つどの経路でも、`errorCodes` の `NOT_CONFIGURED`）
- 配備にトークンの署名の秘密が無いときの、認証を要するどの経路でも同じ断り（`NOT_CONFIGURED`）
- 受け持たない経路の断りと、想定していない失敗の固定の 1 文（`INTERNAL`）

これらを決め 8 のとおりに読むと、契約の operation のすべてが `errors` の先頭や末尾に同じ項目を持つことになる。今の契約はどの operation もこれらを挙げていない。UC-017 の契約の頭のコメントがその読みを書いているが、決定の記録には無い。そのため、死活確認の operation `getHealth`（`errors: []`）は、学びの key が解決できない配備で断られる入力を、契約のどの項目も覆っていないように読める。

## Decision

- **受け持つどの経路にも同じ形で立つ断りは、各 operation の `errors` に挙げない。** 振る舞いの正本は受け口のユースケース（UC-017）の要件で、断りの形は `docs/_shared/components.yaml` の `errorCodes` が持つ。
- operation の `errors` の並びが持つ評価順（ADR-0001 の決め 8）は、**これらの断りが立たなかった要求**についての順とする。これらの断りと operation ごとの断りの前後は、契約の並びにもこの記録にも置かず、UC-017 の要件の分割クラスがテストで反証する（R-1207 の「テストクラスで反証する」の側）。
- ADR-0001 は置き換えない。決め 8 の「並びだけが持つ」が及ぶ範囲を、operation ごとの断りに限ると読む記録として重ねる。
- 1 つの operation にだけ立つ断り（発行の入口での署名の秘密の不足のように、その経路の振る舞いとして決めてある物）は、これまでどおりその operation の `errors` に挙げる。

## Consequences

- よい: 同じ断りを数十の operation に写さずに済み、形を変えるときに直す場所が要件と `errorCodes` の 2 つで済む（R-101）。
- よい: 契約の `errors` が空の operation（`getHealth` など）が、共通の断りを忘れているのか、挙げない決まりなのかを、この記録で見分けられる。
- 悪い: operation の `errors` だけを読んでも、その経路が返しうる失敗の全部は分からない。受け口のユースケースの要件も読む必要がある。
- 悪い: 契約の実例の実行（contract-run）は、これらの断りを実例として回さない。押さえるのは要件のテストだけになる。
- 悪い: ある断りが「どの経路にも同じ形で立つ」のか「その経路の振る舞い」なのかの線引きは、機械では止まらない。審査の担当が見る（R-901 の説得による統制）。

## 却下した選択肢

- **すべての operation の `errors` に共通の断りを挙げる**: 決め 8 の文字どおりだが、同じ項目と同じ失敗例が全部の operation に並び、1 か所を変えると全部を直すことになる（R-101 に反する）。
- **死活確認の operation にだけ `NOT_CONFIGURED` を挙げる**: REQ-354 が死活確認を名指ししているので局所的には合うが、同じ断りを受けるほかの operation が挙げない理由が説明できなくなる。
- **共通の断りを 1 つの operation として契約に置く**: 経路を持たない断りを operation に見立てることになり、境界に無い操作を作ることになる（R-1206）。
