# ADR-0015 実行の記録 — テストのコマンドが、画面・API・道具の 4 種類の実行を 1 つの記録に合わせて書き出す

## Context

原本 harness は、仕様と実装の対応を、コードに書く印ではなくテストの実行の記録で確かめる（`harness lint coverage`。記録は lcov 形式で、`harness.config.json` の `commands.test` が毎回書き出す）。範囲に入るソースは、ファイルが記録に載り、1 行以上実行され、名前のある関数が 1 回以上呼ばれていなければならない。

本人は 2026-11-19 に、確かめる範囲を画面・API・共有コードに加えて道具（`scripts/`）までとし、実行されないことを認める宣言（`coverage.not_run`）は使わないと決めた（`brain/PREMISES.md`）。

このプロジェクトのソースは 4 種類の動き方をする。

- テストの実行と同じプロセスで動く TypeScript（画面・API・共有コード）
- テストが子プロセスで回す Python の道具
- テストが子プロセスで回すシェルの道具
- テストが子プロセスで回す Node の道具（契約の実例の受け渡し役、`.mjs` の道具）

テストの実行の道具（vitest）が記録できるのは 1 つ目だけである。テストは、道具をリポジトリの置き場からではなく、一時の置き場へ写した物（影の根）で回すことが多い。時間の上限で打ち切られた子プロセスや、書けるファイルの大きさを絞って回した子プロセスは、記録を残さないか、壊れた記録を残す。手元の Python（3.9）には記録の道具が入っておらず、Python の依存の宣言はリポジトリに無い。手元のシェルは bash 3.2 で、実行の跡を別の出力先へ分ける機能（`BASH_XTRACEFD`）を持たない。

## Decision

- **`commands.test` は、テストを 1 回回して、4 種類の記録を取り、1 つの `coverage/lcov.info` に合わせて書き出す。** 記録のためにテストを 2 回回さない。記録の置き場（`coverage/`）は追跡せず、回すたびに空にしてから始める。
- **記録を始める環境は、テストを回すプロセス（worker）の中で足す。** テストの実行の道具を起動する前の環境には置かない（置くと、テストの実行の道具自身のプロセスまで記録され、記録が桁違いに大きくなる）。
- **同じプロセスの TypeScript**: テストの実行の道具の記録（V8 の記録）を使う。範囲のファイルは、1 行も実行されなくても記録に載せる。テストが 1 件でも落ちた回も記録を書き出す。
- **Python の道具**: 記録の道具（coverage.py）を、版を固定した開発用の依存の宣言（`requirements-dev.txt`）に置き、追跡しない仮想環境（`.venv/`。手元のパッケージも見える形）に入れる。テストのコマンドは、その仮想環境の `python3` を先に見つかる位置に置き、子プロセスの起動のたびに記録が始まるようにする。仮想環境が無ければ、テストのコマンドが作る。作れなければ、理由を 1 行で出して失敗で終わる。記録に載るのは、どれかのテストが実行したファイルだけである（1 回も実行されなかった道具は記録に載らず、門が「記録に載っていない」として止める）。
- **シェルの道具**: bash が起動のたびに読むファイル（`BASH_ENV`）で、命令を実行する直前に「ファイル・行・関数の名前」を記録のファイルへ書き足す仕掛け（`DEBUG` の trap と `functrace`）を入れる。標準出力・標準エラーには何も足さない。関数の一覧は、道具のソースの関数の定義から読む。
- **シェルの記録の選別**: テストが相手の代わりに置く偽の道具（偽の配備の道具など）の行は、記録に入れない。入れるのは範囲のソースのファイルの行だけ。
- **Node の道具**: 子プロセスに Node の組み込みの記録（`NODE_V8_COVERAGE`）を渡し、lcov に直す。
- **写しで回した道具は、写し元のファイルとして記録する。** 影の根の中のパスを、根からの相対のパスでリポジトリのファイルへ戻す。戻した先に同じ相対のパスのファイルが無い物（テストが置いた偽物）は捨てる。
- **合わせ方**: 4 種類の記録を 1 つのファイルに連ねる。門は同じファイルの記録が複数あっても行は合わせて読めるので、行ごとの回数は足し直さない。関数は、門が名前で数える。同じ関数でも、記録の道具によって名前の付け方が違う（同じプロセスの記録はソースの書き方から付け、子の Node の記録は実行系が推した名前から付ける）ので、連ねるだけだと、片方の記録で呼ばれた関数が、もう片方の記録の 0 回の行で「呼ばれていない」と門に落ちる。そこで合わせる段で、**同じファイルの同じ始まりの行の関数は同じ関数とみなし、どれかの記録で呼ばれていれば、その行の関数をどの記録でも呼ばれたと載せる。**関数を持たないファイルの印（`FNF:0`）は、それぞれの記録の道具が出した物だけを使い、合わせる段で足さない。
- **記録に原理的に載らない関数だけを、設定の `coverage.not_run` に理由つきで挙げる。** 挙げてよいのは、ブラウザのページの中で評価される関数（画面の採取の道具がページへ渡して評価させる関数）だけである。テストで動かせる関数はテストを足し、どこからも届かない関数は消す。挙げる物を足すときは、そのつど本人の承認を取る。
- **読めない記録の扱い**: 打ち切られた・書けなかった子プロセスが残した、読めない記録のファイルは飛ばし、飛ばした数を標準エラーに 1 行で出す。それで失敗にはしない（書けない状態をわざと作るテストがあり、その子の記録は必ず壊れる）。その子プロセスでしか動かないコードは記録に載らず、門が止める。
- **記録を取る・合わせる仕掛けは、テストの足場として `tests/support/coverage/` に置く。** `scripts/` の道具（入口。ADR-0014）にはしない。テストのコマンドが書き出す記録の観測できる性質（子プロセスで動いた道具の行と関数が、写しで回したときも写し元のファイルとして載る、記録を取る間も道具の標準出力・標準エラー・終了の状態・書き出すファイルが変わらない、記録には今回の実行の分だけが入る）は、門を回すユースケースの要件が持ち、テストで反証する。
- **完了の条件は、記録を取りながらの全体の実行が緑であること。** 記録を取ると子プロセスの起動が遅くなるので、時間の上限を持つテストの足場（上限の値・並べて回す数）は、記録を取りながらの実行で通るように持つ。終了のたびの門（Stop のフック）の時間の上限も、記録を取りながらの実行の時間より大きく取る。

## Consequences

- よい: 画面・API・道具のどれも、どのテストからも動かないコードが門で止まる。印（注釈）の付け忘れ・消し忘れに依らない。
- よい: 記録を取る間も、道具が外へ出す物（標準出力・標準エラー・終了の状態）は変わらないので、既存のテストの確かめを弱めない。
- 悪い: 開発用の依存が 3 つ増える（Python の coverage.py、vitest の V8 の記録の部品、Node の子プロセスの記録を lcov に直す部品）。初回は仮想環境を作るためにネットワークが要る。CI は依存を入れる段を持つ。
- 悪い: シェルの仕掛けは、記録を取る間だけ bash の特殊変数 `$_` の値を変える。道具は `$_` を使わない（使う道具を足すと、記録を取る間だけ動きが変わる）。自分で `DEBUG` の trap を張る道具は記録できない。
- 悪い: シェルの記録は「命令を実行した行」だけを数える。実行する行の一覧（1 回も動かなかった行）は、bash からは取れないので、道具のソースを読んで決める近似になる。門が見るのは「ファイルが 1 行以上動いた」「名前のある関数が 1 回以上呼ばれた」までなので、近似は判定に効かない。
- 悪い: 関数を始まりの行で合わせるので、同じ行に関数が 2 つ以上あると、片方が呼ばれただけで、その行の関数がすべて呼ばれたと載る（記録の書式が関数の位置を行でしか持たない）。
- 悪い: ブラウザのページの中で評価される関数は、テストで実際に動いていても記録に載らず、設定の宣言（理由つき）で門を通す。その関数が動いたことは、画面の採取のテストの確かめ（測った結果が出力に載る）が持つ。
- 悪い: テストのコマンドが遅くなる（子プロセスごとに記録の起動が入る。試しでは全体で 25〜39% 増）。
- 悪い: 「範囲のファイルが 1 行も動かなくても載る」のは同じプロセスの TypeScript だけで、道具は動いた物しか載らない。門の結果はどちらも違反になるが、違反の名前が違う（載っていない／1 行も動いていない）。消す手はどちらもテストを足すこと。

## 却下した選択肢

- **道具を範囲から外す（API と共有コードだけを見る）**: 違反は早く 0 にできるが、道具が検査の外に残る。本人が退けた。
- **Python の記録を標準ライブラリだけで自作する（`sys.settrace`）**: 依存は増えないが、行と関数の数え方を自分で持つことになり、数え違いが門の判定を黙って変える。広く使われている道具に任せる。
- **シェルの実行の跡（xtrace）を別の出力先へ分けて読む**: bash 4.1 以上が要る。手元の bash 3.2 では標準エラーに混ざり、標準エラーを確かめているテストが落ちる。
- **道具をテストのプロセスの中で関数として呼ぶ形に書き直す**: 子プロセスの記録は要らなくなるが、道具の入口（コマンドとして回したときの引数・出力・終了の状態）を通らないテストになり、契約の操作を入口から呼ぶ決まり（R-1204）に反する。
- **Python の記録で、動かなかったファイルも載せる（記録の道具に置き場をソースとして渡す）**: リポジトリの置き場のファイルは全部載るが、影の根の写しで回した道具が測れなくなる。写しで回すテストが大半なので採らない。
- **読めない記録が 1 つでもあれば失敗にする**: 取りこぼしは隠れないが、書けない状態をわざと作るテストがあるので常に落ちる。取りこぼしたコードは門が止めるので、失敗にしなくても隠れない。
- **ブラウザの側の実行の記録も取り込む**: 設定の宣言は要らなくなるが、ページの中の 1〜2 個の関数のために、ブラウザの記録を取る・写し元へ戻す・合わせる仕掛けと、その要件・テストが増える。本人が退けた（2026-11-20）。
- **4 種類の記録を連ねるだけにする（関数を合わせない）**: 合わせる段は単純だが、テストが呼んでいる関数が、名前の付け方の違いだけで門に落ちる。
- **記録のためだけにテストをもう 1 回回す**: 作りは単純だが、終了のたびの門の時間が倍になる。
