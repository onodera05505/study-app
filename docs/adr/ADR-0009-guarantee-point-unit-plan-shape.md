# ADR-0009 保証点 — 単元の構成の形（BR-057・BR-058）は DB の制約、学ぶ順の組み立ては門の 1 か所で守る

## Context

資格対策の単元の構成には、守る場所が 2 つある決まりが並んでいる。

- 形の決まり: 全体像とまとまりの名前と説明が空でない、論点が自分自身を前提にしない（BR-058）。まとまりの順とまとまりの中の順は 1 から数え、1 つの順に論点を 1 つだけ置く（BR-057）。単元の構成の門 `scripts/check_unit_plans.py` と、単元の構成を持つ表の制約（スキーマ正本 `src/server/db/schema.ts`）の両方が見ている。
- 順の決まり: 単元の学ぶ順は、まとまりを並びの順に、まとまりの中は論点の並びの順につないだ順（BR-057）。表は並びの番号を持つだけで、つなぎ方は持たない。

R-704 は、複数の箇所で強制できる規則について、どの箇所を除くと正しさが壊れるかで保証の SSOT を決めて記録すると言う。門は配る前の検査で、門を通さずに表へ入る経路（手元の直接の投入、門を回さない道具）には効かない。表の制約は、どの経路で入っても断る。

## Decision

- **形の決まりの保証点は DB の制約**とする。守る箇所は `src/server/db/schema.ts` の `ck_unit_plans_overview_not_empty`・`ck_unit_groups_name_not_empty`・`ck_unit_groups_description_not_empty`・`ck_topic_prerequisites_not_self`（BR-058）と、`ck_unit_groups_group_no_positive`・`ck_unit_group_topics_position_positive`・`uq_unit_group_topics_position`（BR-057）。それぞれに `@implements` を付け、検査（スキーマの制約と規則の対応）が外れを止める。門の同じ判定は、表に入る前に書き手へ理由を返すための早い検査で、保証点ではない。
- **学ぶ順の組み立ての保証点は `scripts/check_unit_plans.py` の学ぶ順を組み立てる 1 か所**とする。単元の構成の門と、書き直しの束を作る道具は、この 1 か所を呼んで順を得る。別の場所で順を数え直さない。数え直しを止める機械の検査は無く、審査の担当が見る（R-901 の説得による統制）。

## Consequences

- よい: 門を通らない経路で入った単元の構成も、形が崩れたまま利用者に届かない。
- よい: 門と束と一覧が別々に順を数えて食い違う余地を、呼ぶ先を 1 つにすることで減らす。
- 悪い: DB の制約が断るのは投入の途中で、門より遅い。門を外すと、書き手は投入が止まるまで形の崩れに気づけない。
- 悪い: 同じ形の判定が門と表の 2 か所にあり、片方だけを変えると食い違う。食い違いを止める検査は無い。
- 悪い: 学ぶ順を別の場所で数え直す変更は、機械では止まらない。

## 却下した選択肢

- **形の決まりの保証点を門にする**: 門を通さない経路で表に入った行を止められない。門を外しても表の制約が残れば正しさは保たれるが、逆は成り立たない。
- **形も順も両方を保証点にする**（ADR-0006 と同じ形）: 形の決まりは非対称が立つ（表の制約だけで足りる）ので、両方とする理由が無い。順の決まりは表が持てない。
- **学ぶ順の組み立てを DB の側（ビューや問い合わせ）に置く**: 門と束を作る道具は投入の前に順を要るので、DB に入る前に使えない。
