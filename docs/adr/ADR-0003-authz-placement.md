# ADR-0003 認可の置き場 — まなびばがアカウントと権限の正本、学び側は Bearer のトークンだけを見る

## Context

§4・§15（v0.8、2026-09-17）で「まなびばが認証と権限の正本。学び側はまなびばからのログインだけを受ける」と決めた（経緯は `docs/作業ログ_2026-09-17_SSO.md`）。現物: まなびばは Cookie セッション（`mb_session`、30 日、DB の `sessions` で失効）と `accounts.role`（ADMIN／MEMBER）・`grants`（学びごとの権限）を持ち、`/logout`・`/me/*`・`/admin/*` を経路の列挙で `requireLogin`、`/admin/*` はさらに ADMIN の判定。学び側は `/api/auth/*` と `/api/health` 以外の全経路を 1 本の認証ミドルウェアで Bearer JWT 必須にし、通った要求だけ `users` の本人（`sub`）として扱う。学び側に入る唯一の経路は使い捨てコードの交換（`/sso/start` → `POST /api/auth/sso` → まなびば `POST /api/sso/exchange`。共有秘密を本文に載せ、発行時と交換時の両方で権限を確かめる＝BR-003）。学び側のパスワードログインと登録は、まなびばの場所が設定された配備では 404 で受けない。

## Decision

現物のとおり記録する: 権限の正本はまなびばの `accounts`・`grants`。学び側はトークンの中身（`sub`・`name`・`role`）だけを信じ、権限の判定を持たない（権限はコードの発行と交換の時点でまなびばが確かめる）。本人の資源の判定（BR-018）は学び側の各経路が `user_id` で絞る。守る箇所: 学び側 `src/server/index.ts` の認証ミドルウェア（BR-001 の enforced_at）、まなびば `portal/src/index.ts` の `requireLogin` と ADMIN の判定、`portal/src/index.ts` の交換（BR-003）。

## Consequences

- よい: 権限を付け外しする場所が 1 つ（まなびば）。学び側は秘密を 2 つ（JWT・共有秘密）持つだけで、アカウントの表を持たない。
- 悪い: 権限を外しても、既に配った学び側のトークンは期限（14 日）まで通る（UC-014 の本人の決定「失効させない」と同じ性質。管理者の再設定はまなびばのセッションを切るだけで学び側のトークンは切れない）。学び側の JWT の秘密が未設定だと開発用の既定値に倒れる（OQ-59。移行後の最初の修正）。まなびばの `requireLogin` は経路の列挙なので、経路を足したときに列挙を忘れる余地がある（R-901 の説得的統制）。

## 却下した選択肢

- **学びごとに登録とログインを持つ（前の形）**: 学びが増えるたびにアカウントが増え、権限を外す場所が学びの数だけになる。2026-09-17 に廃止（`docs/作業ログ_2026-09-17_SSO.md`）。
- **学び側で権限を再確認する（まなびばの grants を都度問い合わせる）**: 学び側がまなびばに依存する呼び出しが毎要求に増える。コードの交換時に確かめる形にし、失効の遅れ（最大 14 日）を受け入れた。
- **共有秘密をヘッダに載せる**: 現物は本文の `secret`。比較の記録は無い（移行時に付した記録）。
