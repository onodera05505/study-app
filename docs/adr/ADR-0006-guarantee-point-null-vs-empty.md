# ADR-0006 保証点 — 「取得前と結果が空を区別する」（BR-015）は応答と画面の両方で守る

## Context

BR-015「一覧・集計・進行中のテストの案内は、取得前と結果が空を区別して示す」の `enforced_at` が 2 か所（`scripts/check_api.py` が応答の `null`／`[]` を見る、`scripts/check_source.py` が画面の `useState([])` を止める）になっている。R-704 は「複数の点で守れる規則は、どれを外すと正しさが壊れるかの非対称で保証点を 1 つ決める」と言う。2026-09-14 の事故（読み込み中に「該当する論点がありません」と出た。中央 reports/15）は画面側の初期化が原因で、応答が区別していても画面が空配列で初期化すれば同じ症状が出る。逆に画面が区別しても応答が `[]` と `null` を混ぜれば同じ症状が出る。

## Decision

両方を保証点とする（非対称が立たないため）。応答側は `check_api.py` の `check_empty_lists`（空の一覧が `[]`、未取得に当たる値を返さない）、画面側は `check_source.py`（一覧の `useState` を `[]` で初期化しない。`// 空で開始可` の印で例外）。どちらか一方を外した変更は差し戻す。守る箇所: 2 本の検査スクリプト（`npm test` と deploy の門が回す）。

## Consequences

- よい: 事故の再発を 2 層で止める。
- 悪い: 同じ規則の検査が 2 か所にあり、片方の緩和に気づきにくい（stop_gate の緩和検知は `trace-check` の有無しか見ない）。

## 却下した選択肢

- **応答側だけを保証点にする**: 画面が空配列で初期化すれば応答が正しくても誤表示が出る（2026-09-14 の事故そのもの）。
- **画面側だけを保証点にする**: 応答が `null` と `[]` を混ぜれば画面の区別が成り立たない。
