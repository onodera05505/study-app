## 立てた計画と、その理由

### 優先順位の判断

限られた予算で最終到達点に近づけるため、以下の順で進める。

1. **シラバスのマスタ化** — 分類の受け皿が無いと何も分類できない。最初に要る
2. **複数回分の過去問抽出** — 設計の根幹である「出題頻度＝重要度」は、1回分100問では成立しない（どの論点も出現1回になる）。頻度に意味を持たせるには最低でも1,000問規模が要る
3. **分類と論点の抽出** — ここで初めて重要度が算出できる
4. **教材（解説・周辺知識）の生成**
5. **アプリ本体** — 学習機能・練習テスト機能・過去問実践機能

### なぜ全29回を先に抽出しないか

抽出は1回分あたりのコストが大きい。全28回分を先に流すと、アプリ本体に手が回らなくなる。
アプリはスクリプトで再生成できないが、**残りの回の抽出はスクリプトを再実行するだけで後から足せる**。
そのため「頻度が意味を持つ最小限の量」を先に確保し、アプリを作り、余力で回数を増やす方針とする。

新しい回ほどシラバスの改訂を反映しており最短合格には有用なので、**新しい年度から順に**取り込む。

### 予算配分の目安

| 用途 | 配分 |
| --- | --- |
| シラバス・分類・論点抽出 | 少なめ |
| 過去問の追加抽出 | 中（回数は残予算で調整） |
| 教材生成 | 中 |
| アプリ本体 | 多め |

### 1. シラバスのマスタ化（完了）

`scripts/parse_syllabus.py` を作成。シラバス Ver.6.5 の PDF（テキストレイヤーあり）から
**3分野 / 9大分類 / 23中分類 / 63項目**を抽出し、`data/syllabus.json` に落とした。

途中で2回つまずいた。

- 項目17と60だけ、番号「17.」と項目名が**別の行に分かれていた**。番号だけの行を検出して
  次行を項目名として拾う分岐を追加
- 用語例ブロックの終端判定が「17.」を拾えず、項目17以降が丸ごと欠落。終端の正規表現から
  ドット後の空白要求を外して解決

**大きな収穫**: シラバスには IPA が「知識として習得すべき用語」として挙げている
**用語例が1,119語**含まれていた。論点マスタを自分で発明せず、これを土台にできる。
網羅性の根拠として公式の裏付けが得られる。

なお、項目23・33・45・47・56 の5項目には用語例が存在しない。原文を確認済みで、
パーサーの取りこぼしではない。

### 2. 過去問の追加取り込み（3回分・300問完了）

令和6・7・8年度の3回分を抽出。**すべて 100/100、抽出テキストだけで解いた正答率も
3回とも 100%、解答不能の申告0件**。

読み取りの分割単位を6ページから11〜12ページに広げてコストを下げたが、品質は落ちなかった。

**仕様書が効いた**: 令和6年度では句読点のブレ（1チャンクだけ「．」）が出たが、
`scripts/prompts/extract_questions.md` を先に読ませた令和7・8年度では**正規化ゼロ**。
チャンク間のブレも警告ゼロだった。仕様を文書に固定する方針が実際に機能している。

### 3. 分類と論点の抽出（300問完了）

`scripts/prompts/classify_questions.md` を作成し、300問をシラバス項目と論点に紐づけた。
結果は `data/topics.json`（240論点）。

**予想どおり表記揺れが出た。** 複数の担当が独立に命名するため避けられない。

- 「IT ガバナンス」と「ITガバナンス」（空白の有無）
- 「アジャイル」と「アジャイル開発」
- 「システム監査の手順」と「システム監査」

`scripts/build_topics.py` で2段構えの対策を入れた。

1. **照合キーによる自動統合** — NFKC 正規化し空白・記号を除いた文字列で突き合わせる。
   「IT ガバナンス」問題はこれで自動的に解決
2. **別名辞書による手動統合** — `data/topic_aliases.json`。文字列が違うものはここで寄せる

似ているだけの候補（「DNS」と「DNS キャッシュポイズニング」など別物）は**自動統合せず
報告にとどめる**設計にした。誤統合のほうが害が大きいため。

分類の判断で項目が割れた論点も多数決で決め、割れた事実を警告として出すようにした。

**注意点**: 分類担当が全員指摘していたが、著作権法・ランサムウェア・ゼロトラストなどの
**頻出テーマがシラバスの用語例に無い**。240論点のうち87が新設。回数を増やすと新設論点が
増え続けるので、別名辞書の育成が継続的に必要になる。

### 4. アプリ本体（動作確認済み）

Hono + Cloudflare Workers + D1 + Drizzle + React SPA。Workers Assets で API と静的配信を
1デプロイにまとめた。

実装した3機能:

- **学習機能** — 分野→中分類→論点。既定の並びは出題頻度順。論点詳細で解説・周辺知識・
  その論点が出た過去問を読み、理解度を3段階で記録
- **練習テスト機能** — 論点ドリル / 分野別演習 / 弱点復習
- **過去問実践機能** — 公開回をそのまま100問120分で通す、または全範囲からランダム100問

**前身アプリ から引き継いだ設計**: 出題時スナップショット（出題時点の問題文・選択肢・正解を
JSON で固定）と、中断・再開時のズレ防止（クライアントの位置とサーバの位置が食い違ったら
採点しない）。どちらも動作確認済み。

**前身アプリ から変えた点**:

- 合格判定を正答「数」ではなく**正答率**にし、さらに**分野別**の判定を入れた。
  本番の合否が分野単位の AND 条件なので、分野別が出せないと最も重要なフィードバックが出せない
- 出題数・制限時間・除外条件・合格ラインを `app_settings` に出した。前身アプリ はコードに
  埋まっていて管理画面から変えられなかった
- 放置セッションが新規開始を塞ぐ問題に対し、409 で止めるだけでなく**進行中の内容を返して
  再開か破棄を選ばせる**ようにした

つまずいた点2つ:

- **D1 のバインド変数上限**。過去問実践は100問を一度に INSERT するため上限を超えて失敗。
  16行ずつに分割して `db.batch` でまとめる形に修正
- **SPA フォールバックで 500**。`ASSETS.fetch()` が返す Response はヘッダが immutable で、
  後段の secureHeaders が書き込もうとして落ちていた。複製してから返すよう修正

検証として、**令和6年度100問を正解表どおりに自動回答して満点・全分野100%・合格判定**まで
通ることを確認した。ブラウザでの表示も確認済み。

### 5. 教材の生成（実行中）

`scripts/prompts/write_materials.md` を作成し、240論点の解説・周辺知識を執筆中。

**方針**: 市販テキストのような網羅的解説ではなく、**その論点が試験でどう問われるかを軸に、
理解に必要な周辺知識を添える**。各執筆者には「その論点が実際に出題された過去問」を渡し、
それを見てから書かせている。これが「過去問暗記にしない」ための具体的な仕掛け。

出典表示の義務が生じるため、**過去問の問題文をそのまま引用させない**ことも仕様に明記した。

### 教材生成でつまずいた点（アプローチ変更）

最初は1バッチ30論点で8体を走らせたが、**全滅した**。1回の Write で3万字近い JSON を
書かせようとして、全エージェントが応答の途中で接続を切られた。

**1バッチ8論点に細分化して再投入**したところ安定した。仕様書にもこの経緯と
「これ以上増やさないこと」を明記した。同じ失敗を繰り返さないため。

### 設計上の欠陥を2つ修正

教材を DB に入れる段になって、**放置すると後で必ず壊れる問題**が2つ見つかった。

**1. 論点 ID が並び順に依存していた**

`topics.json` は出題頻度の降順で並ぶ。ID を並び順から採っていたので、**回を追加すると
順位が変わり、ID が別の論点を指してしまう**。ユーザーの理解度（progress）も、執筆済みの
教材も、まとめて別の論点に紐づく。

照合キーごとに採番した ID を `data/topic_ids.json` に残し、一度振った ID は使い回さない
方式に変更した。今回の採番は現在の並び順と一致するので、執筆済みの教材はそのまま使える。

**2. 初期データ投入が外部キー制約で失敗していた**

`DELETE` してから `INSERT` する作りだったが、`progress` や `session_questions` が
参照している行を消すことになり失敗していた。しかも `PRAGMA foreign_keys = OFF` は
D1 では効かない。

**UPSERT（`ON CONFLICT DO UPDATE`）に変更**。教材を入れ替えても学習の進捗と受験履歴が
飛ばない。これは「何度でも再実行できる」という当初の意図どおりの挙動になった。

### UI のバグ1件

論点詳細で、図表のない過去問に「0」が表示されていた。`hasFigure` が D1 から 0/1 の
**数値**で来るため、`{q.hasFigure && ...}` が偽のときに `0` を描画していた。
真偽値に変換して修正。

### 教材の検証スクリプトを追加

`scripts/check_materials.py` を作成。カバレッジ・論点との対応・分量・Markdown の混入・
句読点の混入に加えて、**過去問の原文をそのまま写していないか**を調べる。

これが効いた。「〜として最も適切なものを選ばせる問題が出ました」のように、出題の
説明をするつもりで**問題文をそのまま30字以上写している箇所**が複数見つかった。
引用にあたると出典表示の義務が生じるので、言い換えに直した。

人が読んで気づける類のものではない（読むと自然な日本語に見える）ので、機械的に
検出できるようにしておく価値が高い。

### バンドル再分割時の事故

教材のバッチを30論点から8論点に切り直したとき、**旧分割で動いていたエージェントが
まだ生きていた**。担当ファイルが実行中に差し替わり、書き上げた内容と担当範囲が
食い違う事態になった。

幸い、論点 ID 自体は安定しているので**内容が壊れることはなかった**（担当範囲が
重複しただけ）。エージェント側も差し替えに気づいて報告してきたため、旧分割で
書かれた30論点分を退避ファイルから回収して取り込めた。

**教訓**: 実行中のエージェントが読むファイルを書き換えない。やり直すときは
新しい名前（`remaining_*.json`）で作る。

## 図を含む問題の扱い（追加対応）

「問題文に画像が載っていて、それを見ないと解けない問題はないか」という指摘を受けて調査した。

### 調べた結果

400問のうち**64問が図表を含む**。内訳は表が54問、擬似言語プログラムが6問、
図（矢印や箱で描かれたもの）が3問、その他1問。本文が実際に「図」を参照しているのは5問。

**すべて文章に書き起こしてあり、品質検証では64問すべてが「文章だけで解答可能」と
判定されていた。** 実際、信頼性ブロック図の問題（令和6年度 問67）は原本の画像と
照合したところ、「左から線が入り分岐して2つの箱が並列に接続され、合流後に直列で
1つの箱」という説明で過不足なく、稼働率 0.864 が計算できる内容だった。

### それでも画像を足した理由

**解けることと、学習しやすいことは別。** ブロック図やアローダイアグラムを
「左から線が入り分岐して…」と文章で読むより、図を見たほうが速い。本番も図で出るので、
図で慣れておくほうが実戦的でもある。

### やったこと

1. 図として描かれている13問を特定（表と擬似言語以外を機械的に判別）
2. ページ画像から**図の矩形領域の座標**を読み取らせ、`data/figures/boxes.json` に集約
3. `scripts/crop_figures.py` で原本 PDF から図だけを 200dpi で切り出し、
   `public/figures/<exam>-q<N>.png` に保存
4. `past_questions.figure_image` 列を追加し、出題時スナップショットにも含めた
5. 学習画面・演習画面・結果画面の3箇所で画像を表示（共通コンポーネント `Figure`）

**表には画像を付けていない。** Markdown 風の書き起こしのほうが折り返しに強く、

## スマホ対応と本番デプロイ

### スマホ対応

想定は iPhone の 390px 幅。`src/client/styles.css` に 640px / 400px の2段階の
メディアクエリを足した。主に直したのは4点。

1. **ヘッダー** — ナビが折り返すとヘッダーが3段になり本文が押し下げられるので、
   ブランドを1行目、ナビを2行目の**横スクロール**にした
2. **論点一覧の行** — 出題回数のバッジは左に残し、論点名と分類を縦に積んだ
3. **分野別スコアの表** — `.table-wrap` で包み、表だけを横スクロールさせる
4. **タップ領域** — ボタンと選択肢に `min-height: 44px` を確保

**Chrome のウィンドウ最小幅の制約で 606px までしか絞れなかった**ため、
実機幅の確認は本番デプロイ後に回した。代わりに、コンテナ幅を 375px に強制して
はみ出し要素をプログラムで検出する形で検証した（はみ出しゼロ）。

#### 図が小さくなりすぎる問題

375px 幅では 660px の図が 299px まで縮む。擬似言語プログラムのように文字が
詰まった図は読めない。**タップで原寸に切り替えて横スクロールで読める**ようにした。

実装時に1つ引っかかった。原寸表示にすると図だけでなく**親カードごと横に広がった**。
論点一覧が CSS グリッドで、グリッドの子は既定で min-content 幅を下回れないため。
`.list > li { min-width: 0 }` で縮小を許可して解決。

### 本番デプロイ

**https://study-app.onodera-yudai.workers.dev**

D1 を作成し、`JWT_SECRET` と `SIGNUP_CODE` を secret として設定、マイグレーションと
初期データ（1,652文・1.9MB）を投入して Worker をデプロイした。

新規登録は合言葉つきにした。身内向けなので、URL を知っただけでは登録できない状態にする。

#### 本番でだけ起きた不具合

**ログインが 500 になった。** ローカルでは動いていた。ログを取ると原因は明確だった。

```
NotSupportedError: Pbkdf2 failed: iteration counts above 100000 are not supported (requested 210000).
```

**Cloudflare Workers は PBKDF2 の反復回数を 100,000 までしか受け付けない。**
ローカルの miniflare はこの上限を課さないので、本番に出すまで分からなかった。

上限いっぱいの 100,000 に変更し、`build_seed.py` 側の値も揃えて管理ユーザの
ハッシュを作り直した（反復回数は保存文字列に含まれるので、既存ハッシュのままだと
検証時に 210,000 を要求して失敗し続ける）。あわせて管理ユーザの投入を
`INSERT OR IGNORE` から UPSERT に変えた。

**推測で「CPU 時間の超過だろう」と決めつけずにログを取ったのが正解だった。**
CPU 制限だと思って反復回数を下げすぎるところだった。

#### もう1つの引っかかり

動作確認スクリプトが 403 を返した。アプリの不具合ではなく、**Cloudflare のボット対策が
Python の既定 User-Agent を弾いていた**。`curl` は通る。ブラウザ相当の User-Agent を
付けたら通った。

#### ローカル環境が壊れた件

`wrangler.jsonc` の `database_id` を本番の UUID に変えたところ、**ローカルの D1 も
別のデータベースに切り替わって空になった**（ローカルの状態は database_id ごとに
保存されるため）。migrations と seed を流し直して復旧。README に注記した。

## 公開 URL からアカウント名を消した

最初のデプロイ先 `study-app.onodera-yudai.workers.dev` に**アカウント名が入っていた**ため、
URL を変更した。

### なぜ単純に変えられないか

workers.dev の URL は `<worker名>.<アカウント共通サブドメイン>.workers.dev` という形。
名前が入っているのは**アカウント共通サブドメイン**のほうで、ここを変えると
**同じアカウントの他の Worker の URL も一斉に変わる**。

確認したところ、このアカウントには他に3つの Worker があり、いずれも workers.dev で
公開されていてカスタムドメインは無かった。

```
同アカウントの Worker が すべて workers.dev 公開
カスタムドメイン … なし
```

**他の Worker は稼働中の別システムのため、アカウント共通サブドメインの変更は
行わなかった。** URL が変われば、ブックマークや設定に埋め込まれた参照が一斉に壊れる。
本人に確認せずに踏むべき操作ではない。

### 採った方法: Cloudflare Pages へ移す

Pages の URL は `<プロジェクト名>.pages.dev` で**アカウント名を含まない**
（同アカウントの別プロジェクトが実例）。他に影響を出さずに名前を消せる。

**新しい URL: https://itpass-study-c91.pages.dev**

Hono のコードはそのまま使える。Pages の advanced mode（`_worker.js` を置く方式）なら
Worker をそのまま載せられ、`env.ASSETS` も Pages 側が提供してくれる。

手順で引っかかった点:

- **Pages は wrangler 設定ファイルのカスタムパスに対応していない**（`--config` が使えない）。
  Workers 用の `wrangler.jsonc` を一時退避してからデプロイする必要がある。
  この手順を `scripts/deploy-pages.sh` に固めた
- D1 と secret は Pages プロジェクト側に別途設定が要る（API の
  `deployment_configs.production` に `d1_databases` と `env_vars` を入れる）

### 旧 URL の扱い

`study-app` Worker の workers.dev だけを無効化した（404 になることを確認）。
**他の3つの Worker が有効なままであることも確認済み。**

Worker 自体は残してあるので、Pages 側に問題が出たら戻せる。不要になったら削除してよい。
