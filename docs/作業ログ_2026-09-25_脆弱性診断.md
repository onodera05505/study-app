# 作業ログ 2026-09-25 脆弱性診断（点。当時の記録）

本人の要求「このアプリを就活で社外に見せたいので脆弱性診断を」。対象は自分のアプリ（まなびば＝認証の正本、学び側 8 Pages、D1、Pages の設定、依存）。**コードの読み（サーバ全ファイル・入口・描画）と、本番への非破壊の確認（ヘッダ・未認証アクセス・秘密の設定）**で見た。侵入テスト（総当たり・負荷）はしていない。

## 結論
**外から入られる穴は見つからなかった。** 設計の筋（認証の正本を 1 か所に、API は全部 Bearer 必須、SQL は全部パラメータ、HTML を流し込む口を作らない、秘密は secret で持つ）が通っている。直したのは小さな 3 点、残る指摘は「運用で足すもの」。

## 残る指摘（運用で足す。本人の判断）
| 重さ | 指摘 | 手当て |
| --- | --- | --- |
| 中 | **ログインの総当たり対策が無い**（まなびば `/api/login`。PBKDF2 10 万回で 1 回は重いが、回数制限は無い） | Cloudflare の WAF ルール（Rate limiting、無料枠で 1 本）を `manabiba-5oz.pages.dev/api/login` に。またはアカウント単位の失敗回数を D1 に持ってロック（要件と migration が要る） |
| 低 | JWT は取り消せない（14 日）。まなびばでパスワードを変えても学び側のトークンは生きる | 学び側に「発行時刻より前のトークンを拒む」列を足すか、TTL を短く（要件） |
| 低 | 学び側のトークンは `localStorage`（XSS が起きれば持ち出せる） | CSP と innerHTML 不使用で XSS の口が無いことが前提。維持する（`check_render.sh` と Markdown の記法の門） |
| 低 | 認証ミドルウェアが毎リクエスト `daily_visits` に INSERT（費用と DoS 面） | 1 日 1 回に間引く（KV か日付のメモ） |
| 情報 | 静的ファイルに `access-control-allow-origin: *`（Pages の既定）。API 応答には無い | 影響なし |
| 情報 | 診断は本番の配信経路で行った（`reports/67` の教訓: dev サーバで診断すると `_headers` が効かない） | 再診断も本番 URL で |

## 就活で見せるときの言い方
「認証は 1 か所（まなびば）に寄せて学び側は使い捨てコードの交換だけ、API は全部トークン必須で SQL はパラメータ、HTML を流し込む口を作らず CSP で固め、秘密は環境の secret。残る課題はログインの回数制限で、WAF で足す予定」。
