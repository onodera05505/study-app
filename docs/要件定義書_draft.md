## 1. 目的とゴール

### 目的

**何かに特化した学び（資格・分野・職種・入社先の業務）について、「何が必要か」を定義し、ロードマップを敷き、
コンテンツを作って学べる仕組み**を作る（2026-09-14 に v0.4 で広げた。それまでは IT パスポート合格が目的）。
IT パスポートと応用情報 午前は、その第 1 の実例。出題頻度＝重要度という優先信号がただで手に入る対象から始めた。
身内・友人・会社の人が気軽に使えるものにする（公開範囲は**所有者が権限を与えた人**。2026-09-17 v0.8 で「身内限定」から言い換え。§11-5・§15）。

- 例: SES の中間営業なら、その会社の e ラーニング相当のロードマップが出る。銀行の特定の事務なら、その事務に特化した内容が出る
- 資格以外では「出題頻度」が無いので、代わりの優先信号（一次資料の目次の交差数・面接や現場で問われる頻度・依存関係・到達基準からの逆算）を対象ごとに定める。**ここがロードマップ生成の設計の中心**（§13）
- 正解表も無いので、生成物の誤りを止める門を先に置く（出典必須・別担当による確認問題の解答・引用検査）。門の無い生成物を学習者に出さない

（以下は IT パスポートを実例として書いた当時の記述。構造の説明として残す）
IT パスポート試験に**最短で合格する**ための学習アプリ。身内・友人・会社の人が気軽に使えるものにする。

### ゴール

- 公開されている過去問を網羅的に潰せること
- ただし**単なる過去問暗記にしない**。各問題の背後にある論点と周辺知識を添えて、「ちゃんと学んでいる」実感が持てる状態にする
- 学習の優先順位が**データで決まる**こと（後述の出題頻度による重要度算出）

### あえてやらないこと

市販テキストのような体系的網羅は目指さない。テキストは「テキストとしての完成度」が優先されるため不要な内容が混ざり、合格までの最短経路にならない。**出題実績のある論点を、頻度順に潰す**のがこのアプリの立場。

## 2. 事実確認の結果（前提の修正）

設計前に IPA 公式で裏を取ったところ、当初の想定と食い違う点が2つ見つかった。**ここが設計を大きく左右する。**

### 2.1 「過去10年以上の過去問を一式」は入手できない

IPA が公開しているのは **29回分・約2,900問**（平成21年度春期〜令和8年度分）。しかも CBT 方式に移行した平成24年度以降は、**年度あたり100問しか公開されない**。実際に出題された問題の大半は非公開。

| 期間 | 公開のされ方 |
| --- | --- |
| 平成21〜23年度 | 筆記方式の試験問題（6回分） |
| 平成24〜令和2年度 | CBT のうち**特別措置試験**の問題を各100問（17回分） |
| 令和3年度以降 | 実際に出題した問題100問を年1回（6回分） |

→ 母数は約2,900問で頭打ち。「全過去問を網羅する」ことは**現実的な目標として達成可能**（むしろ量として手頃）だが、それだけで本番の出題を覆えるわけではない。だからこそ §3 の論点ベースの周辺知識が効いてくる。

出典: https://www3.jitec.ipa.go.jp/JitesCbt/html/openinfo/questions.html

### 2.2 PDF のダウンロードは容易。ただし問題冊子はテキストを持たない（実測で確認済み）

**29回分・58ファイル・181MB を実際に一括ダウンロードして全数調査した結果:**

| 項目 | 問題冊子（`_qs.pdf`） | 解答例（`_ans.pdf`） |
| --- | --- | --- |
| ダウンロード | 問題なく取得できる。パスワード不要で開ける | 同左 |
| ページ数 | 44〜56頁（全29回で計 **1,450頁**） | 各1頁 |
| **テキスト文字数** | **全29回すべて 0 文字** | 670〜1,050 文字 |
| 中身 | 1頁につきスキャン画像1枚（JPEG, 1432×2026px ≒ 175dpi 相当） | 通常のテキスト（フォント埋め込み） |
| 機械抽出 | **不可**。画像→テキスト化が必要 | **可能** |

つまり「PDF を落として読み込む」だけでは問題文が取れない。**ダウンロードが容易なことと、中身が読めることは別問題**だった。

なお PDF には暗号化（`/Encrypt`）が掛かっているが、ユーザーパスワードは空なので閲覧・レンダリングは普通にできる。落ちているのはコピー権限のフラグで、そもそもコピーすべきテキストが存在しない。IPA も「公表している PDF 以外の電子データの提供はできません」と明言しており、CSV/JSON での入手手段は無い。

### 2.3 ただし画像として読むことは十分に実用的（実証済み）

ページを画像にレンダリングしてビジョンモデルに読ませたところ、**損益計算書の表組みを含む問題を、選択肢まで完全に判読できた**（令和6年度 問8・問9 で確認）。1,450頁という規模も現実的な範囲。

さらに **解答例からの正解抽出は既に完成している**。全29回で **2,900/2,900問**、欠番ゼロで抽出できた（`scripts/extract_answer_keys.py`、成果物は `data/answer_keys.json`）。

→ 取り込みパイプラインのうち**正解データ側は完了済み**。残るは問題文・選択肢の画像→テキスト化で、これは正解表と突合して検証できる。**依然として本プロジェクト最大の実装コストだが、見通しは立っている。**

### 2.4 各問題に分野タグは付いていない

IPA の公開問題には分野・分類の情報が無い。分類はアプリ側で独自に付与する必要がある。

ただしこれは悪い話ばかりではない。**シラバス Ver.6.5 が既製の分類マスタとして使える**（§3.2）。

### 2.5 合格判定は IRT なので正確な再現は不可能

- 合格基準は「総合評価点 600点以上（1,000点満点）**かつ** ストラテジ系・マネジメント系・テクノロジ系の各分野別評価点が 300点以上」の **AND 条件**
- スコアは **IRT（項目応答理論）** で算出され、**換算式は非公開**
- 100問のうち **8問は採点対象外**（今後の出題を評価するためのプレテスト問題）。評価対象は92問（ストラテジ32・マネジメント18・テクノロジ42）

→ 模試の点数は**素点による近似**にしかならない。UI 上で「公式スコアとは算出方法が異なる」旨を明示する。

出典: 試験要綱 Ver.5.6 https://www.ipa.go.jp/shiken/syllabus/rcu1hd00000141gq-att/youkou_ver5_6.pdf

## 3. 中核となる設計判断

### 3.1 過去問中心ではなく「論点」中心にする（重要）

素直に作ると「過去問1問ごとに解説を付ける」構造になるが、これは**同じ知識の解説が何十個も重複する**うえ、学習単位が問題になるので「過去問暗記」そのものになってしまう。

そこで **論点（知識項目）を学習の単位に据え、過去問とは多対多で結ぶ**。

```
論点（例: 「損益分岐点」）
  ├─ 解説・周辺知識  ← 学習する対象はこっち
  └─ 紐づく過去問: 平成24春 問3 / 平成28秋 問11 / 令和3 問7 …（M:N）
```

これで得られるもの:

1. **重要度が実データで決まる** — 論点に紐づく過去問の件数がそのまま出題頻度になる。「29回中12回出題」の論点から潰せば、それが最短経路そのものになる
2. **解説が重複しない** — 同じ論点を問う複数の問題が1つの解説を共有する
3. **暗記にならない** — 学習画面で論点を理解してから、その論点の過去問を解く順序になる
4. **周辺知識の置き場所ができる** — 「この論点を理解するために必要な前提」を論点に紐づけられる

### 3.2 テーマ分けはシラバスに乗る

分類体系を自前で考える必要はない。IT パスポートのシラバス Ver.6.5 が **3分野 → 9大分類 → 23中分類 → 63項目** の階層を持っている。これをそのままテーマ分けに使う。

| シラバスの階層 | アプリでの扱い |
| --- | --- |
| 分野（ストラテジ系／マネジメント系／テクノロジ系） | 最上位。分野別評価点の単位でもある |
| 大分類（9個） | テーマ |
| 中分類（23個） | カテゴリ |
| 項目（63個） | 論点をぶら下げる単位 |

自前分類より圧倒的に良い理由は、**分野別評価点の判定にそのまま使える**こと。合否条件が分野単位なので、分類が分野に接続していないと「マネジメント系が足りない」という最も重要なフィードバックが出せない。

出典: シラバス Ver.6.5 https://www.ipa.go.jp/shiken/syllabus/omgdg50000005kn1-att/syllabus_ip_ver6_5.pdf

なお、**大分類・中分類ごとの出題数配分は IPA が公表していない**。配分は自前で集計した過去問の実績から算出する（これも論点中心モデルの副産物）。

## 4. 利用者と権限（2026-09-17 v0.8 で決定）

- **アカウントは 1 人 1 つ**で、正本は入口「まなびば」（§15）。学びごとのアカウントは持たない
- **役割は 2 つ**: 所有者＝管理者（アカウントを作る・権限を付け外しする・パスワードを再設定する）と、利用者（与えられた学びを使う。自分のパスワードを変えられる）
- **権限は「アカウント × 学び」**。管理者がアカウント作成時に付け、あとから変える。自己登録（合言葉）は廃止し、管理者が作る
- 学び側（ip / ap / itc / mkt / msg）は、まなびばからのログインだけを受ける。本番では学び側のパスワード画面・登録画面・合言葉は無い。ローカル（まなびばの場所が設定されていない環境）に限り、開発と API 検査のために従来のパスワード登録と合言葉が動く（§15）。進捗と受験履歴は学びごとの DB に残り、メールアドレスで同じ人と分かる
- 管理画面はまなびばの中に置く（v0.3 で「管理者ダッシュボードは不採用」としたが、権限を所有者が付け外しするには要るので v0.8 で最小のものを採用。一覧・作成・権限の付け外し・パスワード再設定・削除だけ。統計や CSV は作らない）
- 管理の決まり
  - 管理者がアカウントを作るときは、メール・名前・初期パスワード・学びの権限・役割を決める。作るときに管理者も選べる。役割は管理者か利用者のどちらかで、それ以外は受け付けない。本文の検証は対象の存在の確認より先に行う
  - 管理者は他人の名前・役割・学びの権限を変えられる。権限は送られた一覧に総入れ替えする
  - 管理者は自分の役割を利用者に下げられず、自分を削除できない（管理者が 0 人になるのを防ぐ。理由を出して受け付けない）
  - 管理者がパスワードを再設定すると、その人が開いている全部の端末のログインが切れる
  - 利用者が自分でログアウトしたとき、切れるのはその端末だけ。自分でパスワードを変えたときも他の端末は残る
  - 同じメールアドレスのアカウントは作れない。既にあるときは理由を出して受け付けない
  - 管理の画面で受け付ける値は、名前 1〜50 文字、初期パスワードと再設定のパスワード 8〜200 文字、利用者が自分で変えるパスワードも 8〜200 文字。登録簿に無い学びの権限は受け付けない。範囲から外れたときは、どの項目がどう悪いかを日本語で示す（§10）
  - アカウントの一覧は作った順に返す。権限の無いアカウントの権限は空として返す
  - 存在しないアカウントを指す操作（権限の付け外し・再設定・削除）は、見つからないものとして扱う

## 5. 機能要件

### 5.1 学習（インプット）

- **分野 → 単元（中分類）→ 論点** の階層で辿れる。大項目（§3.2 の 9 件）は単元一覧の見出しとして出す
- **階層の一覧** — 分野の一覧と単元の一覧に、その下の論点数・過去問数・「理解した数／論点数」を出す。分野は登録簿の順、単元は中分類の番号順に並べる
- **論点一覧** — 各論点に「出題頻度（◯回）」と自分の理解度を表示。頻度順に並べ替えられる（取り込み済みの回数）も出す
  - 並べ替えは出題頻度順・名前順。絞り込みは分野・単元・理解度（複数選べる）。単元の名前と同じ小項目名は出さない。理解度の絞り込みを全部外したときは、結果を空の一覧として出し、1 つ以上選ぶ促しとすべて表示に戻す手段を出す
- **論点の学習画面**
  - 解説（短い説明）と、展開して読む詳しい解説・周辺知識
  - この論点が出題された過去問の一覧（出典付き）
  - 理解度を3段階で記録: 未理解 / やや理解 / 理解
  - 過去問の一覧は、答えを押したときだけ正解を出す。解説は正解を出したあとだけ見られる。最初は先頭の数問だけを出し、続きは求めたときに足す
  - 理解度は押した時点で選ばれた見た目になり、記録の完了を待たない。記録に失敗したときは押す前の段階に戻し、教材は消さずにその場で理由を出す（§16.5）
  - 理解度は段階の文字と色の両方で示す（未理解＝グレー／やや理解＝オレンジ／理解＝青）。記録が無い論点は未理解として示す（色だけに頼らない）
- **おすすめ順の提示** — 「出題頻度が高く、まだ理解していない論点」を上から並べる。これが最短経路の実体
  - ホームの「次に学ぶ」には、論点名・出題回数・分野を出す。候補が無いときは節ごと出さない
  - 論点の詳細にも「次に学ぶ」（同じ定義の先頭。いま開いている論点は除く）を添え、候補が尽きたときは「ひととおり学べた」と伝えて論点一覧への導線を出す

### 5.2 演習（過去問を解く）

- **論点別ドリル** — 論点を学習した直後に、その論点の過去問だけを解く
- **分野別・カテゴリ別演習** — 範囲を絞って解く
- **弱点復習** — 間違えた問題と、理解度が低い論点の問題を優先的に出す。理解度が低い論点とは、理解度を記録して未理解・やや理解にした論点（記録の無い論点は含めない）。間違えた問題を先に詰め、余りを理解度が低い論点の過去問（出題頻度の高い論点から）で埋める。理解度が低い論点の過去問には正解したことのある問題も含まれる（定着した問題の除外だけが掛かる）。除外で「範囲の問題が全部無くなる」かは、間違えた問題と理解度由来を合わせた全体で見る
- **定着した問題の除外** — 連続正解した問題は、演習（論点別・分野別・カテゴリ別・弱点復習）とランダム構成の模試で当面出題しない（回数は設定可能にする）。公開回の通し受験は原本どおりなので除外しない。範囲の問題が除外で全部無くなるときは除外しない
- **練習テストの画面** — 選べる範囲（論点別ドリル・分野別・カテゴリ別・弱点復習）とそれぞれの問題数、進行中のテストの有無を出す。カテゴリ別は「カテゴリ別」の見出しの節に置き、分野を選んだあと、その分野の単元（中分類）の一覧をそのとき取りに行って並べ、単元を選ぶと確認を挟まずに始める。進行中のテストがあるあいだも分野は選べるが、単元（開始）は押せない。範囲の一覧と進行中の確認のどちらかだけが取れなかったときは、取れた側を出し、取れなかった側に理由と読み直す手段を出す（§16.5）
- **1 回の問題数** — 論点別ドリルと模試は設定値（§5.4）から決め、分野別・カテゴリ別・弱点復習は 20 問。いずれも 1 問以上 100 問以下。範囲に過去問が 1 問も無いときは始めず、理由を出す
- **弱点復習の並び** — 最後に間違えた時刻の新しい順
- **回答と判定** — 選択肢を押すとその場で正誤が分かる。選んだ選択肢と正解の選択肢を色と文字の両方で示し、「次の問題へ」で進む。送信中と判定後は選択肢を押せない（二重に送らない）。あと何問残っているかを画面に出す。回答した時刻を記録する（§5.5-9 の計測で使う）
- **問題ごとの解説** — 正解の根拠と、選択肢ごとの 1 行（誤答が何の説明か）で出す。正解の行を目立たせる。誤答の説明に出る用語は押せる語にする（§16.1）。解説が用意されていない問題では、解説の見出しも出さない

### 5.3 模擬試験

- **本番形式** — 四肢択一。問題数と制限時間は対象ごとの値（§5.8）
  - 出題構成: ①公開回をそのまま1セットとして解く ②分野比率（§5.8）に沿ってランダム構成 — **両方を持つ**。①は本番の追体験、②は繰り返し使える。②の並びは毎回同じにならない。②で分野の付いた過去問が比率に足りないときは分野の付いていない過去問で埋める（分類の穴を隠さない。消す案）
  - **公開回の一覧** — 新しい回から並べ、回ごとに自分の受験回数と最高正答数を出す
- **制限時間あり**（前身アプリ には無かった機能なので新規実装）
- **合否判定** — 合否の目安は対象ごとの値（§5.8）。分野ごとの基準点がある対象では分野別の正答率にも達否の色を付け、基準点を置かない対象では総合だけで示す。届いている／いないで文言と色を出し分ける
  - ※ 300点/1000点・600点/1000点を素点の割合に読み替えた**近似値**。IRT のため公式スコアとは一致しない旨を画面に明記する
- **結果画面** — 分野別の正答率、間違えた問題とその論点へのリンク。誤答だけを初めに出し、「すべて」に切り替えられる。各問に自分の解答と正解を並べ、解説は畳んで開く形にする。合否の目安・基準・近似である旨の断り書きは模試の結果だけに出し、演習の結果には出さない
- **模試の最中は 1 問ごとの正誤も解説も出さない**（本番形式のため。演習との違い）。正誤と解説は結果画面で見る

### 5.6 新しい版の反映（2026-09-16 合意）

画面は最初に開いたときの束を持ち続けるので、デプロイしても開いている画面には届かない。
ビルドのたびに `version.json`（コミットの短い ID と時刻）を静的ファイルとして出し、画面は**画面を移るときと 5 分おき**にそれを取りに行く。
違っていたら上部に「新しい版があります。」の帯と「更新」ボタンを出す。**自動では読み直さない**（テスト中の入力を失わせない。本人の決定「帯を出させましょう」）。
更新で読み直すと、覚えていた分野・単元の集計（apiCached）も捨てられる。
見比べる相手は、最初に取れた版の印を 1 度だけ覚えたもの。版の印が取れなかったときは新しい版が無いものとして扱い、帯を出さない。最初の印が取れなかったときは、次に取れた値を最初の印にし、その回は帯を出さない。ビルドのたびに版の印（コミットの短い ID と時刻）を配信物に書き出す。

### 5.7 演習・模試の共通の決まり

演習（§5.2）・模試（§5.3）・ロードマップ型の「この日の確認」（§13.6）に共通の決まり。対象ごとの値は §5.8。

**出題時スナップショット**
- 出題した時点の問題文・選択肢・正解・出典を保存する。あとで問題データを直しても、当時の内容で採点と振り返りができる
- 採点は出題時の正解で行う（現在のデータの正解では行わない）
- 出題中の問題には正解と解説を渡さない（回答したあとに渡す）

**進行中は 1 人 1 つ**
- 進行中のテストがあるあいだは新しく始められない。始めようとしたときは、進行中の範囲と回答済み／全体の数を示して「再開」か「破棄」を促す
- 進行中があるあいだ、開始の操作は押せない形にする

**中断と再開**
- 未回答のうち最も小さい番号が現在位置。「中断してホームへ」でいつでも抜けられる（回答は残る）
- ホーム（ロードマップ型はロードマップの先頭）と練習テストの画面に進行中の案内を出し、範囲と回答済み／全体を示して「再開する」で出題の画面へ戻れる
- 画面が持っている位置とサーバの位置が食い違ったときは採点せず、ずれた旨とサーバの位置を伝えて現在の問題を取り直す

**破棄**
- 進行中のテストを捨てられる。捨てると、そのテストの回答も一緒に消える
- 捨てる前に、回答済みの問数を示して確かめる。すでに無いときは成功として扱う
- 捨てるのに失敗したときは理由を出し、進行中の案内は消さない（§16.5）

**始めるときと締めるとき**
- 始める前に確かめる。模試は制限時間が始まる旨、「この日の確認」は範囲と問数を示す
- 締めると完了になり、正答数と締めた時刻を記録する。2 回押しても結果は変わらない
- テストを作ると、範囲の名前・問題数・制限時間（無い対象は無し）を返す
- 未回答を残したまま「ここまでで採点する」で締められる。その前に残りの問数を示して確かめる
- 締めるのに失敗したときは理由を出し、「まだ採点できていません」と伝えて押し直せるようにする
- 終わったテスト、未回答が残っていないテストへの回答は受け付けない（記録を増やさない）

**制限時間**（時間を持つ対象だけ。§5.8）
- 残り時間を画面の上部に出し、1 秒ごとに減らす。残り 5 分未満で見た目を変える
- 残り 0 になったら自動的に締めて結果画面へ移す。時間を過ぎたあとの回答は受け付けず、時間切れの印を付ける
- 時間切れかどうかは「締めた時刻が開始＋制限時間を過ぎているか」で決める。制限時間内に自分で締めた回は時間切れにしない
- 時間切れで締めた回の結果には「そこまでの回答で採点した」旨を出す

**結果と履歴**
- 完了していないテストの結果は出さない（未回答の問題の正解と解説が見えてしまうため）
- テストを指す画面と API は本人のものだけを開く。他の人のものは見つからないものとして扱う
- 受験履歴は、締めたテストを新しい順に一覧する。1 行に種別の表示名・範囲・正答率・日時を出し、押すと結果画面へ移る。出す件数に上限を置く。取得前と 0 件を区別し、0 件のときだけ履歴が無い旨を出す

### 5.8 対象ごとの値

値の実体は登録簿（§17）。コードは対象名を列挙しない。

| 対象 | 1 回の問題数 | 制限時間 | 合否の目安 | ランダム構成の分野比率 |
| --- | --- | --- | --- | --- |
| IT パスポート（ip） | 100 問 | 120 分 | 総合 60% かつ 各分野 30% | 35 / 20 / 45 問程度 |
| 応用情報 午前（ap） | 80 問 | 150 分 | 総合 60%（分野ごとの基準点は置かない） | 置かない |
| ロードマップ型（itc / mkt / msg …） | その日の単位数 × 登録簿の `questionsPerRound` | 置かない | 出さない | 置かない |

- 合否の目安は素点の割合に読み替えた近似値で、公式スコアとは算出方法が異なる旨を画面に出す（§2.5）
- 分野ごとの基準点を置く対象だけ、結果画面の分野別の正答率に達否の色を付ける（§5.3）
- 制限時間を置かない対象では、時計も自動の締めも出さない（§5.7）

## 7. コンテンツ構築パイプライン

本プロジェクトの山場。アプリ実行時ではなく**オフラインのバッチ処理**として作り、成果物を DB に流し込む。

```
IPA の PDF（29回分 × 問題冊子 + 解答例）           ✅ scripts/fetch_pdfs.py
   ├─ 解答例 → テキスト抽出 → 正解表 2,900問       ✅ scripts/extract_answer_keys.py
   │                                                      → data/answer_keys.json
   └─ 問題冊子（1,450頁の画像）
        ↓ ① ページを画像にレンダリング                   ✅ scripts/render_pages.py
        ↓ ② ビジョンモデルで問題文・選択肢を読み取り     ✅ scripts/prompts/extract_questions.md
        ↓ ③ 結合・正規化・構造検証                       ✅ scripts/merge_questions.py
        ↓ ④ 抽出テキストだけで解かせ、正解表と突合       ✅ scripts/check_answerability.py
     過去問データ（令和6年度 100問は完了。残り28回分）
        ↓ ⑤ シラバス項目への自動分類（AI）＋ 人手レビュー   ← 次はここ
        ↓ ⑥ 論点の抽出と、過去問への紐付け（M:N）
        ↓ ⑦ 論点ごとの解説・周辺知識を生成（AI）＋ 人手レビュー
     DB へ投入
```

**令和6年度（100問）での検証結果**

| 指標 | 結果 |
| --- | --- |
| 抽出できた問題 | **100/100**（欠番・重複なし） |
| 構造チェック | 選択肢4つ・重複なし・図表の整合性すべて通過 |
| 図表を含む問題 | 15問（表・アローダイアグラム・擬似言語・信頼性ブロック図など） |
| **抽出テキストだけで解いた正答率** | **100/100（100%）** |
| テキストだけでは解けないと申告された問題 | **0件**（15問の図表問題を含めて0） |

正答率100%は「読み取りが原文どおりである」ことの証明にはならない（IT パスポート
程度なら多少の欠損があっても知識で正答できてしまう）。ただし**解答不能の申告が
0件だったこと**、とりわけ図表15問すべてが図の情報だけで解けたことは、
`figure_description` が実用に足る精度で書き起こせている強い証拠になる。

**見つかった問題と対処**

読み取りを9分割したところ、**チャンク単位の系統的なブレ**が出た。個々の問題を見ても
気付けない種類の欠陥で、29回分に広げると効いてくる。

| 症状 | 実際に起きたこと | 対処 |
| --- | --- | --- |
| 句読点の流儀が担当範囲ごとに違う | chunk_02（問12-28）だけ句点が「．」。他は「。」（52箇所） | `merge_questions.py` で自動正規化。小数点を壊さないよう前後が数字なら置換しない |
| 箇条書きの置き場所が不統一 | `text` に改行区切り / 全角スペース連結 / `figure_description` 側 の3通りが混在 | 自動修正は不可能。`scripts/prompts/extract_questions.md` で仕様を固定し、マージ時にブレを警告 |
| `has_figure` の基準が不統一 | 問94（箇条書きのみ）が true、同種の問96・97 は false | 同上。「視覚的なブロックがある場合だけ true」と明文化 |

なお IPA 原文の句読点は**読点「，」・句点「。」**であることを、600dpi に拡大して
目視で確定させた。

**押さえるべき点**

- ②の読み取り精度がすべての土台。図表を含む問題（特にテクノロジ系）は崩れやすいので、**④で検証できない問題は人手確認に回す**仕組みを最初から入れる
- ④の突合には限界がある。正解表と照合できるのは「正解記号が妥当か」までで、**問題文の誤読は検出できない**。別途サンプリング検査が要る
- ⑤⑥は AI に任せきりにできない。**管理画面で分類を直せること**（§5.4）が前提
- ⑦の解説は IPA が公開していない（正解記号のみ）。**自作となり、その部分の著作権はこちら側に帰属する**
- 取り込みの安定キーとして、過去問には `外部ID`（例: `2024r06-q17`）を持たせる。再取り込み時に UPSERT できるようにする（前身アプリ の `externalId` と同じ発想）
- 新年度は**毎年4月頃**に公開される。`fetch_pdfs.py` は既存ファイルをスキップするので、再実行すれば差分だけ取得できる

### 13.6 ロードマップ型のメニューを 2 つに絞る（2026-09-18 決定、v0.9）

**決めた理由。** 同じコードで 2 種類の学びを出している。資格版（ip / ap）は 1 論点に過去問が何十問もあり、練習・通し受験・履歴がそれぞれ働く。
ロードマップ型は 1 単位 2 問しかなく、**同じ問題が単位の下に並んでいる**ので、別画面の練習テストとドリルは重複だった（本人 2026-09-18「練習テストは機能していない」「教材の中のドリルは下に同じ問題がある」）。
あわせて、確認問題そのものが品質の指標にならないと分かった（`brain/reports/27`。形だけで 84/84・129/130 が当てられる）。テスト系の画面を前面に置く理由はさらに弱い。

| 画面 | ロードマップ型（2026-09-18 以降） | 資格版（据え置き） |
| --- | --- | --- |
| 上部メニュー | **「ロードマップ」「フィードバック」の 2 つだけ** | ホーム／学習／練習テスト／確認テスト／履歴／フィードバック |
| ホーム | **無くす。** `/` はロードマップへ送る。進捗（理解 n / N・連続日数）と「前回の続きから」はロードマップの先頭に置く | 据え置き |
| 練習テスト | **無くす**（単位の下の問題と同じものを引くだけ） | 据え置き |
| 確認テスト | **無くす（独立した画面としては）。** ロードマップの各日の見出しに「この日の確認（N 問）」を置く。範囲はその日の単位、通しで受ける形は無くす。押す前に範囲と問数を示して確かめ、進行中のテストがあるときは移らずその場で進行中の案内を出す（§5.7） | 据え置き |
| 履歴 | **無くす。** 各日の見出しに、その日の確認テストの結果（受けたか・何問正解か）を出す | 据え置き |
| 教材の中のドリル | **無くす**（同じ問題が同じ画面の下にある） | 据え置き（1 論点に過去問が多数あり、時間を測って記録に残る演習として働く） |

**失うもの。** 通しで受ける形と、受験の記録の一覧。受け皿は各日の結果表示。ここが無いと機能が減っただけになるので、同じ作業で入れる。
**触らないもの。** 進行中のテストがある場合の再開の案内（データが残っているので、行き先が無いと迷子になる）。

## 15. SSO と権限 — まなびばが認証の正本（2026-09-17 決定、v0.8）

本人「やっぱ SSO しようよ」。審議: Cloudflare Access は pages.dev の本番に掛けられない（原文: preview deployments だけを保護）ため、
**自作 SSO（pages.dev のまま、費用ゼロ）**を選んだ（A: ドメイン購入＋Access は見送り）。所有者がアカウント作成時に権限を設定し、後から変える。既存のアカウントは名前・メール・パスワードを引き継ぐ。

### しくみ
- **まなびば**（Pages `manabiba` ＋ D1 `manabiba-db`）が認証と権限の正本。表: `accounts`（メール一意・名前・パスワードハッシュ・役割 ADMIN/MEMBER）、`grants`（アカウント × 学び）、`sessions`（Cookie のセッション、30 日）、`sso_codes`（学びへ渡す使い捨てコード、2 分）
- 学び側で「まなびばでログイン」→ `まなびば/sso/start?app=<key>` → 未ログインならまなびばのログイン → 権限があれば使い捨てコードを付けて `学び/sso/callback?code=…` へ戻す → 学び側サーバが `まなびば/api/sso/exchange`（共有秘密 `SSO_SECRET`）でコードをメールと名前に交換 → 学び側の `users` にメールで見つけるか作る（パスワード列は `sso`）→ 学び側の従来のトークンを発行。以後は今までどおり
- 学び側の `/api/auth/login` と `/register` は、`SSO_PORTAL_URL` が設定された環境（本番）では 404。ローカル（未設定）では従来どおり動くので、API 検査（check_api）はそのまま
- 管理: まなびばの管理画面（役割 ADMIN のみ）。アカウントの一覧・作成（メール・名前・初期パスワード・権限）・権限の付け外し・パスワード再設定・削除。利用者は自分のパスワードだけ変えられる
- 移行: 4 つの学びの `users` をメールで名寄せしてまなびばへ（`scripts/portal_migrate_accounts.py`）。同じメールが複数の学びにあれば 1 アカウントに束ね、元の学びの権限を付ける。パスワードのハッシュは同じ形式（PBKDF2）なのでそのまま移す。管理者は所有者のメール 1 つ。旧 `admin@example.com`（既定値の管理者。brain 2026-08-31）は移さない
- 入口の一覧は権限のある学びだけ「開く」、無いものは「権限なし」と出す（一覧の存在は隠さない）

- まなびばの入口は、学びの一覧（名前・種類・説明・入口。秘密は含めない）と本人のアカウントと権限を返す。ログインしていない人には本人と権限を返さない
- 学び側の画面は、その環境が SSO かどうか・まなびばの場所・自分の対象の key を聞ける。共有秘密が設定済みかどうかは返さない
- 権限の無い学びへ入ろうとしたときは拒否（denied）だけを返し、使い捨てコードを作らない。ログインしていないときはまなびばのログイン画面へ送る。ログイン後の戻り先はまなびば側が組み、外から渡された行き先は使わない
- 戻り（`学び/sso/callback`）でコードが無い・交換に失敗したときは、ログインさせずに「ログインできなかった」旨と理由、まなびばへ戻る導線を出す
- 認証に失敗したときは 401 で、文はメールアドレスが登録されているかどうかで変えない
- 共有秘密が違う・無い呼び出しは 403 で拒む（共有秘密の確認は本文の検証より先）。まなびばに届かないときは 502、共有秘密が設定されていないときは 503 を返し、設定の不足を画面に出さない
- 学び側のトークンは JWT（HS256）で、本人を指す値・名前・役割を持ち、14 日で切れる。秘密は入れない
- 管理の画面と管理の操作は、役割が管理者でない人を 403 で拒み、理由を返す。まなびばの本人・自分のパスワードの変更・ログアウト・管理は、ログインしていない人には 401（死活確認と学びの一覧だけは認証なし。§17）

### 守ること
- 共有秘密 `SSO_SECRET` は Pages の secret（まなびばと 4 つの学び）。コード・登録簿には書かない
- 使い捨てコードは 1 回・2 分。交換時に権限を再確認する（付け外しの直後でも通らない）
- Cookie は HttpOnly・SameSite=Lax。Secure は https のときだけ付ける（ローカルの http では付かない）。パスワード変更は現在のパスワードを要求し、違うときは 401 で受け付けない
- パスワードは PBKDF2（SHA-256）で保存し、毎回別のソルトを使う。反復回数は 100,000 以下（Cloudflare Workers の上限）。照合にかかる時間は入力の内容で変えない。保存されている値が壊れているときは一致しないものとして扱う
- 学び側の `users` は消さない（進捗・受験履歴の外部キー）。SSO で作る行はパスワード列に `sso` を置き、パスワードログインは受けない
- 不変条件 D17（アカウントの正本はまなびば。学び側で register を復活させない）と O13（`SSO_SECRET` が 5 か所で同じ）を `docs/不変条件と門.md` に登録

## 16. 画面の共通の振る舞い（全対象）

資格版・ロードマップ型を問わず、学び側の画面が共通に守ること。ユースケースの `source` から参照される規範的な節。

### 16.1 本文の描画
- 教材・解説の本文は **記法（見出し ###・箇条書き・番号付き・太字・表・`[[用語]]`）だけを解釈**し、それ以外は書かれた文字のまま出す
- `[[用語]]` は用語集を引いて色付きの押せる語になり、押すと 1 行の説明と（論点があれば）「この論点を学ぶ →」が出る。太字の中でも効く。用語集の 1 行説明は問題解説の note の 1 文目
- 教材の図は `/figures/materials/<試験>/<id>-<n>.svg` の実在する画像だけを画像にし、他の画像記法は文字のまま出す
- 用語集は画面を開いている間に 1 度だけ引く。引けていない間は色を付けず、書かれた文字のまま出す。引けなかったときも本文はそのまま出す（用語が無いのと同じ扱い）
- 用語集はログインした人だけが引け、用語の順で全語（用語・1 行説明・紐づく論点）を返す
- 本文に出す用語の表示名は、末尾の括弧書き（読み・英字表記）を落として短くする。ポップの見出しは正式な表記のまま出す
- 教材の図もタップで原寸に切り替える（過去問の図と同じ。§16.2）

### 16.2 過去問の表示
- 図として描かれた過去問は、原本から切り出した画像（`public/figures/<試験>/`。試験ごとに分ける）を出し、書き起こし（表・擬似言語）を併記する。画像はタップで原寸に切り替える。表だけの問題は書き起こしを本体として出す
- 組合せを問う選択肢（a：…／b：… の並び）は項目の切れ目で改行して縦に並べる。普通の読点では割らない。データは変えない
- 同一内容（`content_key` が同じ）の過去問は学習側で 1 問にまとめて代表は最新の回にし、画面に「同一の問題が N 回出題されています」と他の出典を出す。公開回をそのまま 1 セットとして受ける形（§5.3①）だけは原本どおりで畳まない（本番の追体験のため）。分野比率に沿ったランダム構成（§5.3②）は学習側と同じく畳む（繰り返し使う形なので同じ問題が 2 度出るのを避ける）。出題頻度は重複を数えたまま（§3.1）
- 選択肢の記号は「ア・イ・ウ・エ」。組合せを問う選択肢は、30 字を超えるときに項目の切れ目で改行して縦に並べる（30 字以下は 1 行のまま）
- 書き起こしの解析は、閉じていない囲みや列数の揃わない表でも止まらない。読めないところは文としてそのまま出す
- 同一内容の代表を選ぶときの「回の新しさ」は、年 → 実施時期（春 → 10 月 → 秋。時期の無い回はその年で最後）の順で比べる
- 弱点復習で出す問題の「同一の問題が N 回」と他の出典は、範囲の中だけでなく過去問全体から数え直す

### 16.3 一覧・戻り・記憶
- 一覧は取得前を `null`、結果が空を `[]` で区別し、読み込み中に「該当なし」を出さない
- 一覧以外の画面の左上に、行き先とラベルを明示した戻るリンクを置く（ブラウザの履歴に頼らない。タップ領域 44px）
- 最後に開いた論点と画面を端末に覚え、ホーム（ロードマップ型はロードマップの先頭）から「前回の続き」で戻れる
- 分野・カテゴリの集計は画面を開いている間だけ覚えて取り直さず、理解度を変えたら捨てる。失敗した取得は覚えない
- 「前回の続き」に覚えるのは、最後に開いた論点の ID・名前・単元名・単元の番号と画面。端末が覚えられないときも画面は止まらない。覚えた値が読めないときは「前回の続き」を出さないだけにする

### 16.4 認証状態と API の失敗の扱い
- 発行されたトークンは端末の `localStorage` に保存し、以後の API 呼び出しに `Authorization: Bearer` で付ける。ログアウトと 401 で捨て、捨てるときは「前回の続き」も消す
- ヘッダーにログインしている本人の名前を出す。名前はトークンの中身から読み、サーバに聞かない
- API の失敗は本文 `{error}` を画面に出せる形（message・status・body）で投げる。通信できないときは status 無しで日本語の固定文
- トークン付きで 401 なら期限切れの印を立ててトークンを捨て、ログイン画面で **1 度だけ** 理由を伝える。自分でログアウトしたときは出さない
- 期限切れのときログイン画面に出す文は「ログインの有効期限が切れました。もう一度ログインしてください。」
- API の失敗の本文 `{error}` が無いときは既定の日本語の 1 文を message にする

### 16.5 失敗時の画面の共通の決まり

- **取得の失敗**（一覧・集計・教材・問題・結果）— 失敗した旨と理由を、その中身が出るはずだった場所に出し、読み直す手段を添える。読み込み中の表示は消す
- **操作の失敗**（理解度の記録・回答・締め・破棄・送信）— 理由を出して押し直せるようにする。画面の中身は消さず、押す前の見た目に戻す
- **画面の一部だけが取れなかったとき** — 取れた部分は出し、取れなかった部分だけを欠いたまま見せる（画面全体を失敗にしない）
- **読み込み中と空を区別する** — 一覧は取得前と結果が空を区別し、読み込み中に「該当なし」を出さない（§16.3）
- 通信できないときは日本語の固定文で伝える（§16.4）
- 端末の記憶（前回の続き・フィードバックの添え先・覚えた集計）が使えない／読めないときは、その機能を出さないだけにして画面を止めない

## 17. 運用の土台

- 学び側とまなびばの `/api/health` は認証なしで `{ok: true}` を返す（監視と検査スクリプトの死活確認）
- 学び側のデータは学びごとの Cloudflare D1 に保存し、サーバは drizzle のスキーマ定義を通して読み書きする。生 SQL の連結はしない
- トークンの署名の秘密は環境の `JWT_SECRET`（Pages の secret）から読む。未設定の環境（ローカル）では開発用の既定値を使う（本番で未設定なら止める形に改めるかは判断待ち）
- 対象（試験・題材）ごとの名前・種類・設定は登録簿 `src/shared/targets.json` の 1 か所から読み、コードは対象名を列挙しない。知らない対象の key や key の無い呼び出しは既定の対象（ip）として扱う
- トークンの署名は HS256（共有秘密方式）。発行と検証で同じ秘密を使う
- 試験名が対象と違う過去問、年度ラベルが内部の記号のままの過去問は投入しない
- 同一内容の過去問で正解が割れていたら seed の門で止める。出典（試験・年度ラベル・問番号）の無い過去問は投入しない
- 回ごとの問題数（資格版は回ごとの定数。IP 100・AP 80。ロードマップ型は 1 日の単位数 × 登録簿の questionsPerRound）が合わない seed は投入しない
- 全 POST/PUT の入力は zod で検証し、失敗は 400・本文 `{error: 日本語}`（§10）。認証が要る API は Bearer トークンを要求し、無い・壊れている・期限切れは 401
