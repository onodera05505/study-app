## 前提条件
- まなびばに役割 ADMIN のアカウントがあり、その人でログイン中（Cookie のセッションがある）
- 権限を付けられる学びが、まなびばの学びの登録簿に載っている
- 更新・パスワードの再設定・削除の相手となるアカウントはすでにあり、その人が別の端末でログイン中のこともある

## 基本の流れ
1. 管理者が管理の API を呼ぶ。まなびばは役割が ADMIN の呼び出しだけを通し、利用者の呼び出しは断る
2. 管理者がアカウントの一覧を求める。まなびばは全アカウントの名前・メール・役割・作成時刻と、その人に付いている学びの権限を返す
3. 管理者がメール・名前・初期パスワード・開ける学びを入れて作成する。まなびばはアカウントと権限の行を作り、役割の既定を利用者にする
4. 管理者が名前・役割・開ける学びを送って更新する。まなびばは送られた学びの一覧で今の権限を置き換える
5. 管理者が、別の端末でログイン中の人のパスワードを再設定する。まなびばはハッシュを入れ替え、その人が開いているセッションを全部切る
6. 管理者がアカウントを削除する。まなびばはアカウントとその権限を消す（学び側の利用者と進捗は消さない）

## 例外の流れ
E1. 3・4・5 で入力が正しくない（メールの形・名前の長さ・パスワードの長さ・知らない学び）。まなびばは 400 と {error} を返し、何も変えない
E2. 3 で同じメールのアカウントがすでにある。まなびばは 409 を返し、作らない
E3. 4 で管理者が自分の役割を利用者に変えようとした。まなびばは 400 を返し、役割を変えない
E4. 6 で管理者が自分を削除しようとした。まなびばは 400 を返し、消さない
E5. 4・5・6 で指定した ID のアカウントが無い。まなびばは 404 を返す

## 事後条件
- accounts と grants が管理者の操作どおりになっている
- 管理者自身の管理者権限とアカウントは残っている
- 学び側の users と進捗・受験履歴は消えていない
