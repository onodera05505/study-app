## 前提条件
- 学び側とまなびばがそれぞれ Pages の Worker として動き、D1 のバインディングがある
- 学び側の環境にトークンの署名の秘密がある（UC-017）

## 基本の流れ
1. 呼び出し元が学び側の API を呼ぶ。学び側は全応答にセキュリティヘッダ（CSP・HSTS・X-Frame-Options DENY・nosniff・Referrer-Policy）を付ける
2. 呼び出し元がまなびばの API を呼ぶ。まなびばも全応答に同じセキュリティヘッダを付ける
3. 呼び出し元が学び側の保護された API を Bearer トークン付きで呼ぶ。学び側はトークンの署名と期限を確かめ、本人を確定してから処理に進む
4. 呼び出し元がまなびばのログインが要る API を呼ぶ。まなびばはセッションの Cookie から本人を確定してから処理に進む
5. 呼び出し元が POST で本文を送る。サーバは本文をスキーマで検証し、通った値だけを使う
6. 呼び出し元がパスワードを含む本文を送る。サーバはパスワードを平文で持たず、ハッシュにして保存し、照合もハッシュで行う

## 例外の流れ
E1. 5 で本文が検証を通らない。サーバは 400 を返し、本文はどの項目が悪いか分かる日本語の {error} にする
E2. 呼び出し元が学び側の知らない API の経路を呼ぶ。サーバは 404 と {error} を返す
E3. 処理の途中で想定していない例外が起きた。サーバは固定の文の 500 を返し、内部の情報を本文に出さない

## 事後条件
- 保護された API は本人として呼ばれたときだけ処理され、失敗はステータスと日本語の {error} で返る
- 全応答に 5 つのセキュリティヘッダが載っている
- 利用者は自分のデータにしか触れない（資源ごとの持ち主の確認は、その資源を扱う UC の要件にある）
