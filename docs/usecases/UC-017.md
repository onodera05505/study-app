## 前提条件
- 学び側とまなびばが本番に配備され、それぞれ D1 のバインディングを持っている

## 基本の流れ
1. 運用者が学び側の死活確認の経路を認証なしで叩く。学び側は {ok: true} を返す
2. 運用者がまなびばの死活確認の経路を認証なしで叩く。まなびばは {ok: true} を返す
3. 運用者が本番のトークンの秘密が設定されていることを確かめる。サーバは署名の秘密を環境の JWT_SECRET から読む
4. 運用者がデータの保存先を確かめる。サーバは学びごとの D1 を、スキーマ定義を通してだけ読み書きする
5. 運用者が対象（試験・題材）の名前と設定を確かめる。サーバは登録簿の 1 か所から解決し、コードは対象名を列挙しない
6. 運用者が seed を投入する前に、門が回ごとの問題数（資格版は回ごとの定数、ロードマップ型は 1 日の単位数 × 登録簿の questionsPerRound）を確かめる
7. 運用者が本番の各 Pages プロジェクトの秘密の一覧を機械で確かめる。共有秘密 SSO_SECRET（まなびばと各学び）とトークンの秘密 JWT_SECRET（各学び）が設定されている（値は読まない）

## 例外の流れ
E1. 3 で JWT_SECRET が設定されていない（ローカルの開発）。サーバは開発用の既定値を使う
E2. 5 で知らない対象の key が渡された、または対象が指定されていない。サーバは既定の対象に倒れる

## 事後条件
- 死活確認は認証なしで通り、他の API は同じ条件で 401 になる
- 対象を足しても、コードではなく登録簿の 1 か所を直せば済む
