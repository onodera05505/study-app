# フィードバックの採否の判断基準（規則。育てる）

目的: 審議の判定を規則の ID で説明できるようにし、規則が安定したら「人の確認なしで採用（自動）」に昇格させる（本人 2026-09-16）。
書式: `R<番号>` ・ 条件 ・ 判定 ・ 状態（**人が確認**／**自動可**）・ 実例の件数（審議台帳の行数）。
規則を変えるときは消さず「以前は X → 今は Y（日付）」で残す。判定は `brain/feedback/審議台帳.md` に 1 行ずつ、規則 ID を名指しして溜める。

| ID | 条件 | 判定 | 状態 | 実例 |
| --- | --- | --- | --- | --- |
| R1 | 事実として再現し、要件・設計の中核・不変条件に反さず、誰にでも起きる不具合（バグ） | 採用。直す | 人が確認（3 例で自動可に昇格を検討） | 2 |
| R2 | 一般的な期待（他の同種アプリでは当然あるもの）で、費用が小（1 画面・1 部品）、意図に反しない | 採用 | 人が確認 | 2 |
| R3 | 要件の意図（§13 の「ロードマップらしさ」など）に**合致する方向**の仕様変更 | 採用。要件定義書に骨子を書いてから | 人が確認（仕様変更は常に本人） | 1 |
| R4 | 設計の中核（頻出＝重要度、次に学ぶの出口、論点 ID の固定…）に触る変更 | 保留か条件付き（触らない範囲に絞る）。本人が決める | 人が確認（自動化しない） | 1 |
| R5 | 言い回し・見た目の好み（文言・色・並び）で、費用ゼロ〜小 | **所有者**の声なら採用。所有者以外の 1 人の声なら保留し、2 人目で採用 | 人が確認 | 3 |
| R6 | 手段が指定された要望（「警告を出して」「ボタンを足して」）で、目的（入力を失わない等）が読める | 目的に置き換え、既知の穴（中央の報告書）を避ける別の形で応えてよい。手段どおりにしない理由を note に | 人が確認 | 1 |
| R7 | 内容側（教材・解説の書き方）の指摘で、仕様書の規則が原因のもの | 採用。仕様書の規則を直してから全件に当てる（1 か所だけ直さない） | 人が確認 | 2 |
| R8 | 資格版とロードマップ型で意味が違う指摘（並び・ホーム・見出し） | 対象の種類ごとに判定を分ける。片方に当てる変更が共用コードを通るなら受入で他方を起こす | 人が確認 | 3 |
| R9 | 事実が再現しない・原本と一致している（誤報） | 不採用。理由を note に（誤報 7/8 の実績） | 人が確認 | 0 |
| R10 | 送った本人の意図を推測で広げないと応えられない | 保留。本人に聞く経路が無いので、画面側で分かる形にできるかだけ考える | 人が確認 | 0 |

## 自動化への道筋
1. 各判定が規則 ID を名指しする（審議台帳）
2. 同じ規則で 3 件以上、本人の判定と案が一致したら、その規則を「自動可」に昇格（表の状態を変える）
3. 「自動可」の規則に当たる件は、審議の表を出さずに直して `mark done` し、締めの報告にまとめて書く。当たらない件だけ表を出す
4. 本人が判定を覆した件は、規則を分割するか条件を足す（覆しは規則の穴）
